# S20+ 메인라인 부팅 조사 — 커널 적재 위치와 기기 트리 인계

대상은 SM-G986N / y2q / G986NKSS8IYC2다. 순정 부트로더가 선택할 수 있는 커널 적재 위치 일부에서 기존 UniLoader가 FDT를 읽기 전에 정지하는 조건을 재현했다. 지난 실기에서 선택된 위치나 마지막 실행 명령은 관측되지 않았다. 이번 조사는 보관된 파일과 격리된 QEMU에서 수행했다.

## 순정 부트로더와 기존 후보의 차이

IYC2 배포 ZIP에서 정확한 BL 아카이브의 ABL을 풀고, 펌웨어 볼륨의 이름과 PE 섹션으로 ARM64 LinuxLoader를 식별했다. ARM64 Image를 복사하고 실행하는 코드에서 적재 위치를 32 KiB 단위로 조정하는 경로를 확인했다. 이 경로는 Image 헤더의 런타임 크기를 읽고 커널과 기기 트리 사이의 공간을 검사한다. 최종 ARM64 직접 호출은 조정된 커널 위치와 선택된 FDT를 사용한다. 이미지에 저장된 Android 헤더의 주소 필드만으로 실기 배치를 계산할 수 없다.

소모된 PROCA 후보의 진입 코드는 현재 Image 주소에서 자체 헤더의 text_offset을 빼고 2 MiB 정렬을 검사한다. 실패하면 FDT 검사 함수를 부르기 전에 대기 루프로 분기한다. 후보 안의 삼성 커널 바이트는 원본과 같았고, 바깥 Image의 런타임 크기는 안쪽 Image의 런타임 크기와 2 MiB 접두부의 합과 정확히 일치했다. 삼성 4.19 소스의 초기 진입 코드는 자기 위치의 하위 정렬 비트를 계산해 초기 페이지 테이블 구성에 사용한다. 메인라인 6.18에 사용할 목적지는 그 Image 자체의 text_offset과 런타임 크기를 따라야 한다. [Linux 6.18 ARM64 부팅 규약](https://www.kernel.org/doc/html/v6.18/arch/arm64/booting.html)

| 같은 소모 후보 바이너리로 수행한 QEMU 대조 | 결과 |
| --- | --- |
| 2 MiB 구간 안의 합성 입력 위치 64개. RAM·initrd를 채운 동일 FDT | 1개에서 삼성 커널 첫 명령에 도달했다. 나머지 63개에서 정렬 조건 분기를 한 명령씩 실행해 FDT 검사 전 대기 루프로 들어감을 확인했다. |
| 다음 2 MiB 구간의 정렬된 위치 | 삼성 커널 첫 명령에 도달했다. |
| 정렬된 입력에서 연속된 RAM을 두 항목으로 나눠 후보가 경계에 걸치게 한 대조 | 정렬 분기를 통과한 뒤 FDT 검사 안에서 거부됐다. |

64개는 호스트에서 열거한 배치의 수다. 실기 선택 분포나 과거 실패 확률은 측정하지 않았다. 물리 실기에서 후보 AP 전송과 원본 Magisk 복귀는 확인됐다. 그 사이 180초 안에 후보 Android를 확인하지 못했다. 해당 실행의 종료 커밋은 `8f3aae5d06`이다.

## 같은 메인라인 Image를 다른 위치에서 시작한 결과

QEMU 전용 복사 코드는 서로 겹치지 않는 입력과 목적지를 사용한다. 목적지에 필요한 공간은 파일 크기보다 큰 Image 헤더의 런타임 크기로 계산했다. 기존 y2q용 Linux 6.18 Image와 RAM initramfs를 바이트 그대로 사용했다. 각 양성 사례에서 커널로 분기하기 직전에 전체 복사본, FDT·initrd 원본, 인수 레지스터를 대조했다. USB 장치와 외부 네트워크는 격리했다. [기존 y2q 호스트 빌드](S20PLUS_G986N_MAINLINE_Y2Q_H0_2026-11-22.md)

| 실험 | 관측한 범위 |
| --- | --- |
| QEMU virt FDT, 입력 위치 64개, 별도 정렬된 목적지 | 64개 모두 동일한 빌드의 Linux 6.18이 RAM init을 PID 1로 실행하고 빌드 표식을 출력했다. |
| 복사 거부 대조 6개 | 원본과 겹침, 목적지 정렬 불일치, FDT와 겹침, initrd와 겹침, BSS만 예약 영역과 겹침, RAM 끝 초과를 각각 거부했다. 복사 전후 확인 가능한 목적지 바이트가 일치했다. |
| y2q 메인라인 DTB로 바꾼 두 극단 입력 위치 | 가상 RAM 및 initrd 범위만 채운 y2q DTB 전체를 커널의 FDT 검사 진입점에서 대조했다. 두 경우 모두 실제 `early_init_dt_verify()`가 성공했고 `unflatten_device_tree()`가 호출자에게 돌아왔다. 이 시험의 관측은 여기까지다. |

첫 virt 하네스는 PID 1 표식을 받고도 USB 컨트롤러 부재 표식을 기다리다 시간 제한을 넘겼다. RAM init 소스 자체가 해당 표식을 쓰기 전에 20초를 기다린다. 수정본은 한 기준 사례에서 두 표식을 모두 확인하고, 모든 위치에서 PID 1 표식을 요구했다. y2q DTB 실험의 첫 호스트 판독기는 상위 비트가 설정된 커널 가상 포인터를 음수로 해석했다. 64비트 부호 없는 포인터로 판독을 고쳐 두 사례를 다시 실행했다. 이전 기록도 보존했다.

## 기기별로 남은 입력

보관된 순정 DTB와 한국형 오버레이의 조합 6종은 모두 RAM 크기가 0인 `/memory` 항목을 담고 있었다. y2q 메인라인 DTB의 `/memory@80000000`에도 RAM 크기가 0으로 남아 있었다. 순정 조합별 고정 예약과 메인라인의 고정 예약을 함께 제외하는 호스트 계산에서 이 정적 입력 6개는 모두 목적지를 산출하지 않았다. 합성 RAM 뱅크를 넣은 대조에서는 6종 × 64곳에서 전체 런타임이 들어갈 위치를 찾았다. 각 순정 트리의 실제 고정 예약 안으로 제한하거나 뱅크가 너무 작은 대조 12개는 모두 거부됐다. 이 계산과 virt 복사 시험은 서로 다른 입력에서 수행했다.

기존 S20+ 실행 기록 29개 디렉터리의 파일 3,744개 중 첫 4바이트가 FDT 매직인 독립 파일은 0개였다. 이 검색은 압축·포장된 자료 안의 FDT까지 배제하지 않는다. 다음 판별 자료는 정상 원본 부팅에 사용된 FDT의 RAM 뱅크, 예약 영역, initrd 범위와 크기다. 이를 사용해 입력·목적지의 동시 배치 가능성을 검사하고, 기존 접두부의 단일 뱅크 조건과 비교한다. 원본 부팅의 배치를 알아도 지난 후보 부팅이 어느 분기를 탔는지는 별도 관측이 필요하다. 앞선 ADB Download 대조에서도 원본 복구 후 PMSG 표식 일치가 0건이어서, 해당 경로에서 표식이 없다는 사실만으로 부팅 단계를 배제할 수 없다.

원본 삼성 커널에서 이 자료를 제공하는 코드도 확인했다. 보관한 Magisk Image에는 `CONFIG_OF_EARLY_FLATTREE=y`와 `CONFIG_SYSFS=y`가 들어 있다. IYC2 소스의 `drivers/of/fdt.c`는 초기 FDT가 존재하고 CRC가 일치하면 소유자 읽기 전용인 `/sys/firmware/fdt`를 생성한다. 경로의 실기 존재 여부와 내용은 이번에 읽지 않았다. 향후 판별에 필요한 값은 장치 식별자나 부팅 인수를 제외한 배치 판정과 범위 크기다.

보관된 FDT 파일용 판독기 `inspect-kept-fdt.py`도 준비했다. libfdt로 전체 구조와 길이를 검증하고 RAM 노드 형태·뱅크 수, 고정·동적 예약 수, initrd 크기와 단일 뱅크 포함 여부를 출력한다. 실행 주소나 부팅 인수 값은 출력에 포함되지 않는다. 순정 조합 6개, 메인라인 원본 1개, RAM·initrd가 채워진 두 합성 입력에서 예상값을 확인했다. 잘림·길이 초과·잘못된 헤더 대조 3개를 거부했다. 이 요약만으로 실제 적재 주소와 예약 충돌을 판정할 수는 없다.

## 순정 펌웨어의 Kernel 영역으로 다시 계산한 결과

IYC2 BL 아카이브에서 XBL을 꺼내 펌웨어 볼륨의 UI 이름과 섹션 종류로 `uefiplat.cfg`와 `QcomBds`를 식별했다. 설정 파일에는 256 MiB 크기의 `Kernel` 영역이 하나 있다. QcomBds는 이름으로 영역을 조회하고, 성공하면 시작값과 크기를 각각 8바이트 EFI 변수로 등록한다. LinuxLoader가 두 변수를 읽을 때 사용하는 이름·GUID와 일치했다. 두 조회가 모두 성공하는 ARM64 경로가 이번 계산의 전제다. 지난 부팅에서 그 경로를 선택했다는 실기 기록은 없다.

LinuxLoader의 적재 위치와 상단 FDT·ramdisk 공간을 계산하는 실제 ARM64 명령 구간을 분리해 QEMU에서 실행했다. 별도 호스트 계산과 결과를 대조했다. 원본 Magisk와 기존 PROCA 후보는 각 64개 입력 위치에서 두 런타임 크기 검사를 모두 통과했다. 경계 4건에서 허용 크기와 한 바이트 초과 결과가 예상대로 갈렸다. 이 경로에서 기존 후보의 런타임 크기는 부트로더가 인계를 거부할 조건에 해당하지 않는다.

| 같은 펌웨어 배치에서 수행한 대조 | 관측 |
| --- | --- |
| 기존 후보와 RAM·initrd를 채운 순정 DT | 첫 DT의 입력 위치 64개 중 63개가 FDT 검사 전 정렬 분기에서 멈췄다. 정렬된 위치는 순정 DT 6종 모두에서 삼성 커널 첫 명령에 도달했다. |
| 기존 후보의 FDT 검사 | 같은 정렬 위치에서 RAM 뱅크를 둘로 나눈 경우와 FDT 크기를 후보의 수용 한도보다 키운 경우를 각각 거부했다. |
| 메인라인 Linux 6.18의 별도 목적지 | 4.5 MiB 런타임 전체가 들어가고 기존 후보의 64개 입력 위치, 상단 FDT·ramdisk 공간, 확인한 고정 예약을 모두 피하는 동일한 2 MiB 정렬 목적지가 순정 DT 6종에서 나왔다. |
| 입출력 위치를 분리한 y2q FDT 인계 | 모델의 양 끝 입력 위치 2개를 사용했다. 두 경우 모두 커널 진입점에서 전체 복사본과 인수를 대조했다. 같은 커널이 전달된 y2q FDT 전체를 검증하고 `unflatten_device_tree()`에서 복귀했다. 가상 RAM 범위는 해당 펌웨어 영역을 바탕으로 시험에 넣었다. |

원본 Magisk ramdisk, 시험용 메인라인 initramfs, 합성 4 MiB·8 MiB ramdisk에서도 동일한 목적지가 남았다. 그 자리를 추가 예약으로 막으면 계산기가 다른 목적지를 골랐다. XBL 설정에는 `Kernel`과 일부 중첩되는 `SEC LOG` 매핑도 있다. 속성은 `NoHob / MMAP_IO`이며 기존 후보의 모델 입력 구간 64개 중 48개가 이 매핑과 겹친다. 선택한 새 목적지는 이를 제외했다. 해당 매핑의 실기 사용 시점이나 충돌은 관측되지 않았다.

Opus 5.5와 세 번째로 대조해 런타임 EFI 조회 성공 여부, 펌웨어가 추가하는 예약, FDT 크기 변화가 남는다는 점을 확인했다. 그 제안에 따라 같은 배치에서 기존 후보를 다시 실행하고 ramdisk와 예약을 바꿔 보았다. 다음 실기 판별에 필요한 것은 정상 부팅의 유효 RAM 뱅크가 목적지 런타임 전체를 포함하는지, 그때의 예약·initrd가 이를 침범하는지다. 과거 후보의 정지 분기는 그 후보 부팅에서 남긴 별도의 단계 증거가 필요하다. 이번 조사 중 휴대폰에 보낸 명령은 0건이다.

이 판별을 위해 보관된 FDT 파일을 받는 호스트 도구 `assess-kept-layout.py`를 만들었다. 지명된 목적지와 모델 입력 구간 각각에 대해 단일 사용 가능 뱅크의 포함 여부, 고정 예약·initrd 중첩만 출력한다. 원본 보드 트리 6종은 입력 부족, 채운 트리 6종은 고정 배치상 적합으로 분류했다. 별도 대조 6건에서 예약 끝의 한 바이트 중첩, initrd 중첩, 뱅크 분할, 한 바이트 부족, 비활성 RAM, FDT 헤더 예약을 구별했다. 출력은 물리 진입 판정이나 기기 작업 권한을 부여하지 않는다. `offline-discriminator.json`의 SHA-256은 `fe6c788448a4a0d2e16cc8a74cd7a5a84ccd527992b6d6ff4983c1f86b528839`다.

후속 실험 코드와 사례별 GDB 출력은 `workspace/private/analysis/s20plus-y2q-boot-map-20261123/`에 보관했다. `evidence.json`은 새 산술 대조·VM 실행과 이전 연구 결과의 해시를 연결한다. SHA-256은 `209eb2bc1ccbb4a6d62902b19767d602f17e89d01806153d1f93464c1bbe076d`다.

## 원본 Magisk 실기의 FDT 배치 관측

FDT 자체는 기기 안에 두고 집계값 43바이트만 받았다. 읽기 전후 Android 상태와 인벤토리도 일치했다. [관측 범위](../operations/targets/S20PLUS_G986N_TARGET_CONTRACT.md#s20-foreground-fdt-layout-d0)

같은 부팅에서 기존 pstore 준비도 프로필로 메타데이터를 확인했다. pstore는 마운트되어 있었고 고정 PMSG·console·dmesg 레코드는 사용할 수 없었다. `/proc/last_kmsg`는 읽기 접근 검사를 통과한 2,097,136바이트 파일이었다. 내용은 읽지 않았다. 후보별 표식이 Download 복구를 넘어 유지되는지는 여전히 확인할 항목이다.

## 쓰기 공간과 첫 명령의 호스트 대조

별도 2 MiB 정렬 FDT 출력 공간과 128 KiB 스택을 이번 실기에서 확인한 입력 구간 안에 배치하는 계산을 검증했다. 두 쓰기 영역은 메인라인 목적지, 64개 모델 입력 파일, 알려진 펌웨어 매핑, 상단 FDT·initrd 구간과 겹치지 않았다. 후보에 보드 DT와 로더 코드를 추가한 크기로도 다시 계산했다.

입력 구간 일부는 펌웨어의 `SEC LOG` 매핑과 겹치므로 첫 명령만 읽고 2 MiB 뒤의 코드로 분기하는 ARM64 시험편을 만들었다. 호스트 계산에서 64개 위치 모두 분기 후의 코드·보드 DT·커널 바이트가 해당 매핑 밖이었다. 실제 ARM64 QEMU에서 대표 위치 세 곳을 한 명령씩 실행해 분기 위치와 원래 소스 위치 계산, FDT 인수와 스택 포인터 보존을 확인했다. 첫 명령 자체는 여전히 모델 위치 48곳에서 매핑과 겹친다. 실기 첫 인출과 예정한 최종 FDT 조립은 이 시험에서 다루지 않았다. 휴대폰에는 시험편을 전송하지 않았다.

새 실행기 커밋은 `eb3ce5b625`다. 독립 검토는 지적 0건으로 통과했다. 새 집중 테스트 7건과 기존 pstore 회귀 테스트 18건이 통과했다. Magisk APK의 ARM64 BusyBox에 969,385바이트 보드 입력을 준 QEMU 판독은 최적화 후 30.18초에 끝났다. 12개 보드 입력에서도 같은 APK의 x86_64 BusyBox와 호스트 libfdt 결과가 일치했다. 기존 활성화 문서 회귀 묶음의 오류 5건과 실패 1건은 변경 전 계약과 새 계약에서 동일하게 재현됐다.

비공개 증거는 `workspace/private/analysis/s20plus-y2q-fdt-d0-20261123/close.json`에 연결했다. 그 파일의 SHA-256은 `3c6f4d31734a52535c5c0110e38bd8e9ec79ee6378913076e9351ecd60aabb1e`다. 실기 FDT 결과의 SHA-256은 `96da3ab8ab305a893e6d16617c668a2a879616fcaaa61fdcac3ef60b4e5f2f05`다. 건강 검사·FDT 판독·pstore 메타데이터 확인 모두 읽기 전용으로 종료했다.

## 입력 FDT로 조립한 메인라인 인계와 관측 한계

새 ARM64 로더는 부팅 때 받은 FDT에서 사용 가능한 RAM과 initrd, 고정 예약과 동적 풀을 읽고 y2q 메인라인 보드 트리에 합친다. 스택을 쓰기 전에 입력 파일·FDT·initrd와 커널 목적지, 출력 트리와 스택의 공간을 검사한다. 그 뒤 initrd 전체를 빌드 원본과 비교하고 Linux 6.18을 별도의 2 MiB 정렬 목적지에 복사한다. 전달된 트리에는 메인라인 기기와 phandle이 유지된다. 입력의 chosen 노드에서는 initrd 범위만 취한다. 시험 입력은 보관한 순정 트리에 모델 RAM 배치와 메인라인 initramfs 정보를 채워 만들었다. [로더 소스](../../workspace/public/src/mainline/s20plus_y2q_h0/mainline-handoff/entry.S) · [ARM64 부팅 규약](https://www.kernel.org/doc/html/v6.18/arch/arm64/booting.html)

최종 FDT에는 XBL 설정에서 읽은 `SEC LOG` 범위 15 MiB 전체를 반영했다. 적재 공간과의 교차 부분만 취한 2 MiB는 전체 예약 크기로 쓰기에 부족했다. libfdt가 새 자식을 앞에 넣으므로 출력에서 동적 풀의 처리 순서가 원본과 같도록 조립 순서를 바로잡았다. 독립 검토에서 발견한 풀 속성 중복도 조립 단계에서 거부한다. 로더는 복사한 커널의 캐시 라인을 PoC까지 정리하고 명령 캐시를 무효화한다. 실제 펌웨어의 진입 예외 레벨과 캐시·DMA 상태는 실기에서 확인할 사항이다.

실기 쪽에 남은 두 판별 조건이 있다.

- **펌웨어 적재와 첫 명령**. 64개 위치 중 48개에서 첫 명령과 `SEC LOG` 선언이 겹친다. 전체 입력 파일을 적재하면 이들 위치에서 32 KiB부터 최대 1.5 MiB까지 겹친다. 2 MiB를 건너뛴 뒤의 실행 코드는 모두 선언 밖이다. 분기 전 펌웨어의 파일 복사와 첫 인출은 이 코드가 통제할 수 없다. `NoHob` 표기만으로 그 시점의 메모리 사용 주체를 결정할 수 없다.
- **ADB 이전의 단계 증거**. 순정 트리 6종은 35 MiB 부트 화면 영역을 선언한다. 메인라인 템플릿의 framebuffer는 1080×2400, 줄당 4,320바이트로 선언돼 있지만 비활성이다. 확보한 순정 트리만으로는 해당 부팅에서 펌웨어가 실제 선택한 화면 버퍼·stride·형식을 특정할 수 없다. 기존 ADB Download PMSG 복귀 대조에서 표식은 0건이었다. Samsung의 별도 `/proc/last_kmsg` 경로는 첫 복귀에서 후보별 고유 표식을 회수하는 양성 대조가 남아 있다. [기존 PMSG 대조](S20PLUS_G986N_PMSG_DOWNLOAD_CALIBRATION_H0_2026-11-22.md)

Opus 5.5와 펌웨어의 DT 선택, MMU 이전 정렬 접근, 캐시 상태와 단계 관측을 대조했다. 이번에는 모델에서 관측한 커널의 FDT 처리와 풀 할당까지 증거가 있다. 실기 펌웨어의 후보 선택과 초도 진입, 실기 Linux 및 PID 1 도달은 미확인이다. 이번 구현·재현 과정에서 기기에 보낸 명령은 0건이다.

이번 H0 독립 검토에서 풀 속성 중복 거부를 수정하고 최종 Image의 해당 거부 지점을 재검증했다. 최종 Image SHA-256은 `6a56253f53ad8fde25dda124269c7c1148874c47dd4e357d83f6d5583e1cff34`다. 빌드 입력, 실패한 이전 ELF의 예외 기록, 최종 91개 사례의 GDB 출력과 별도 할당 추적은 `workspace/private/analysis/s20plus-y2q-mainline-compose-20261123/qualified.json`에 연결했다. 이 증거 목록의 SHA-256은 `43b88dc31a008ca598b3ba24f79d0f941ccc380928752dbed4b23a6fca348d64`다.

## Samsung 로그 링의 위치와 원복 시 읽는 내용

IYC2 정상 LinuxLoader 모듈에서 Samsung의 `sec_log` 부팅 인수를 만드는 ARM64 명령과 실제 포맷 함수를 실행했다. 출력한 크기는 2 MiB였다. 이 링은 XBL의 15 MiB `SEC LOG` 선언과 1 MiB만 겹친다. 순정 보드 트리 6종 모두에서 링 전체가 Samsung 디버그 예약 안에 들어간다. 성공한 EFI 영역 조회를 전제로 새 메인라인 Image·기존 PROCA Image·원복용 Magisk Image의 적재 위치를 각각 64개씩 대조했다. 세 경우 모두 파일 복사, 선언한 커널 런타임, 상단 FDT·ramdisk 공간과 2 MiB 로그 링 사이의 중첩은 0건이었다. 앞서 관측한 48개 첫 명령 위치와 넓은 XBL 선언 사이의 중첩은 그대로다.

복구된 실기에서 독립 검토를 마친 D0 프로필이 두 소스를 읽었다. 커널의 `/proc/cmdline`과 FDT의 `/chosen/bootargs` 양쪽에서 크기와 시작 주소가 펌웨어의 두 숫자와 일치했다. 기기·포트·부팅 ID 해시는 직전 PROCA 원복의 최종 건강 기록과 일치했다. 루트 명령은 분류값 12바이트를 반환했고 stderr는 비어 있었다. 이 관측에서는 로그 본문을 읽지 않았다. D0 커밋은 `3afb81c443`이다. [관측 범위](../operations/targets/S20PLUS_G986N_TARGET_CONTRACT.md#s20-foreground-samsung-log-argument-d0) · [chosen 노드 규약](https://devicetree-specification.readthedocs.io/en/stable/devicenodes.html#chosen-node)

Samsung 배포 소스의 헤더와 초기화·기록·직전 로그 복사 함수 네 개를 원본 아카이브와 대조한 뒤 ARM64에서 실행했다. RAM과 I/O 복사는 호스트 메모리로 모델링했다. 정상 표식과 링 끝을 가로지른 표식은 모두 다음 스냅샷에서 복원됐다. 원래 헤더의 magic이 바뀐 경우, 한 바퀴가 넘도록 새 기록이 쌓인 경우, 기록기 시작 전인 경우, RAM 초기화, 표식 미기록 대조에서는 표식이 없었다. 각 스냅샷 생성 뒤 새로 쓴 표식도 이미 복사된 스냅샷에는 없었다. 실제 Download·펌웨어 초기화·원복 경로에서 링 헤더와 데이터가 보존되는지는 이 모델로 측정할 수 없다.

Opus 5.5와 대조한 결과, 다음 실기의 양성 증거는 해당 실행에서만 생성 가능한 표식이어야 한다. 이전 원본 Android의 정상 로그가 보존된 것만으로도 복구 후 파일은 채워질 수 있다. 기존 PROCA 후보의 삼성 커널은 원본과 같고, 로더는 chosen 속성을 추가하나 그 값을 커널 로그에 출력하지 않는다. 과거 정상 배너로 해당 후보의 실행 여부를 가릴 수 없는 이유다. [순정 PMSG 복귀 대조](S20PLUS_G986N_PMSG_DOWNLOAD_CALIBRATION_H0_2026-11-22.md)

## 펌웨어 정리 코드의 예외 마스크와 Android 컨테이너 대조

실제 LinuxLoader의 부팅 서비스 종료 성공 경로는 CPU 정리 함수를 호출한 뒤 별도 함수와 최종 분기 경로를 거친다. ARM64 QEMU에서 정확한 정리 함수를 EL1·EL2에서 실행했다. 각 경우 시험용 항등 매핑과 켜진 MMU·데이터 캐시·명령 캐시로 시작했다. 복귀 때 세 기능은 꺼졌고 SError·IRQ·FIQ가 마스크됐다. 디버그 예외 마스크 `PSTATE.D`는 처음 값을 유지했다. QEMU 시험편은 여기서 곧바로 로더로 분기한다. 정리 뒤에 실행되는 펌웨어 경로와 실기 인계 순간의 D 값은 미측정이다.

D가 0이면 기존 로더가 FDT 접근 전에 멈추는 현상을 두 EL에서 재현했다. 수정한 로더는 기존 SError·IRQ·FIQ 마스크를 확인한 뒤 D를 직접 세운다. 같은 펌웨어 대조 4건 모두 FDT 검사 진입점에서 네 마스크가 설정돼 있었다. 별도 VM 95건에서 새 raw Image는 74건의 전체 커널 복사·인수·FDT·트리 전개를 검증했고, 나머지 21건은 정해진 거부 지점에서 멈췄다. SError·IRQ·FIQ를 각각 풀어 둔 입력은 여전히 거부됐다. 과거 실기에서 같은 비트 때문에 정지했는지는 특정할 수 없다. [Linux ARM64 진입 규약](https://docs.kernel.org/6.18/arch/arm64/booting.html)

새 raw Image와 이전부터 사용한 299,446바이트 initramfs를 실제 Android v2 boot 형식과 단일 `boot.img.lz4` 멤버의 `AP.tar.md5`에 넣었다. 기기용 보드 선택에 쓰는 순정 DTB는 그대로였다. AP를 다시 열어 풀었을 때 커널·initramfs·DTB 전체와 64 MiB 부트 크기가 일치했다. 원복 AP도 독립적으로 풀어 정확한 Magisk 원본과 대조했다. Android AVB 도구는 순정 배포본을 검증했고, 정상 부팅한 원본 Magisk와 새 운반 대조 이미지 둘 다 기존 서명 메타데이터의 boot 해시와 불일치한다고 보고했다. 새 이미지의 펌웨어 수용과 실기 부팅은 미검증이다. 이 AP에는 후보 전용 Samsung 로그 기록기가 없고, 실기 전송은 0건이다.

비공개 재현 자료는 `workspace/private/analysis/s20plus-y2q-seclog-20261123/close.json`에 연결했다. 증거 목록 SHA-256은 `18665b78cbd55a65d129cc5653bff74b27d85222a44e6603b12dc7c7645407b5`다. 수정한 raw Image SHA-256은 `cfe380dd198b4e665b02d5e264a162617653345e1c474841ab1492f4223f01cf`다.

독립 검토는 로그 인수 판독기와 CPU 진입 변경 각각 지적 0건으로 종료했다. CPU 검토는 기존·수정본의 정리 함수 실행 8건과 수정본 95건의 GDB 실행 파일·로그를 대조했다. D0의 실기 결과는 양쪽 인수의 일치까지이며, 다음 연구 단위는 후보 안에서만 만들어지는 단계 표식과 첫 원복에서 그 표식을 읽는 경로다.

## 순정 펌웨어의 마지막 호출에서 후보 커널의 두 표식까지

앞선 CPU 대조에서는 펌웨어 정리 함수가 복귀한 직후 시험편이 후보를 직접 호출했다. 이번에는 IYC2 LinuxLoader의 부팅 서비스 종료 호출 직후부터 원래 명령을 실행했다. QEMU가 제공한 입력은 종료 상태, 펌웨어 스택의 기기 트리·배치 주소, 시간 측정용 메모리와 펌웨어 변수 응답이다. 원래 CPU 정리 함수, 마지막 시각을 기록하는 함수, 간접 분기, 후보 로더와 Linux 6.18 코드는 연속해서 실행했다.

- 정상 경로 다섯 건에서 펌웨어는 후보 진입 시 `x0`에 입력 FDT, `x1`에 스택에서 읽은 기준 주소, `x2`에 후보 진입 주소와 그 기준 주소의 차, `x3`에 0을 전달했다. 후보가 메인라인으로 분기할 때는 `x0`가 조립된 y2q FDT를 가리켰고 `x1`부터 `x3`까지 모두 0이었다. 복사된 Linux Image 전체와 두 단계에서 회수한 링 전체가 이전 검증의 바이트와 일치했다. [후보 진입 코드](../../workspace/public/src/mainline/s20plus_y2q_h0/mainline-handoff/entry.S) · [Linux 6.18 ARM64 인계 규약](https://docs.kernel.org/6.18/arch/arm64/booting.html)
- EL1·EL2 각각에서 초기 디버그 예외 마스크를 0 또는 1로 주었다. 펌웨어의 마지막 시각 기록을 지나도 입력 D 값이 유지됐고, 후보 진입에서 시스템 제어 레지스터의 MMU·데이터 캐시·명령 캐시 활성 비트는 모두 0이었다. 후보가 메인라인에 넘길 때 네 예외 마스크가 모두 설정됐다. 시간 측정 주소가 이미 채워진 경우, 두 번의 변수 조회에 모형이 응답한 경우, 카운터가 0인 경우를 포함한다.
- 부팅 서비스 종료가 실패했다는 상태를 준 대조는 정리 함수 전에 오류 분기로 갔다. 다른 이미지 형식 선택값을 준 대조는 다른 인수 배치의 호출 지점에 도달했다. 별도로 실제 후보·원본 AP의 커널 헤더를 모델 양 끝 위치에서 순정 헤더 비교와 공간 검사에 넣어 네 건 모두 ARM64 직접 호출에 해당하는 선택값과 크기 통과를 확인했다. 매직과 크기를 각각 바꾼 합성 입력은 예상 분기로 갈라졌다.

Opus 5.5와 확인한 결론은 이 조건에서 펌웨어가 남긴 추가 인수가 메인라인 진입을 막지 않는다는 것이다. 실물의 부팅 서비스 종료 결과, 실제 배치와 예외 레벨, 시간 측정 주소의 유효성 및 첫 명령 인출은 이 호스트 실행으로 측정할 수 없다. 실험의 기기 명령은 0건이다. 비공개 증거 목록은 `workspace/private/analysis/s20plus-y2q-firmware-final-call-20261123/close.json`이며 SHA-256은 `3a1f653fb1759840c2eb59365845e398677fa0352133164a6a6003ff645d2ca9`다.
