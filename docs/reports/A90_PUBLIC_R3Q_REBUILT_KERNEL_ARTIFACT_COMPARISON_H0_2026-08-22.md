# A90 public r3q rebuilt-kernel artifact comparison — H0

Date: 2026-08-22
Target: Samsung Galaxy A90 5G (`r3q`) only
Tier: H0 host-only public-artifact analysis
Device contact: none
Authority: no D0, D1, F1, candidate, rollback, reboot, or live authority
Disposition: exact public artifacts plus release history strongly contradict a
universal rebuilt-kernel ban; exact public device boot and
stock-security-equivalent boot-only acceptance remain unproved

## Result

Two independently published A90 `r3q` ROM archives contain source-built A90
kernels rather than the Samsung stock kernel:

1. Evolution X 7.9.9 contains
   `Linux 4.14.190-Grass,SD855-Perf+`, the same upstream base version as the
   failed H34 reconstruction.
2. `/e/OS U` 2.4 contains `Linux 4.14.334-ShareMyPerf`, a later build from the
   same public r3q kernel lineage.

Both boot artifacts select `CONFIG_SEC_R3Q_PROJECT=y` and
`CONFIG_MACH_R3Q_KOR_SINGLE=y`. Both carry only the two SM8150 hardware FDTs,
with no RTIC FDT, no `MP_DATA`, and no in-Image `RTIC MP` marker. Their
extracted configurations disable or omit Samsung RKP/CFP. They retain strict
Linux external-module signature enforcement and each contains the generic
build-time autogenerated kernel-key subject marker.

The release threads present these packages as installable A90 ROMs. That is
credible public boot precedent, not a retained same-run boot log. This report
therefore keeps the exact public device boot result **unproved**.

The extracted bytes directly defeat either artifact-side requirement below:

- an A90 boot image must contain Samsung's stock kernel bytes; or
- an A90 boot image must contain an RTIC measurement FDT merely to be a
  distributable r3q kernel artifact.

Together with the release history they strongly contradict, but do not by
themselves forensically disprove, a universal bootloader rejection claim.

It is **not** a stock boot-only acceptance proof. Both ROM installers replace
`system`, `vendor`, `boot`, `dtbo`, and `vbmeta` together. Both matching
top-level `vbmeta.img` files have flags `3`, meaning AVB hashtree and
verification disabling are both requested. Both kernel command lines also set
`androidboot.selinux=permissive`. The public examples therefore change the
platform and trust environment around the kernel, while the A90 project permits
only a `boot` payload and keeps the existing stock platform.

The strongest corrected conclusion is:

> H34 is not evidence that A90 universally rejects rebuilt kernels. H34 is a
> bad hybrid: an MPGen-free rebuilt Image coupled to the stock RTIC FDT that
> measures different stock bytes. Public A90 ROMs avoid that hybrid by omitting
> RTIC metadata and disabling the associated Samsung hardening configuration,
> but they do so inside a broader full-ROM transition that is not the project's
> boot-only lane.

H34 boot-loop causality remains unproved. The public artifacts materially
strengthen stale RTIC metadata as the leading H34-specific defect, but do not
prove whether an RTIC-free Image is accepted with the project's unchanged
stock `vbmeta`, `dtbo`, `vendor`, and trusted firmware.

The exact H34 differential and retained live disposition remain in
`A90_H34_RTIC_MP_STALE_DTB_HOST_CAUSAL_ANALYSIS_H0_2026-08-22.md`.

## Exact r3q targeting

Both updater scripts reject devices other than `r3q` or `r3qxx` and name the
same Samsung base fingerprint:

`samsung/r3qks/r3q:11/RP1A.200720.012/A908NKSU5EWF1:user/release-keys`

Both then unconditionally update:

1. `system`;
2. `vendor`;
3. `boot`;
4. `dtbo`; and
5. `vbmeta`.

This confirms that these are A90 artifacts, not merely generic SM8150 kernels.
It also establishes why they cannot be treated as a direct control for the
current project: four of their five write targets are outside the permanent A90
boot-only boundary.

## Kernel and DTB comparison

MagiskBoot v30.7 unpacked each exact boot artifact. The H34 values below come
from the retained exact H34 artifact, not from a historical summary.

| Surface | H34 failed boot-only artifact | Evolution X 2023 | `/e/OS U` 2024 |
|---|---:|---:|---:|
| kernel banner | `4.14.190` | `4.14.190-Grass,SD855-Perf+` | `4.14.334-ShareMyPerf` |
| compiler | Snapdragon LLVM 10.0.7 | Android Clang 14.0.6 | Android Clang 17.0.2 |
| boot kernel format | raw Samsung `UNCOMPRESSED_IMG` | gzip | gzip |
| raw Image bytes | 48,830,480 | 48,150,544 | 44,677,136 |
| hardware FDT sizes | 497,331 + 499,609 | 496,809 + 499,699 | 496,639 + 499,529 |
| RTIC FDT size/count | 173 / 1 | 0 / 0 | 0 / 0 |
| `RTIC MP` marker | absent from rebuilt Image | absent | absent |
| stock RTIC binding | present and stale | absent | absent |

The first two public FDT roots retain the exact SM8150 selectors used by the
stock/H34 hardware FDTs:

- `qcom,sm8150`, `SM8150 V1`, `qcom,msm-id = <0x153 0x10000>`; and
- `qcom,sm8150`, `SM8150 V2`, `qcom,msm-id = <0x153 0x20000>`.

Their complete bytes are not stock copies: their sizes and hashes differ from
H34's first two FDTs. The public kernels and hardware FDTs were rebuilt as a
set, while H34 combined a rebuilt Image with the complete three-object stock
tail.

The Evolution X artifact is the closest available comparison because it uses
the same Linux 4.14.190 base as H34. Its two-FDT tail ends exactly at byte
996,508 and contains no third object. This is a structural absence, not a
failed string search.

## AVB and surrounding-platform distinction

`avbtool info_image` reports an unsigned per-partition AVB footer
(`Algorithm: NONE`) on each public 64 MiB boot image. More importantly, each
separately shipped top-level `vbmeta.img` is RSA-signed but has `Flags: 3`.
The [AOSP libavb header](https://android.googlesource.com/platform/external/avb/+/master/libavb/avb_vbmeta_image.h)
defines bit 0 as `AVB_VBMETA_IMAGE_FLAGS_HASHTREE_DISABLED` and bit 1 as
`AVB_VBMETA_IMAGE_FLAGS_VERIFICATION_DISABLED`.

The installer writes that matching `vbmeta.img` after writing its matching
boot and DTBO. Consequently, the public evidence does not answer either exact
boot-only question:

- Will the unchanged A90 stock boot chain accept a rebuilt Image with RTIC
  absent?
- Will the unchanged stock vendor/userspace remain compatible with that
  kernel's disabled RKP/CFP/DEFEX/FIVE and new module key?

Both remain **unproved**. No device inference fills that gap.

## Consequence for H34 and the next host unit

The previous report's rejection rule remains valid but must be stated narrowly:

- reject every rebuilt Image that carries a stale RTIC FDT; and
- do not infer that every MPGen-free Image is intrinsically unbootable.

There are now two coherent architectural controls:

1. **Stock-security-equivalent control:** reproduce MPGen and append a new RTIC
   FDT bound to the exact rebuilt Image, retaining the current boot-only lane.
2. **Community-compatible control:** omit RTIC and disable the related Samsung
   hardening as the public r3q kernels do.

Control 2 is useful H0 evidence but is not currently a live candidate. Its
public precedent depends on broad platform changes outside the repository's
permanent boot-only boundary and lowers kernel hardening. Choosing it would
require a separate architecture/security decision; it cannot be smuggled into
an ordinary kernel canary.

The cheapest next discriminator is still host-only: reconstruct the public
4.14.190 configuration and boot payload sufficiently to explain every relevant
delta, while independently completing the MPGen-consistent stock-security
build. Only after those two byte closures exist should the project decide which
single boot-only canary has the higher information value. Neither preparation
creates F1 authority.

Follow-up: `A90_PUBLIC_MPGEN27_SELF_CONSISTENT_RTIC_REBUILD_H0_2026-08-22.md`
completed the structural MPGen control and tested the closest public 4.14.190
source snapshots. RTIC byte consistency now passes, but the public test catalog
differs from the stock production MP and exact public-ROM source remains
unproved; no candidate or live authority was created.
