# S22+ 메인라인 SCM 첫 연결의 USB 판독 · H0

ML053 기반 ARM64 Image `5a0b12b0e690…`를 QEMU에서 부팅해 지정된 SCM 플랫폼 장치의 미연결 상태를 Debian SysV init의 자식 관측기에서 USB로 회수했다. USB는 게스트의 가상 호스트 컨트롤러와 CDC-NCM 장치를 연결했다. 진행 중·성공·실패의 시점을 제어한 대조에는 별도의 시험 드라이버를 썼다. S22+ 실기의 메인라인 SCM 연결은 미측정이다.

## 부팅별 결과

| 장치와 커널에서 확인한 조건 | USB 응답 |
| --- | --- |
| 실제 SCM 호환 OF 노드, 연결할 인터커넥트 공급자 부재 | `unbound`, 36,248바이트. 실제 SCM probe 진입 여부는 측정하지 않았다. |
| 시험 드라이버의 첫 probe를 대기 상태로 유지. 응답 전과 후에 모두 probe 안에 있었음 | `indeterminate`, 35,772바이트 |
| 시험 드라이버의 첫 probe 성공. 응답 전에 커널의 연결 완료 통지 확인 | `bound`, 35,772바이트 |
| 시험 드라이버의 첫 probe 거부. 응답 전에 커널의 연결 실패 통지 확인 | `unbound`, 35,772바이트 |
| SCM 관측 요청의 인증 태그 한 비트를 바꿈 | 응답 0바이트. 관측기가 `EACCES`로 정지 |

첫 진행 중 대조에서는 USB 모듈을 준비하는 동안 시험 probe의 대기 시간이 만료됐다. 이 실행의 원시 응답은 보존하고 진행 중 결과에서 제외했다. USB 모듈과 인터페이스를 먼저 준비한 뒤 같은 제한 시간으로 다시 부팅했다. 최종 실행에서는 USB 응답이 끝난 뒤에도 시험 probe가 대기 중임을 확인하고 나서 해제했다.

## 판독과 검증

[판독 함수](../../workspace/public/src/mainline/s22plus_canary_h0/scm-usb-observe.h)는 지정된 플랫폼 장치의 OF 노드, 호환 문자열, 양방향 드라이버 링크, 공급자 대기 속성을 두 번 확인한다. 이번 커널의 새 장치가 **처음 연결될 때**는 probe가 반환되기 전에도 드라이버 링크가 생긴다. 이때 공급자 대기 속성까지 남아 있으면 판정 불가다. 일단 연결에 성공한 뒤의 unbind/rebind, 중간 전이의 이력, SCM 펌웨어 요청에 대한 반환값은 이 판독으로 알 수 없다. 이 판독 함수 자체는 SCM 호출을 보내지 않는다.

[생성기](../../workspace/public/src/mainline/s22plus_canary_h0/scm_usb_h0.py)는 모듈 없는 ML022 RAM 아카이브에 넣을 H0 관측기와 판독기 소스를 만든다. 원본 아카이브에서 SysV init, 기본 inittab과 나머지 멤버는 보존하고 관측기만 교체했다. VM 시험에서는 별도 부가 아카이브에 USB 호스트 도구·모듈과 시험용 init 작업을 넣었다. 서로 다른 네트워크 네임스페이스 사이의 CDC-NCM을 거친 응답을 호스트에 원본 그대로 저장한 뒤 판독했다. 가상 직렬 포트는 요청과 회수한 바이트를 VM 밖 시험기로 전달했다.

356바이트 응답 본문의 마지막 4바이트에 상태를 넣고 본문 전체를 HMAC으로 인증한다. 요청별 nonce, 후보 ID, 부팅 ID, PID 1·관측기·기본 inittab의 해시와 라이브 DT 해시가 같은 본문에 들어간다. 실제 SCM 노드와 시험 장치는 별도 프로토콜 식별자·인증 도메인·키·후보 ID를 쓴다. VM 판독기는 전송된 DT의 해시 및 VM 호환 문자열을 검사한다. 부팅에 공급한 Image와 입력 DT의 정확한 파일 해시는 각 실행기의 기록에서 확인했다.

회수한 원본으로 상태·태그·DT 변경, 다른 키·후보·nonce, 올바른 태그를 가진 미정의 상태값, 다른 프로토콜과 실기 판독 모드를 포함한 11개 거부 대조를 확인했다. 두 관측기에서 프로파일을 잘못 선택한 빌드 6건도 컴파일 단계에서 거부됐다. 이 검사를 추가해 다시 링크한 ARM64 정적 실행 파일 두 개는 각각 VM이 실행한 파일과 바이트가 같았다. [회귀 테스트](../../tests/test_s22plus_scm_usb_h0.py)와 기존 canary 테스트 12건을 통과했다.

원시 응답, 게스트 로그, 실행별 입력과 빌드 출처는 `workspace/private/analysis/s22plus-scm-wire-lifecycle.slA4DOx6/`에 있다. 최종 5건의 기록과 원본 재검증 결과는 `recheck-zqgnc8p_/qualification.json`에 묶었다. SHA-256은 `10b18199135e43dc8d904029b0c3a334391f7e5ff773063d02ff034746c2e037`이다.

## 입회 부팅에 적용할 범위

이번 USB 판독은 Debian 서비스가 요청을 받았을 때의 상태를 제공한다. 별도로 개발한 보존 RAM 표식은 다른 Image의 더 이른 부팅 시점을 기록한다. 두 관측에는 한 부팅 시도를 연결하는 공통 식별자가 없으며 결과를 합칠 수 없다. 1회 SCM 연결 관측의 첫 실기 후보로는 기준 Image를 유지하고 USB로 판독하는 구성을 선택했다. USB 응답이 없으면 SCM 결과는 미확인으로 남는다. 정확한 실기용 관측기·판독기·부트 산출물, 커널 SCM 초기화 효과 및 입회 Download 복구에 대한 검토와 실행 자격 확인이 남아 있다. [실기 목표](../GOAL_S22PLUS_MODEM.md#다음-실기-목표--s22-메인라인-scm-연결-1회-입회-관측)
