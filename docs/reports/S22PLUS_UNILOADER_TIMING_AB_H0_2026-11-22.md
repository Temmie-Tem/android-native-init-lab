# S22+ FYG8 uniLoader LOGM 부팅 시간 실기 비교

2026-11-22에 LOGM 끔과 켬으로 같은 FYG8 벤더 커널, ABL DTB, initrd를 부팅하는 두 후보를 만들었다. 두 후보의 ARM64 실행 바이트와 FDT 준비 경로가 일치한다. 후보 식별자와 보고서 데이터가 각각 다르고 LOGM 호출 여부는 4바이트 플래그로 바뀐다.

| 기록 | 구간 |
| --- | --- |
| uniLoader ARM 가상 카운터 | 진입 가드 통과, FDT 준비, 커널·최종 FDT 복사, LOGM 호출 또는 건너뛰기, 보고서 확정 직전 |
| 호스트 BOOTTIME | 후보 전송 시작부터 Android 부팅 완료를 확인한 뒤 첫 상태 검증을 시작할 때까지 |

호스트 기록에는 전송과 ABL 실행이 포함된다. 두 시계를 직접 빼지 않는다. LOGM 켬에서 정상 기록과 안정적인 읽기 확인이 있어야 LOGM 쓰기 비용을 비교한다. 카운터 보고서가 미확정 상태이거나 Android 부팅이 실패하면 비교에 쓸 표본이 없다. 부팅 실패 원인은 별도 증거가 필요하다.

실제 ARM64 후보로 QEMU EL1·EL2에서 타이밍 보고서와 인계를 검증했고 EL3에서는 진입 가드가 거부했다. 두 후보의 초기 카운터 명령과 정규화한 실행 바이트를 대조했다. LOGM 켬 바이너리의 기존 쓰기 검증 44개를 다시 실행해 헤더 및 기록 위치 검증, 중간 중단, 읽기 불일치 경로를 확인했다. 두 후보의 AP와 원복 AP를 실제로 풀어 대조했고 상대 후보 AP를 바꾼 준비 기록을 거부하는 것도 확인했다.

실기 순서는 LOGM 끔, 원래 Android 복귀 확인, LOGM 켬이다. 각 후보는 별도 입회 승인을 받는다. 준비 단계에서 후보 전송은 없었다. 실기의 ABL 인계 시점에 ARM 카운터를 읽을 수 있는지는 첫 실행에서 확인한다. [실행 및 복귀 조건](../operations/S22PLUS_LOADER_ANDROID_V1.md#optional-paired-boot-timing-control)

## LOGM 끔 실기 결과

2026-11-22 첫 입회 실행에서 실기의 19.2 MHz ARM 가상 카운터를 읽었다. 같은 Android 부팅에서 타이밍 보고서와 미변경 LOGM 보고서를 읽고 원본 캡처에서 다시 검증했다.

| 구간 | LOGM 끔 |
| --- | ---: |
| 진입 가드 통과 → FDT 준비 완료 | 8.040511초 |
| 커널·최종 FDT 복사 | 1.176835초 |
| LOGM 분기와 건너뛰기 | 1.927µs |
| 보고서 준비 | 1.894843ms |
| 진입 가드 통과 → 보고서 확정 직전 | 9.219243초 |
| 호스트에서 후보 전송 시작 → Android 준비 뒤 첫 상태 검증 시작 | 49.122208초 |

로더에서 측정한 시간의 약 87%가 FDT 준비 완료 전 구간에 있었다. 이 구간의 세부 원인은 추가 계측이 필요하다. LOGM 기록 비용을 구하려면 LOGM 켬에서 기록 성공을 확인한 뒤 두 로더 카운터 값을 비교해야 한다.

후보와 원복 이미지를 각각 한 번 전송했다. 원복 직후 첫 상태 판독이 오류로 끝나 같은 실행기가 원본 전송 증거를 확인하고 상태 판독만 재개했다. 원래 Android로 정상 복귀해 `ANDROID_CLOSED_HEALTHY`로 종료했다. 비공개 실행 폴더 `s22plus-loader-timing-off-v2-h0-20261122-1/task-1`에 구조화된 결과, 타임라인, 원본 캡처 인덱스가 있다.

## LOGM 켬 실기 결과

LOGM 끔 실험이 정상 복귀한 뒤 같은 커널·DTB를 쓰는 켬 후보를 한 번 전송했다. ADB가 잠시 연결됐고 첫 판독에서 `bootanim=running`과 비어 있는 `sys.boot_completed`를 읽었다. 다음 판독은 `error: closed`와 종료 코드 1을 반환했다. 실행기는 후보 전송 시작 후 114.274초에 멈췄다. 240초 관측 만료 전에 일어난 판독 오류였다.

Android 준비 확인과 타이밍·LOGM 보고서 판독까지 도달하지 못했다. LOGM 기록 성공 여부와 켬·끔 시간 차이는 미확인이다. 끔 실행의 9.22초 가운데 8.04초가 로더 재배치, 초기화, FDT 준비를 포함하는 구간에 있었다는 결과는 유효하다. ADB 연결 종료의 원인은 원본 캡처로 확정할 수 없다.

운영자가 물리 Download 모드에 들어간 뒤 기존 실행기가 원래 Android 이미지를 한 번 전송했다. 첫 복구 상태 판독은 ADB 오류로 끝났다. 같은 실행기가 원본 전송 증거를 확인하고 상태 판독만 재개해, 원래 FYG8 Android의 정상 부팅과 파티션 해시 일치를 확인했다. 종료 상태는 `ANDROID_CLOSED_HEALTHY`이고 LOGM 켬 실험 결과는 `NO_PROOF`다. 구조화된 종료 결과, 타임라인과 원본 캡처 인덱스는 비공개 실행 폴더 `s22plus-loader-timing-on-v2-h0-20261122-1/task-1`에 보존했다.

## ADB 종료 원인 조사와 다음 비교

같은 호스트 부팅에서 후보 전송 시작 기록, ADB 원본 캡처, 해당 USB 포트의 커널 저널을 대조했다. 아래 시간은 후보 전송 시작 기록의 파일 시각을 기준으로 한 근사값이다.

| 호스트에서 본 사건 | LOGM 끔 | LOGM 켬 |
| --- | ---: | ---: |
| 첫 Android USB 식별 | 46.203초 | 112.333초 |
| 초기 USB 연결 끊김 | 47.094초 | 114.264초 |
| 같은 포트에 Android USB 재등장 | 47.927초 | 115.028초 |
| 부팅 준비 속성 판독 | 46.768초와 49.097초 성공 | 113.625초 성공, 114.271초 `error: closed` |

두 실행 모두 Android USB가 한 번 끊겼다가 다시 나타났다. 끔에서는 판독 사이에 재연결이 끝났다. 켬에서는 재연결 직전의 연결 종료와 준비 상태 명령 실패가 겹쳤다. 기존 수집기는 이 stderr를 처리하는 예외가 없어, 첫 건강 판독과 두 FDT 보고서 판독에 들어가기 전에 중지했다. 이 상관관계는 관측 중단을 설명한다. 켬에서 첫 Android USB가 66.13초 늦게 나타난 차이는 해당 ADB 명령과 보고서 수집보다 먼저 발생했다. 각 조건의 한 번씩의 관측으로 그 차이를 LOGM 쓰기에 귀속할 수 없다.

새 비교에서는 같은 FYG8 커널·DTB와 같은 호스트 수집기를 쓰는 새 끔·켬 후보를 각각 실행한다. 두 후보 모두 준비 단계의 정확한 `error: closed` 실패를 보존하고, 기존 240초 안에서 다음 USB 목록부터 같은 기기를 다시 선택한다. 부팅 완료 확인, 같은 부팅·USB 세대의 전체 상태 검증, 두 FDT 보고서 판독, 원래 Android 복귀는 기존 조건을 유지한다. 각 조건에서 첫 USB 등장까지의 시간과 로더 내부 시간을 각각 기록한다. 성공한 켬 보고서에서 LOGM 기록과 안정적인 읽기 확인을 얻으면 카운터의 LOGM 구간 차이를 계산한다. 첫 USB 지연만 재현되면 해당 시간은 로더 카운터가 덮지 않는 구간까지 포함하므로, ABL·로더 인계 이후·USB 준비 중 어느 지점인지는 이 비교만으로 확정할 수 없다.

새 켬·끔 이미지는 이전과 같은 커널·DTB 및 원복 이미지를 유지하며, 각 후보의 식별자와 AP는 새로 만들었다. 두 이미지 모두 QEMU EL1·EL2 인계와 EL3 거부를 확인했고 켬 바이너리의 LOGM 쓰기 검증 44개가 통과했다. 독립 검토를 거친 수집기를 적용했다. 직전 실험의 정상 원복 기록에 연결한 새 끔 실행 요청을 호스트에서 준비했다. 다음 실기에서는 끔이 정상 복귀한 뒤 같은 쌍의 켬을 별도로 승인한다.
