# S22+ FYG1용 Debian 원격 저장소·TFTP 동시 서비스 시험

ML053 기반 ARM64 VM의 한 부팅에서 SysV PID 1이 Debian `rmtfs`와 `tqftpserv`를 시작했다. 한 합성 원격 노드가 같은 GLINK `IPCRTR` 채널로 두 서비스의 광고를 받고 각각 데이터를 읽었다. 정상 시험에서는 원격 저장소 파일 세 개의 핸들을 연 채 TFTP로 FYG1 배포 파일 전체를 받은 다음, 기존 핸들 세 개를 모두 정상적으로 닫았다.

## 펌웨어 디렉터리의 게시 순서

기존 초기 램디스크의 `/lib`는 `usr/lib`를 가리킨다. 이전 TFTP 단독 시험처럼 부팅 전에 `/lib/firmware/modem_pr`를 만들면 28개 펌웨어를 받는 수신기의 목적지가 이미 생긴다. 수신기는 목적지 경로가 존재하지 않을 때만 시작하며, 검증한 임시 디렉터리를 그 자리에 게시한다.

별도 RAM 아카이브에 583,456바이트 TFTP 파일을 `/usr/lib/fyg1-tftp/modem_pr/so/847_f_0.mbn`으로 넣었다. SysV가 기존 수신기의 종료를 기다리고 두 서비스 시작 프로그램을 한 번씩 실행한다. TFTP 시작 프로그램은 게시된 RAM 디렉터리와 `modem.mdt`를 확인한 뒤 그 안에 고정된 `modem_pr` 링크를 만들고 Debian 배포 서버를 실행한다. 게시 성공은 수신기가 검사한 28개 파일에 적용된다. 별도로 담은 TFTP 파일은 아카이브를 만들 때와 상대가 받은 뒤에 각각 CP 원본과 SHA-256을 대조했다. [Debian SysV의 wait와 once 동작](https://manpages.debian.org/trixie/sysvinit-core/inittab.5.en.html)

기존 펌웨어 수신기·인증 형식·송신 파일 목록과 `rmtfs` 시작 프로그램의 바이트를 보존했다. TFTP 단독 시험의 libc·로더는 기존 아카이브와 해시가 달랐다. 기존 libc·로더·QRTR 라이브러리를 사용해 배포 서버의 라이브러리 연결을 검사한 뒤 실제 VM에서 실행했다. 추가한 배포 실행 파일은 `tqftpserv` 1.1-4이고, 추가한 배포 라이브러리는 `libzstd.so.1`이다. [단독 TFTP 시험](S22PLUS_FYG1_DEBIAN_TFTP_H0_2026-11-22.md) · [기존 SysV 저장소 시험](S22PLUS_FYG1_SYSV_RMTFS_H0_2026-11-22.md)

## 같은 아카이브로 부팅한 세 조건

| 조건 | 28개 펌웨어 게시 | 원격 저장소, 서비스 14 | TFTP, 서비스 4096 |
| --- | --- | --- | --- |
| 정상 입력과 준비된 저장소 메모리 | 성공, 호스트 완료 HMAC 일치 | QMI 응답 11건, 순정 순서의 읽기 4건 | 전체 파일 76블록 수신, 해시 일치 |
| 저장소 메모리 드라이버 연결 지연 | 성공, 호스트 완료 HMAC 일치 | 백엔드 확인 단계에서 정지, 서비스 조회 결과 0건 | 같은 파일 76블록 수신, 해시 일치 |
| 마지막 송신 파일의 한 바이트 변형 | 게시 0건, 완료 HMAC 없음 | 펌웨어 확인 단계에서 정지, 서비스 조회 결과 0건 | 같은 단계에서 정지, 서비스 조회 결과 0건 |

정상 부팅에서 네 번의 저장소 읽기 결과는 기존 시험의 전체 공유 버퍼 해시와 각각 일치했다. 네 번째 읽기 뒤 원격 상대가 TFTP로 파일 전체를 요청했고, 583,456바이트를 대조한 뒤 QMI 닫기 응답 세 건을 받았다. 두 데몬은 요청 전후에 각각 같은 PID로 관측됐다. TFTP가 성공한 두 부팅에서 커널에 등록한 VM 시험 프로세서는 읽기 전후 모두 `offline`이었고 시작 호출 횟수는 0이었다.

이로써 저장소 백엔드가 지연된 부팅에서도 파일 서비스의 광고·읽기 성공을 따로 판정할 수 있다. 실제 S22+의 SCM 메모리 권한 수락, 기기 고유 저장소 입력, 메인라인에서 FYG1이 보내는 요청은 미확인이다. 이번 단위는 호스트에서 수행했다.

통합 아카이브는 2,988,260바이트다. 기존 Image와 대상 DT로 계산한 부트 외피 여유는 52,066,176바이트였고 검사한 RAM 구간에 겹침은 없었다. 검증 소스·아카이브·모델 DT와 부팅별 원시 기록은 `workspace/private/analysis/s22plus-dual-services.QliFmvKQ/`에 있다. `result.json`이 세 실행과 입력 해시를 연결한다.

## 순정의 5바이트 쓰기 요청과 Debian의 임시 디렉터리

FYG8 Android의 R4W1-A 부팅에서 AP의 TFTP 서버는 노드 0의 `readwrite/server_check.txt` 쓰기 요청을 73바이트로 기록했다. 같은 작업 스레드의 블록 크기·시간 제한·창 크기는 각각 7,680바이트, 5,000 ms, 10이었다. 쓰기 요청 기록에서 5,057 ms 뒤에 나온 통계는 1블록·5바이트였고 시간 초과와 잘못된 패킷 수는 모두 0이었다. 순정 서버 바이너리의 마지막 ACK 처리에는 응답을 기다리는 경우와 바로 반환하는 경우가 있다. 이 작업 스레드의 로그에는 어느 분기를 실행했는지나 마지막 ACK의 송신 시각이 없다. 순정의 다섯 바이트 내용도 미확인이다.

Debian `tqftpserv` 1.1-4는 `/readwrite/` 요청에 대해 `/tmp/tqftpserv`를 만들고 그 안에서 파일을 연다. 기존 통합 아카이브로 부팅한 VM에는 부모 디렉터리 `/tmp`가 없었다. 합성 상대가 같은 길이·옵션의 쓰기 요청을 한 번 보냈을 때 5,256 ms 동안 TFTP 응답이 없었고 파일도 생기지 않았다. 이어진 펌웨어 크기 조회와 여섯 구간 읽기는 모두 성공했다. [tqftpserv의 파일 경로 처리](https://github.com/linux-msm/tqftpserv/blob/master/README.md)

후속 RAM 아카이브에는 루트 소유의 빈 `/tmp` 디렉터리 하나(모드 `01777`)를 넣었다. 원래 89개 항목의 메타데이터와 내용은 모두 대조했다. 같은 커널과 같은 후속 아카이브로 두 번 부팅해, 모뎀을 대신하는 시험 상대가 5바이트를 보내는 순서를 바꿨다.

| 합성 상대가 데이터를 보낸 시점 | 서버의 쓰기 응답 | 펌웨어 읽기 |
| --- | --- | --- |
| 읽기 요청 전 | 옵션 3개를 확인한 뒤 데이터 1블록의 ACK 수신. RAM 파일의 5바이트가 입력과 일치 | 크기 조회와 여섯 구간 모두 성공 |
| 여섯 구간 수신 후 | 옵션 응답 뒤 열린 파일은 구간 수신이 끝날 때까지 0바이트. 데이터를 보내자 ACK 수신, RAM 파일의 5바이트 일치 | 쓰기가 진행 중인 같은 서버에서 모두 성공 |

세 부팅 각각에서 없는 `ota_firewall/ruleset` 읽기 두 건에는 오류 1이 돌아왔다. 이어진 여섯 구간은 합계 579,527바이트·79블록이었고 모두 FYG1 배포 원본의 해당 바이트와 일치했다. 독립된 원격 저장소에서는 읽기 네 건과 마지막 핸들 닫기를 포함한 11개 QMI 거래가 완료됐다. 이 시험은 Debian이 두 요청 순서를 처리함을 보여 준다. 실제 FYG1이 보낸 데이터의 시점이나 이 파일이 실기 기동에 필요한지는 미확인이다.

검증한 후속 아카이브는 2,988,281바이트이며 `workspace/private/analysis/s22plus-tftp-startup.epUDGnsc/with-tmp.cpio.gz`에 있다. 같은 디렉터리의 `result.json`에 두 아카이브의 SHA-256, 순정 원본의 근거 행, VM 원시 기록과 검사기 해시를 보관했다.

## PAS 드라이버 등록과 저장소 서비스 시작 순서

후속 아카이브의 SysV 시작 항목은 펌웨어 수신기를 `wait`로 실행한 뒤 `rmtfs`와 TFTP 시작 프로그램을 각각 `once`로 실행한다. 두 시작 프로그램이 명시적으로 적재하는 통신 모듈은 QRTR와 QRTR SMD다. 아카이브에는 PAS·RMTFS 모듈과 별칭 표가 들어 있지만 이들을 적재할 udev 데몬이나 modprobe 실행 파일은 없다. 커널 Image에서 추출한 설정에서도 modprobe와 uevent 보조 프로그램의 기본 경로가 비어 있다. 앞선 통합 VM에서는 시험 프로그램이 RMTFS 메모리 모듈을 적재하고 별도 시험 원격 프로세서를 등록했다.

ML053 기반 MPSS 활성 DT에서 PAS 드라이버 표에 맞는 네 장치 중 상위 노드까지 활성인 것은 MPSS 한 개다. 해당 설명은 `modem.mdt`를 선택하고 자동 기동을 끈다. 실제 드라이버는 SCM 가용 여부를 검사한 뒤에 원격 프로세서 객체를 할당하며, 초기화에 성공해야 `rproc_add`까지 도달한다. [Linux의 원격 프로세서 등록과 기동 API](https://docs.kernel.org/staging/remoteproc.html)

두 ARM64 VM에 MPSS와 같은 호환 문자열을 가진 플랫폼 노드를 넣었다. 둘 다 SCM 공급자는 없고, RMTFS 메모리는 VMID 속성을 생략한 RAM이다. 같은 Image와 같은 RAM 아카이브에서 시험 프로그램이 PAS 의존 모듈 8개(드라이버 포함)와 RMTFS 메모리 모듈을 적재하는 시점만 바꿨다. 두 부팅 모두 PAS 플랫폼 드라이버가 등록됐고, 커널 추적에서 `qcom_pas_probe`가 `-EPROBE_DEFER`(−517)를 반환했다. 모형 MPSS는 지연 목록에 있었고 드라이버 연결과 remoteproc 클래스 항목은 없었다.

| 모듈을 적재한 시점 | 저장소 결과 |
| --- | --- |
| 펌웨어 게시 전 | RAM 문자 장치가 먼저 생겼다. SysV가 시작한 Debian `rmtfs`는 서비스 14를 광고하고 QMI 11거래와 저장소 읽기 4건을 처리했다. |
| 펌웨어 게시 및 `rmtfs` 시작 작업의 `backend` 종료 후 | 같은 문자 장치가 뒤늦게 생겼다. 그 직후와 TFTP 시험을 마친 시점에 서비스 14는 광고되지 않았고 데몬도 없었다. |

두 경우 모두 같은 TFTP 데몬이 RAM의 5바이트 파일 쓰기를 확인했지만, remoteproc 클래스가 비어 있을 때 배포 파일의 첫 52바이트 읽기에는 오류 1을 반환했다. 이후 별도 시험 프로세서를 `offline`으로 등록하자 같은 경로·범위가 원본과 일치했다. 시험 프로세서의 시작 콜백 호출 횟수는 0이었고 모형 MPSS의 PAS 드라이버도 여전히 연결되지 않았다. 따라서 TFTP 쓰기, 펌웨어 읽기, 원격 저장소 응답은 각각 어느 구성요소가 제공했는지 구분할 수 있다.

실기용 기동 순서에서 남은 조건은 저장소 시작 작업 전에 메모리 드라이버를 적재하고 유효한 백엔드를 준비하는 것, 그리고 실제 MPSS가 remoteproc에 등록되는지 관측하는 것이다. S22+의 SCM 반환값이나 VMID 15 메모리 권한은 이 시험에서 측정하지 않았다. 두 부팅의 직렬 로그, 드라이버 반환값, 대상 DT 대응, 원본·검사기 해시는 `workspace/private/analysis/s22plus-pas-probe-order.5WoCxaC3/result.json`에 있다.

## Debian 시작 프로그램이 저장소 메모리 모듈을 적재한 시험

별도 H0 아카이브에서 `fyg1-rmtfs-start`가 펌웨어 게시와 합성 저장소 파일 세 개를 검사한 뒤 고정 경로의 `rmtfs_mem.ko`를 적재하도록 했다. 적재 후 기존 백엔드 검사를 거쳐 전용 장치 공간에서 Debian `rmtfs -r`를 실행한다. 기존 시작 프로그램을 먼저 재빌드해 보관 바이너리와 바이트 단위로 대조했다. 새 정상 아카이브에서 교체한 항목은 시작 프로그램 하나다. VM 시험 프로그램은 가상 USB·GLINK와 오프라인 시험 프로세서를 제공했다.

| ARM64 VM 입력 | 커널의 메모리 모듈 적재와 probe | 서비스 관측 |
| --- | --- | --- |
| 정상 합성 저장소, VMID 속성 없음 | 1회 적재, probe 0 반환 | 적재한 PID가 `rmtfs`로 전환. 서비스 14에서 QMI 거래 11건과 저장소 읽기 4건 완료 |
| 정상 합성 저장소, VMID 15, SCM 공급자 없음 | 1회 적재, 관측한 probe는 모두 −517 반환. 종료 시 모듈은 `live`, 장치는 지연 목록에 있고 문자 장치는 없음 | 기존 백엔드 검사에서 종료. 서비스 14 광고는 0건, TFTP 파일 쓰기와 여섯 구간 읽기 성공 |
| 합성 FS1의 한 바이트 변형 | 적재 0건 | 입력 검사에서 종료. TFTP 파일 쓰기와 여섯 구간 읽기 성공 |
| 마지막 송신 펌웨어 파일의 한 바이트 변형 | 적재 0건 | 펌웨어 게시 0건. 두 서비스 모두 시작 단계에서 종료 |

네 번의 완료 부팅에서 커널이 기록한 프로그램 실행·모듈 적재·probe 반환을 대조했다. 정상 부팅에서는 시작 프로그램의 실행, 메모리 모듈 적재, 배포 데몬 실행의 PID가 일치했고 최종 데몬은 SysV의 직계 자식이었다. 각 추적 구간은 기록 수와 보존된 이벤트 수가 일치했다. `qcom_scm_assign_mem` 호출은 네 구간 모두 0건이었다. MPSS 활성 대상 DT의 RMTFS 메모리 노드는 VMID 15를 지정한다. 실제 SCM 공급자가 있을 때의 권한 부여 결과와 실기용 저장소 입력은 계속 미확인이다. [Linux의 RMTFS 메모리 DT 속성](https://www.kernel.org/doc/Documentation/devicetree/bindings/reserved-memory/qcom,rmtfs-mem.yaml)

첫 정상 조건 VM은 가상 CDC-NCM 호스트 연결 시간 초과로 펌웨어 전송 전에 끝났다. 호스트가 받은 인증 바이트는 0이었다. 실패 로그를 보존하고 동일한 커널·RAM 아카이브로 새로 부팅해 표의 정상 결과를 얻었다. 정상 H0 아카이브는 2,988,428바이트이며 `workspace/private/analysis/s22plus-sysv-mem-owner.7PXKREeY/valid.cpio.gz`에 있다. 같은 디렉터리의 `result.json`에 원본·변경 항목 해시, 네 완료 부팅의 원시 기록과 첫 실패 기록을 연결했다.
