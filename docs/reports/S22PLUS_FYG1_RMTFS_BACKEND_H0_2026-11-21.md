# S22+ 메인라인 H0 · 원격 저장소 데몬의 백엔드 선택

Debian arm64 `rmtfs` 1.1-4는 기대한 RMTFS 문자 장치가 없어도 대체 경로를 시도한다. 따라서 모듈 적재, 프로세스 기동, 종료 코드 또는 서비스 공지만으로 이 데몬이 의도한 메모리 백엔드를 사용한다고 판정할 수 없다.

## 발견 경위

ML053에서 분리한 PAS 활성 Image로 ARM64 QEMU virt를 부팅했다. 합성 RMTFS 예약 노드의 클라이언트 ID는 1이고 크기는 2,621,440바이트였다. VMID 속성을 생략한 대조 부팅에서는 실제 커널 드라이버가 플랫폼 장치에 바인딩되고 문자 장치가 생겼다.

두 번째 부팅은 메인라인 S22+ DT와 같은 VMID 15를 지정했고 VM에는 Qualcomm SCM 공급자가 없었다. 모듈 적재 자체는 성공했다. 시험 프로그램은 해당 플랫폼 장치가 커널의 지연 탐색 목록에 있고 드라이버 링크와 문자 장치가 사라진 것을 확인했다. 이때 배포 데몬을 바로 시작한 첫 시험은 실패했다. 데몬은 RMTFS·UIO 장치가 없다는 진단, `/dev/mem` 대체 경로 진단을 차례로 출력한 뒤 QRTR 소켓 생성 단계까지 진행했다. 그 시험에는 QRTR 모듈을 적재하지 않았다. 보관된 로그가 직접 보여 주는 마지막 단계는 소켓 생성 실패다. 실제 메모리 내용의 읽기·변경은 측정하지 않았다. 이 경로를 실행한 곳은 폐기 가능한 VM이었다.

## H0 수정의 적용 범위

원래 Image와 initramfs를 보존하고 별도 출력에서 일반 물리 메모리 장치 지원을 끈 커널을 빌드했다. 데몬은 배포 패키지 바이트를 그대로 사용한다. 시험용 SysV 자식은 예정한 DT 노드와 플랫폼 드라이버, 문자 장치 번호, 커널 클래스와 실제 부모가 한 장치를 가리키는지 확인한다. 서비스 자식의 전용 마운트 네임스페이스에는 확인한 문자 장치를 고정해 노출한다. 정상 사용은 펌웨어 게시와 백엔드 확인이 모두 끝난 뒤에 시작한다.

이 조건은 대체 백엔드로 진입하는 이번 실험의 위험을 다룬다. 적용 대상은 이 메인라인 H0 구성이다. 커널의 장치 구성, Debian 패키지 또는 서비스 시작 방식이 바뀌면 해당 경로를 다시 확인한다. 후속 배포본이 다른 백엔드를 열 수 없고 백엔드가 없을 때 정상 서비스를 시작하지 않는다는 소스·실행 증거가 있으면 대체 경로 방지 조치의 필요성을 재평가할 수 있다.

## 검증 결과

새 ARM64 Image의 SHA-256은 `5a0b12b0e6907c6516ad7f839baa59a31ce027e2a16d6d351634f57e64dd7406`이다. Image에서 직접 추출한 설정이 빌드 설정과 일치했다. 변경된 설정은 `DEVMEM=y→n`과 그에 종속된 `STRICT_DEVMEM=y→n` 두 개였다. 별도의 양성·음성 대조 VM에서 동일한 클라이언트 ID와 예약 크기를 쓰고 VMID만 바꿨다. VMID를 생략하면 드라이버가 연결됐다. VMID 15와 SCM 공급자 부재를 조합하면 모듈은 적재되고 정확한 플랫폼 장치는 지연 목록에 남으며 문자 장치는 없었다.

최종 통합 시험 세 건은 같은 커널과 같은 SysV 시험 프로그램을 사용했다. 정상 데이터는 배포 펌웨어 28개이고, 변형 대조는 마지막 파일의 한 바이트만 바꿨다.

| 펌웨어와 백엔드 조건 | 관측 |
| --- | --- |
| 정상 파일, 문자 장치 준비 | USB CDC-NCM으로 전송한 파일 전체를 검증·게시했다. 데몬 전용 `/dev`에서 고정 문자 장치를 확인했다. 합성 원격 노드가 GLINK를 통해 QMI 응답 4건을 받았고, 두 번째 파일 섹터 512바이트가 버퍼 오프셋 4,096에 들어갔다. 버퍼 전체와 원본 파일을 대조했다. |
| 정상 파일, VMID 15와 SCM 공급자 부재 | 파일 검증·게시 후 실제 시작 경로가 데몬 생성 전에 멈췄다. 게스트의 QRTR 이름 서비스가 서비스 14에 대한 빈 조회 결과를 반환했다. |
| 변형 파일, 문자 장치 준비 조건 | 파일을 게시하기 전에 거부했다. 커널에서 MDT가 보이지 않았고 데몬도 시작되지 않았다. |

첫 정상 시험은 장치 파일을 연 후 새 마운트 네임스페이스를 만들면서 bind mount가 `EINVAL`로 실패했다. 네임스페이스를 먼저 분리한 뒤 그 안에서 장치를 열어 고정하도록 수정했다. 최종 실행의 데몬 바이너리는 원래 Debian 패키지와 같다. 독립 검토자가 세 결과의 원시 로그 해시와 최종 실행기 해시를 대조했다.

비공개 빌드 디렉터리는 `workspace/private/analysis/s22plus-ml053-pas-initramfs.BEBv3qNj/`이다. 초기 실패 로그는 `scm-vmid15/run-143449.log`, 최종 통합 결과는 `guarded-glink-{valid,deferred,altered}-pass.json`이다. `phase2-evidence.json`의 SHA-256은 `b34121b52c82f7c9d144709a84af22014eb2579a97010fc568882a54ff9d9f91`이다. 새 Image와 2,005,257바이트 부트스트랩을 다시 링크해 기존 배치 및 96 MiB 외피 적합성도 확인했다. VM 전용 실행기·가상 USB 호스트·두 번째 GLINK 끝점은 시험용 오버레이에 있다.

순정 S22+에서는 별도의 D0로 MPSS·RMTFS 및 IPCRTR 드라이버 바인딩을 관측했다. 새 커널이 S22+에서 SCM에 지정한 고정 영역이 실제로 승인되는지는 여전히 미확인이다. 이어지는 PAS 인증과 실제 FYG1의 GLINK 응답도 각각 실기 증거가 필요하다. [연구 목표와 순정 실측 기록](../GOAL_S22PLUS_MODEM.md)
