# S22+ SCM 입회 관측용 부트 패키지 H0

SM-S906N / g0q / FYG8용 부트 AP를 호스트에서 만들었다. SHA-256은 `c7dd8fa726fee413a0d9cddc37b58cbf16f05b5695ef84469c261e6396bb83d9`, 크기는 25,456,681바이트다. 새 프로토콜은 Debian의 관측기가 읽은 SCM 플랫폼 장치의 첫 연결 상태를 USB로 한 번 보고한다. 앞선 VM에서 검증한 관측 시점과 한계가 적용된다. [USB 판독 실험](S22PLUS_MAINLINE_SCM_USB_H0_2026-11-22.md)

## 패키지에 들어간 바이트

두 번 생성한 AP와 96 MiB 부트 이미지가 각각 일치했다. 두 AP를 각각 열어 유일한 멤버 `boot.img.lz4`를 해제한 뒤, 부트 v4의 kernel 필드에서 uniLoader를 꺼냈다. 링커 심볼이 가리키는 구간에서 Image, DT, 초기 RAM 파일시스템을 다시 추출했다. 실제 패키지에 들어간 조합은 다음과 같다.

| 구성 요소 | 확인 결과 |
| --- | --- |
| ARM64 Image | 선정한 `5a0b12b0e690…`와 일치. 같은 빌드의 ELF에서 다시 추출한 파일과도 일치 |
| DT | MPSS·UFS·SD 컨트롤러를 비활성화한 ML053 원본과 일치 |
| Debian RAM | ML022의 28개 항목 중 관측기만 교체. SysV init, inittab, 런타임 라이브러리와 장치 노드를 포함해 전체 CPIO를 바이트 단위로 대조 |
| SCM 관측기 | 새 후보의 키·ID와 기기용 UDC를 넣은 597,976바이트 정적 AArch64 ELF. 최종 생성 소스로 다시 빌드해서 AP 안의 파일과 일치 |
| 원래 Android | 보관한 원복 AP의 단일 멤버를 해제한 부트 해시가 대상의 최종 건강 검사 기준 및 패키저의 원본과 일치 |

실제 uniLoader 명령을 실행한 배치·인계 대조 20건에서 정상 인계와 거부 분기를 확인했다. QEMU에서는 실제 EL1·EL2에서 재배치 진입, EL3에서 거부를 관측했다. 호스트 검증이 재현한 RAM과 CPU 조건에 대한 결과다.

## 판독기의 기기·시험 구분

기기형 프로토콜에는 VM용 두 프로토콜과 다른 인증 도메인과 요청·응답 매직을 부여했다. [생성기](../../workspace/public/src/mainline/s22plus_canary_h0/scm_usb_h0.py)는 기기용 판독기에 봉인된 원시 캡처를 받는 진입점만 내보낸다. 판독기는 캡처 성공, HMAC, 후보·요청 nonce, 초기 PID 네임스페이스의 Debian PID 1과 관측기, inittab, SCM 상태값, 전송된 DT와 initrd 경계를 검사한다.

기존 속성 비교는 속성이 하나도 없는 빈 DT 말단 노드를 추가해도 통과할 수 있었다. 기기용 판독기는 실제 후보 로더를 실행해 회수한 **500,000바이트 DT 전체의 SHA-256**도 요구한다. 길이를 유지하고 빈 노드 하나만 더한 서명된 시험 응답은 이 검사에서 거부됐다. 과거 ML022 실기에서 받은 DT는 당시 로더를 에뮬레이터에서 실행해 회수한 DT와 해시가 같았다. 이번 후보에서 정당한 런타임 차이가 생겨도 정확한 해시가 다르면 판독은 실패한다.

시험용 ARM64 코덱은 실제 후보와 다른 고정 키와 ID로 세 상태값을 서명했다. 최종 판독기는 세 응답을 각각 판정 불가·미연결·연결로 읽었다. 거부 대조 10건에는 실패한 캡처, 다른 후보·nonce, VM 표식, 변조된 상태, 잘못된 initrd 끝, 변경된 보드 호환 문자열과 빈 DT 노드가 포함된다. 기기용 빌드에 VM 플래그 또는 외부 시험 모델 선택을 넣은 두 조합도 컴파일 단계에서 거부됐다. 기존 두 VM 프로파일의 생성 소스는 앞서 검토한 소스와 바이트가 같았다. [회귀 테스트](../../tests/test_s22plus_scm_usb_h0.py)

비공개 `workspace/private/analysis/s22plus-scm-board-artifact.Z9b5Fre8/final-zacx9vk1/qualified-artifact.json`에 최종 AP·부트·로더·원래 Android 복구 파일·판독기·기대 DT·원시 시험 기록을 연결했다. 목록의 SHA-256은 `f7b87ae16ed194cd20306a090a1dbfe953d4d772e993e02adc593d6a7aef3a75`다. 체크를 보강하기 전의 생성기와 빌드 매니페스트를 보존했고 최종 판독기의 해시는 별도로 기록했다. 독립 검토에서 두 AP의 내부 구성과 세 시험 응답의 HMAC을 다시 대조했다.

## 입회 부팅까지 남은 일

기존 Debian RAM 프로파일에 이 후보의 매니페스트를 입력하면 아카이브 검증과 USB 프로토콜 선택에서 모두 새 스키마를 거부한다. 입회 실행에는 이 후보와 최종 판독기·기대 DT를 묶는 S22+ 프로파일 검토와 채택이 필요하다. 여기에는 SCM 코어의 초기화 효과, 한 번의 USB 요청과 결과 처리, 입회 Download에서 원래 Android를 복원하는 경로가 포함된다. 후보 키로 서명한 실물 응답, 현재 기기 상태·Download 복구 가능성, 실행 승인은 이번 H0에서 확인하지 않았다.
