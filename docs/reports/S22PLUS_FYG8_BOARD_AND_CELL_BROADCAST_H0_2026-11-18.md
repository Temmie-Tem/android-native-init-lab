# SM-S906N 실기 보드 식별과 재난문자 수신 상태

국내판 S22+의 기존 실기 기록을 FYG8 순정 기기 트리와 대조했다. 실기 기록은 AP 보드 리비전 16과 이 보드에 적용된 기기 트리를 식별한다. 모뎀이 선택한 RF 카드나 실장 트랜시버의 실리콘 리비전을 식별할 수 있는 값은 찾지 못했다.

## 실물과 펌웨어의 대응

| 관측 대상 | 대조 결과 |
| --- | --- |
| 실험 단말 | 7월 13일에 수집한 두 보고서가 모두 모델 `SM-S906N`, 제품 `g0q`, 부트로더 `S906NKSS7FYG8`, 베이스밴드 `S906NKSS7FYG1`을 기록했다. |
| AP 보드 | Android 속성 `ro.boot.revision`은 16이고 XBL의 하드웨어 리비전 기록은 `0x10`이다. 커널의 기기 트리 모델 표기는 두 보고서 모두 `Samsung G0Q PROJECT (board-id,12)`이다. |
| 순정 DTBO | 컨테이너의 11개 항목을 모두 해석했다. 항목 10(0부터 셈)의 모델이 실기 기록과 같으며, 시작·끝 리비전은 `0x0c`와 `0x20`이다. 리비전 16이 들어가는 항목은 이것 하나다. FYG8 공개 커널 소스의 `g0q_kor_singlex_w00_r12.dts`와도 일치한다. |
| 모뎀 RF 식별 | RIL이 보고한 값은 `ril.hw_ver=REV0.7`이다. 두 ZIP의 `dumpstate.txt`와 `dumpstate_board.txt`에서 이 값과 RF 카드 ID를 연결하는 기록, QLINK 번호와 실장 칩 리비전을 함께 식별하는 기록을 찾지 못했다. |

따라서 기기 트리 이름의 12를 모뎀 RF 카드 번호로 대입할 근거가 없다. 국내 모델의 n78 지원 자체는 제조사가 명시한다. 확인한 실기 기록에서는 n78 접속, 기지국 역할의 송신, 독립 수신기의 파형 관측을 입증할 수 없었다. [삼성전자 국내 모델 사양](https://www.samsung.com/sec/support/model/SM-S906NZEWKOO/)

국립전파연구원의 해당 모델 적합인증 원문에서도 장비 역할을 확인했다. 2022년 2월 11일 인증한 `R-C-SEC-SMS906`의 모델은 `SM-S906N`이며, 3.5 GHz 5G NR 장비의 분류는 ‘육상이동국의 송수신장치’다. 이 기록은 국내 모델의 이동국 송수신 용도를 뒷받침한다. 기지국 역할의 동작 여부를 판정할 시험 결과나 RF 부품 명세는 이 인증 조회표에 없다. [국립전파연구원 모델별 적합인증](https://www.rra.go.kr/ko/license/A_b_popup_keyno.do?key_no=R-C-SEC-SMS906)

## 실드를 열지 않고 RF 칩을 식별할 수 있는 조건

FYG1 모뎀 펌웨어에는 RF 칩의 식별 워드와 제조원 정보를 읽는 별도 경로가 있다. 보드 리비전 16에 귀속되는 보관 로그에서는 두 값을 실측한 기록을 확인하지 못했다.

| FYG1 초기화 단계 | 코드에서 확인한 동작 | 실기 값을 해석할 때 필요한 구분 |
| --- | --- | --- |
| 초기 객체 | QLINK 0의 초기 형식 20이 선택하는 클래스의 C++ 형식 정보는 `Sdr735v2Seq`다. 생성자가 식별 워드에 `0x39040`을 미리 넣는다. | 이 단계의 클래스명과 값은 펌웨어의 예상값이다. |
| 식별 읽기 | 캐시가 아직 유효하지 않으면 칩 식별 읽기 메서드를 호출한다. 이 메서드는 QLINK 읽기 경로에 `0x400`을 넘긴다. 0을 받으면 최대 세 번까지 시도하고, 세 번 모두 0이면 `0x39040`을 반환한다. | 실제 응답과 대체값이 같은 캐시 필드에 들어간다. 이 워드는 RF 소프트웨어 형식 7로 분류될 수 있다. 형식 7, 캐시 유효 표시, 최종 워드만으로는 읽기 성공을 입증할 수 없다. |
| 제조원 읽기 | `sdr735_common_class`의 `init_chip_params`가 `read_qfprom`을 호출한다. 읽기와 표 해독이 성공하면 `get_sdr_fab_src`가 해독 배열의 여섯 번째 항목을 돌려준다. FYG1의 기호 정의에서 이 항목은 2비트다. | 버퍼를 먼저 할당하므로 포인터 존재나 접근자의 성공만으로 앞선 하드웨어 읽기 성공을 대신할 수 없다. 이 2비트 필드 전체를 제조사 문서의 소스 구성 코드와 같은 열거값으로 볼 근거도 확인하지 못했다. |

RF 카드 진단 함수 `rfc_debug_update_phys_dev_status`는 제조원 조회를 호출하고, 물리 장치별 표에 `Dev_ID`, `Prod_Rev`, `HW_Rev`, `FAB_SRC` 등의 열을 마련한다. 제조원 조회가 실패해 오류를 기록한 경우에도 표 출력은 계속된다. 실드 없이 실리콘 버전을 확정하려면 동일 단말·부팅·트랜시버의 **성공한 식별 읽기와 실제 리비전·제조원 값**을 확보하고 제조사 버전표와 대응시켜야 한다. `0x39040`의 하위 바이트 `0x40`과 패키지 마킹 `001` 사이의 일대일 대응도 입증되지 않았다. [SDR735 리비전 가이드 80-PP662-4의 식별표 전재본](https://bbs.16rd.com/thread-611472-1-1.html)

7월 실기 bugreport 두 건을 모델·베이스밴드·AP 리비전과 원본 ZIP 해시로 다시 확인했다. 두 ZIP 안의 dumpstate·보드·복구 자료 등 78개와 별도 S22+ 부팅·커널 로그 55개를 검색했다. 총 133개 항목 중 내용이 고유하고 비어 있지 않은 것은 81개다. 읽을 수 있는 텍스트에서는 `SDR735`, QLINK 식별 기록, 위 물리 장치표, `FAB_SRC` 값이 발견되지 않았다. 숫자 `039040`이 나온 고유 내용 세 건은 모두 `set_cisd_power_data` 전력 로그의 타임스탬프 소수부였다. 압축 해제된 로그의 텍스트 검색 결과로 미해독 바이너리 패킷의 내용을 판정하지 않았다.

비공개 근거는 `workspace/private/analysis/s22plus-fyg8-cp-static.zjrEXG/rf-id.uGXEUG/`의 `identity-evidence.txt`와 `log-scan.json`에 있다. 원본 CP 해시, 상주 세그먼트 해시, 원본 QDB의 압축 해제 결과, 두 코드 복원본의 대상 구간, 실제 가상 함수 테이블과 제조원 필드 정의를 대조했다.

### 11월 19일 RF 진단표 저장 경로와 실기 관측

FYG1의 `rfc_common_create_efs_report`는 CMW 상태를 조립할 때 `rfc_common_dump_report`를 통해 물리 장치표를 추가한다. 완성된 버퍼와 길이, 파일명 **`rfc/rfdevice_report.dat`** 를 `rfcommon_efs` 쓰기 함수에 전달한다. 이 파일명은 모뎀 EFS 쪽에서 해석된다. 보고서 생성 함수의 존재만으로 특정 부팅에서 파일을 생성했다거나 안드로이드에 사본을 내보냈다고 판정할 수 없다. 같은 보고서의 `RF QLink Init Success`는 공통 초기화 상태다. QLINK 0의 칩 ID 읽기가 대체값 없이 성공했는지 알려면 그 읽기 자체의 결과가 필요하다.

USB 디버깅 허용 후, 운영자 소유 단말의 비공개 USB 식별값과 ADB의 모델·제품을 대조했다. 읽기 전후에 FYG8 부트로더, FYG1 베이스밴드, AP 리비전 16과 동일한 Android 부팅 ID를 확인했다. `su`는 UID 0을 반환했다. RIL 속성 `ril.hw_ver`의 현재 값은 `REV0.7`이었다.

| 확인한 근거 | 해당 부팅의 관측 결과 |
| --- | --- |
| Android 측 보고서 사본 | 조사한 로그·내보내기 디렉터리(최대 3단계)와 AP에 노출된 MPSS의 `readwrite`, `shared`, `hlos`, `ramdumps` 경로에 검사한 이름의 읽을 수 있는 사본이 없었다. CP 내부 EFS의 파일 존재 여부는 미확인이다. |
| 현재 로그 | 현재 커널 로그와 보관 중인 `radio`, `main`, `system` 버퍼에서 칩 이름, QLINK, 진단표 열, 식별 워드와 RFIC·리비전 대체 표기를 검색했다. 장치 행이나 식별 읽기 결과는 발견되지 않았다. `radio_PRECONFG_SET.log` 932줄에서도 관련 표식을 찾지 못했다. |
| 이전 부팅 로그 | `.gz` 확장자였던 기존 파일 6개가 ZIP임을 확인했다. 고유 ZIP 5개, 중복 포함 내부 항목 36개에서 RF 식별 표식을 찾지 못했다. 이 파일들을 현재 부팅의 관측으로 계산하지 않았다. |

판정은 **QLINK 0 칩 ID 읽기 성공 여부 미확인, RF 칩의 `HW_Rev`·`FAB_SRC` 값 미관측, SDR735 v2.0 실장 여부 미확정**이다. 같은 Android 부팅을 확인했으나 CP 부팅을 따로 식별할 기록은 없었다. 최초 전체 버퍼 정규식 검색은 20초 시간 초과로 끝났으며, 현재 로그 판정에는 이후 개별 버퍼에서 완료된 읽기를 사용했다. 이 관측 중 보고서를 새로 생성하거나 단말을 재부팅하지 않았다.

비공개 근거는 `workspace/private/analysis/s22plus-fyg8-cp-static.zjrEXG/rf-report.kAlPuz/`의 `file-writer-evidence.txt`와 `observation-result.json`이다. 파일명 리터럴과 쓰기 호출을 포함한 코드 4개 구간을 대조하고 실기 캡처 핸들 102개의 원본을 재검증했다.

### 기존 CP EFS 파일을 읽는 순정 진단 경로

FYG1 진단 디스패처가 호출하는 `fs_diag_read`에서 경로 검사, 기존 파일 열기(생성 플래그 없음), 내용 읽기와 응답 처리를 확인했다. 이 분기는 RF 보고서 생성 함수를 호출하지 않는다. 특정 파일의 존재나 현재 세션의 CP 접근 허용 여부는 펌웨어 코드만으로 결정할 수 없다.

11월 19일 같은 Android 부팅에서 UID 0으로 확인하니 `vendor.diag-router`가 실행 중이었다. USB 구성은 `mtp,conn_gadget,adb`였고 활성 구성에 전용 DIAG 함수가 없었다. 설치된 진단 HAL은 범용 전송 메서드를 제공한다. 확인한 순정 실행 파일과 인터페이스에서는 현 상태에서 기존 EFS 파일 하나를 조회하는 지원 명령을 식별하지 못했다. 이번 연결에서는 CP에 요청을 보내지 않았으므로 파일의 존재 여부와 값은 미확인이다. 원본 관측과 정적 구간 해시는 비공개 분석 디렉터리 `diag-existing.PqVUzD/`에 보관했다.

같은 부팅에서 수집한 HAL 라이브러리 세 사본의 클라이언트 심볼을 인터페이스별로 대조했다. `Idiag::open`은 콜백 객체를 인자로 받으며 파일 경로 인자가 없다. `Idiag::write`는 메모리 버퍼와 길이를 받고, `send_data`는 콜백 인터페이스에 속한다. 따라서 라우터가 실행 중이라는 관측만으로는 특정 파일을 열었거나 읽을 수 있다고 판정할 수 없다. 이 경로에서 파일을 실측하려면 CP로 EFS 조회 요청을 전송해야 한다. S22+ D0는 페이로드 전송을 제외하므로 이 재검토에는 보관된 자료만 사용했다. [S22+ D0 범위](../operations/targets/S22PLUS_FYG8_TARGET_CONTRACT.md#s22-d0)

### 기존 보고서 단건 조회 절차의 독립 검토

독립 검토자는 [S22+ 전용 조회 절차](../operations/S22PLUS_FYG1_EXISTING_RF_REPORT.md)의 최종 SHA-256 `717e3bbd43c97bbea2e070828add1c82ed3f3c9ab523420d2a63f776ca1b8421`에 대해 **H0 절차 설계 통과, 실기 조회 미승인**으로 판정했다. 초안 검토에서 지적한 타 클라이언트의 응답 저장·콜백 간섭 문제와 EOF 이후 종료 판정 문제를 수정한 뒤 같은 검토자가 최종 문서를 다시 확인했다. 독립 대조에서는 보관한 두 CP 코드 복원본 각각에서 읽기 경로 5구간, 생성 경로 4구간 및 식별 경로 11구간의 해시가 기존 근거와 일치했다.

실기 판단의 근거는 해당 CP 요청을 허용하는 활성 S22+ 계약과 이 한 파일의 무변경 읽기를 보장하는 검증된 클라이언트·거래 경로가 없다는 점이다. 이번에는 단말에 접속하거나 CP에 요청을 보내지 않았다. 보관 기록에서도 CP 부팅 식별자와 파일 내용이 확보되지 않아 QLINK 0의 칩 ID 출처, `HW_Rev`, `FAB_SRC`는 미확인이다.

### 순정 HAL과 FYG1 읽기 함수의 호스트 실행

[H0 실행기](../../workspace/public/src/scripts/analysis/s22plus_rf_report_h0/read_fixture.py)는 `rfc/rfdevice_report.dat` 한 이름을 고정한다. 호스트에 보관한 FYG8 vendor 이미지의 SHA-256을 이전 추출 기록과 대조한 뒤 HAL과 라우터 ELF를 읽었다. Android 쪽은 FYG8 배포본, CP 쪽은 그 배포본에 포함된 FYG1이다. USB 및 실기 접근은 없었다.

| 구간 | 실제 실행 범위 |
| --- | --- |
| ARM64 HAL 프록시 | Unicorn에서 순정 `open`, `write`, 콜백 `send_data`, `close` 진입 코드를 실행했다. Android 프레임워크 함수는 시험용 기록기로 대체했다. 프록시가 넘긴 인터페이스·콜백 참조·공유 메모리 객체·길이를 검사하고 해당 버퍼의 바이트를 다음 구간에 전달했다. |
| ARM64 라우터 | 순정 `diagService::write`의 진입부터 `mapMemory` 호출까지 실행해 전달된 객체와 길이를 확인했다. 이후 CP까지의 전송은 호스트 파이프로 대체했다. 시험용 태그는 실제 FYG1 디스패처에서 이 읽기 함수를 선택할 수 없다. |
| Hexagon CP | 두 코드 복원본에서 해시가 일치하는 순정 `fs_diag_read` 함수 전체를 별도의 ELF에 링크하고 QEMU에서 실행했다. 경로 검사·EFS·패킷 할당 등 외부 함수는 [한 파일의 시험용 구현](../../workspace/public/src/scripts/analysis/s22plus_rf_report_h0/efs_fixture.c)을 사용했다. 성공 경로에서 순정 코드는 고정 이름과 열기 플래그 0을 전달했다. 파일 내용은 위치로 결정되며 변경 API가 없다. |
| 종료 | 라우터의 순정 `diagService::close` 함수 전체는 반환 객체만 채워 복귀했다. 별도 `serviceDied`에서 클라이언트 정보 제거 호출을 정적으로 확인했다. 시험 결과의 `fixture_closed`는 호스트 시험의 종료 상태다. 실제 Binder 사망 통지나 다른 클라이언트의 등록 보존을 관측한 값은 없다. |

11개 시험을 실행했다. 빈 파일, 256바이트, 513바이트, 256 KiB에서 조립한 모든 바이트가 입력 패턴과 일치했다. 256 KiB에서는 열기 1회, 읽기 1,024회, 닫기 1회였다. 가상 파일 부재와 접근 거절에서 열기는 0회였다. 다른 콜백, 잘린 응답, 기한 만료, 종료 확인 유실, 크기 초과도 검사했다. 잘린 두 번째 응답에서는 앞서 검증한 256바이트만 남았다. 종료 확인 유실에서는 10바이트를 모두 얻었고 시험 세션은 종료 미확인이었다.

**실제 순정 전송을 통한 한 파일 무변경 읽기는 부분 검증 상태다.** `fs_diag_read`는 새 파일을 열기 전에 고정된 상태 슬롯의 이전 핸들을 정리할 수 있다. 시험은 슬롯이 비어 있는 초기 상태에서 시작했다. 단말의 CP에서 이 슬롯이 해당 조회에만 귀속되는지, 실제 EFS 백엔드가 접근 시각 등 저장 메타데이터를 보존하는지, 순정 라우터가 요청·응답을 끝까지 같은 클라이언트에 연결하는지는 입증되지 않았다. 가상 파일의 바이트는 실기 RF 칩 판정에 사용하지 않았다.

재현에는 [빌더](../../workspace/public/src/scripts/analysis/s22plus_rf_report_h0/build_fixture.py)에 FYG1 복원본 디렉터리, 새 비공개 출력 디렉터리, Hexagon 지원 LLVM 21 바이너리 디렉터리를 차례로 전달한다. 실행기의 인자는 해당 순정 HAL ELF, 라우터 ELF, 빌드한 `efs-fixture`다. 실행 환경은 Python의 pyelftools·Unicorn 2.1.4, QEMU Hexagon 10.2.1 및 bubblewrap이다. 이번 실행의 원본은 `workspace/private/analysis/s22plus-fyg8-cp-static.zjrEXG/hal-file-h0.1G5VCa/`의 `verified.json`과 `provenance.json`에 있다.

### 응답 수신자와 콜백 수명 추적 (H0)

FYG8 순정 라우터의 송신 쪽과 수신 쪽을 따로 추적했다. `open`은 Binder 호출자의 PID를 키로 콜백의 강한 참조를 저장하고, 같은 PID를 사망 통지의 쿠키로 넘긴다. `write`는 `mapMemory` 이후 공유 버퍼의 포인터와 Binder 호출자의 PID를 얻어 메시지 종류에 따라 분기한다. 확인한 사용자 데이터 분기에서는 등록 상태에 따라 하위 처리기로 넘기는 클라이언트 식별값이 달라질 수 있다.

HIDL로 반환하는 `diag_md_write` 분기에서 수신자 키는 라우팅 테이블에서 선택한 레코드에 들어 있다. `diag_copy_for_hidl_client`는 데이터 길이와 그 키를 큐에 전달한다. 작업 스레드는 키에 일치하는 등록을 찾아 해당 콜백의 `send_data`를 호출한다. 두 순정 ELF를 대조해 콜백 가상 메서드까지 식별했다. **큐의 키가 어느 콜백을 선택하는지는 확인했다. 이 파일의 요청이 나갈 때 선택한 식별값과 CP 응답이 돌아올 때 큐에 들어간 키가 같은지는 미확인이다.** 보관된 실기 기록에는 해당 거래가 없으며 앞선 호스트 시험은 이 연결을 파이프로 대체했다. 이 맵은 같은 PID 안의 개별 요청을 구별하지 않는다.

| 확인 항목 | 검증 결과 |
| --- | --- |
| 다른 PID의 AP 콜백 | ARM64 순정 조회·삭제 코드를 가상 등록 두 건으로 시험했다. 두 키는 각각 자기 콜백을 선택했고 미등록 키는 일치 항목이 없었다. 각 PID의 사망 쿠키를 별도로 넣자 해당 노드만 빠지고 다른 콜백 참조는 유지됐다. 미등록 쿠키에서는 두 등록이 모두 유지됐다. 이 결과는 단일 스레드에서 확인한 해당 맵의 동작이다. |
| `serviceDied`의 해제 범위 | 쿠키와 일치하는 노드를 트리에서 제거하고 그 노드의 비어 있지 않은 콜백에 `RefBase::decStrong`을 호출한 뒤 노드를 해제하는 분기를 확인했다. **이 등록이 소유하던 강한 참조는 해제된다.** 모의 실행은 제거된 노드의 참조값까지 확인했고, 이후 `decStrong` 호출은 정적으로 확인했다. 객체의 마지막 참조 여부, 진행 중인 전달의 완료, 실제 Binder 사망 통지 시점은 관측하지 않았다. |
| 다른 클라이언트의 CP 파일 핸들 | FYG1 `fs_diag_read`의 첫 읽기 분기는 고정된 상태 슬롯에서 기존 핸들을 읽고, 유효하면 닫은 뒤 요청 파일을 연다. 이 결정에 Android 콜백 맵의 PID를 대조하는 동작은 없다. 슬롯의 독점 소유를 입증할 근거가 없어 다른 클라이언트의 CP 핸들 보존은 보장할 수 없다. 실제 타 핸들이 닫힌 관측도 없다. |
| 파일 내용과 저장 메타데이터 | 기존 파일은 열기 플래그 0으로 열린다. 정상 경로에서 할당된 파일 서술자의 읽기 메서드까지 대조했다. 양수 길이를 읽으면 증가하는 값은 열린 서술자의 현재 오프셋이다. 데이터 읽기는 해당 파일 노드(vnode)의 파일시스템 구현으로 위임된다. 이 파일에 선택된 구현과 읽기 전후의 저장 메타데이터를 관측하지 못해 접근 시각(`atime`)을 포함한 메타데이터 보존은 미확인이다. |

이번 추적은 호스트의 보관 ELF와 CP 코드 복원본만 사용했다. 두 PID 조회·삭제 결과, 입력 및 구간별 해시는 비공개 분석 디렉터리 `router-ownership.r50JYI/`의 `registry.json`과 `evidence.json`에 보관했다.
