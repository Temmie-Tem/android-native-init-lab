## Display-Clock Side Effects

The exact source-matched probe is not MMIO-only:

1. `qcom_cc_map()` maps only the display controller's first
   `IORESOURCE_MEM`, using a regmap whose maximum offset is `0x11008`.
2. `qcom_cc_runtime_init()` acquires the optional interface clock, the ICC
   path, and the `vdd_mm`/`vdd_mxa` regulator handles.
3. `pm_runtime_get_sync()` invokes `qcom_cc_runtime_resume()`, which votes
   voltage level 1 for both supplies, votes ICC bandwidth, and resumes the
   interface clock.
4. The probe programs two display PLLs and two display-controller clock-gating
   registers through that MMIO regmap.
5. `qcom_cc_really_probe()` issues maximum-level proxy votes before registering
   reset, clock, and OF clock-provider objects. The regulator implementation
   can call `regulator_set_voltage()` and `regulator_enable()`.
6. The success path calls `pm_runtime_put_sync()`, which can drop the runtime
   voltage and ICC votes. The proxy vote remains until `sync_state`; some
   post-get probe error paths also lack a matching put.

These are standard clock/regulator/interconnect framework operations used by
the same stock module, but they are real transient power-state changes outside
the display MMIO resource. The bounded safety conclusion is:

- no source-reachable persistent-storage, fuse, bootloader, partition, or raw
  PMIC write exists in this closure;
- no DRM, panel, framebuffer, or display userspace is introduced;
- the runtime only inserts modules and never unloads this driver;
- a failed probe may retain a framework vote until reboot; and
- the mandatory reboot into attended Download recovery before exact Magisk
  rollback clears candidate-kernel RAM/MMIO/framework state before Android
  health is judged.

This is acceptable for a later attended boot-only F1, but it must not be
described as an observational or MMIO-only action.
