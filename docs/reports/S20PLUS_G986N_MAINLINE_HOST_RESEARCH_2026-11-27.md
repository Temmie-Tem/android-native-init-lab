# S20+ 메인라인 부팅과 USB 서버의 호스트 조사

2026-11-27. 대상은 Samsung Galaxy S20+ 5G SM-G986N, y2q, IYC2다. Claude Opus 5.5와 Gemini 4 Carbon Medium이 각각 세 차례 검토했다. 3차 검토 때 두 모델은 추가 호스트 조사가 소진됐다고 판단했다. 이후 복귀 판독 실험에서 새 문제가 재현돼 이 결론을 정정했다. [두 부팅을 이어서 시험한 결과](#원복-판독과-부트루프-귀속-재검토) Carbon의 마지막 조건이었던 복합 USB 실험도 완료했다. 이 조사에서 휴대전화 명령, 재부팅, AP 전송은 모두 0건이다.

실물에서 확인된 마지막 단계는 Linux 6.18이 지연된 드라이버 초기화를 재시도하도록 요청하고 첫 `flush_work()`를 호출하기 직전이다. 첫 원복 부팅에서 확보한 하나의 완성 스냅샷에는 이전 커널의 정규 initcall 0–146 진입과 0–145 반환이 들어 있다. 같은 호출의 반환, 해당 장치 이름, 실물 PID 1, 리셋 원인은 미확인이다. ## 로더와 커널에서 함께 확인한 두 변경

| 항목 | 기존 후보 | 이번 호스트 빌드에서 검증한 값 |
| --- | --- | --- |
| Linux에 전달하는 부팅 인수 | 유니로더가 새 DT에 `rdinit=/init`만 기록 | `rdinit=/init cpuidle.off=1`. EL1·EL2로 시작한 두 대조에서 DT 초기화 후 Linux의 실제 `boot_command_line`을 읽었다. |
| 커널이 점유하는 물리 메모리 | `0x480000` | `0x490000`. arm64 Image 헤더의 크기와 최종 ELF의 `_end - _text`가 일치한다. 초기 페이지 테이블도 이 범위 안에 있다. 기존 고정값보다 64 KiB 크다. |
| 정규 initcall 표 | 153개, 지연 probe가 146번 | 159개, 지연 probe가 152번이다. 기존 실기 표식 해석에는 원래 153개 표를 사용했다. |

새 크기와 부팅 인수를 함께 적용한 ARM64 유니로더와 커널을 QEMU에서 실행했다. 펌웨어의 적재 위치 64곳, 순정 DT 6조합, EL1·EL2를 포함한 정상 74건이 Linux의 `unflatten_device_tree()` 반환까지 도달했다. 음성 대조 23건은 각각 예상 지점에서 거부됐다. 별도 비교에서 정상 74개 출력 DT가 입력의 활성 고정 예약, `no-map`과 동적 풀의 크기·정렬·배치 제약을 보존했다. 기본 보드 조합 하나의 고정 예약은 29개, 그중 `no-map`은 23개, 동적 풀은 13개다. 실물의 시동 시점 펌웨어 상태와 Linux가 정할 동적 풀의 실제 주소는 남는다.

순정 펌웨어가 입력 DT를 준비한 뒤 유니로더가 이를 받아 Linux용 출력 DT를 조립한다. 기존 커널은 `CONFIG_CPU_IDLE=n` 때문에 RPMh가 참조하는 PSCI 클러스터 도메인 공급자가 빠져 있었다. 호스트 빌드는 공급자를 포함하고, OSI를 지원하지 않는 PSCI 펌웨어에서 불필요한 모드 설정 호출을 건너뛰는 수정을 사용했다. QEMU에서 PC 모드 등록을 확인했다. 확인한 upstream master와 6.18.y 소스에는 종전 호출이 남아 있었다. ## RPMh의 두 대기와 부트루프 가설

가상 ARM64 기계에서 Linux의 실제 Command DB·RPMh RSC·레귤레이터 드라이버를 실행했다. 레지스터와 Command DB 데이터, 완료 인터럽트 도착은 실험 입력이다.

| 입력 | 관측 |
| --- | --- |
| Command DB 없음 | RSC가 `-EPROBE_DEFER`를 받았다. 첫 대기 안에서 같은 가상 RSC의 작업 스레드 재시도와 호출 복귀를 보았다. |
| Command DB magic 오류 | `-EINVAL`을 받고 첫 대기가 반환했다. |
| 유효한 모의 DB·레지스터와 완료 IRQ | RSC 자식의 레귤레이터가 초기화되고, 두 전원 요청 모두 실제 인터럽트 핸들러와 완료 콜백을 거쳤다. |
| 첫 동기 전원 요청에 완료 IRQ 보류 | 첫 번째와 두 번째 flush가 모두 반환했다. 별도로 실행 중이던 요청이 이후 10초 완료 대기에서 타임아웃됐다. |
| 활성 TCS 두 개, 완료 보류, 비동기 전원 요청 반복 | 같은 주소에서는 두 번째 제출, 서로 다른 주소에서는 세 번째 제출이 TCS를 기다리는 커널의 실제 `schedule()` 호출에 도달했다. 이 대기는 위의 10초 완료 대기에 진입하기 전이며 소스에 자체 제한 시간이 없다. 여기서 VM 측정을 끝냈다. |

실물의 마지막 표식만으로 장치 재시도, 전원 요청 대기, 워치독 리셋, 마지막 기록 손실을 구분할 수 없다. 원래 ELF에서 미사용 클럭 정리는 149번, 전원 도메인 정리는 150번, 레귤레이터 최종화는 151번이다. 어느 것도 마지막으로 확인된 146번보다 앞서지 않는다. 실제 구성은 `MODULES=n`이어서 일반 deferred-probe의 기본 지연 제한도 0이다. 순정 드라이버의 워치독 pet 9.36초, bark 11초, bite 여유 3초는 순정 소프트웨어가 설정하는 값이다. 후보 인계 당시 타이머가 가동 중이었는지는 알 수 없다. 이전 실기 판독은 바이트 수·앵커 수·검증된 스냅샷 수·선택한 비트맵을 보관했다. 리셋 사유 레지스터나 부팅별 시간 기록은 담겨 있지 않다. [Linux 드라이버 재시도](https://github.com/torvalds/linux/blob/v6.18/drivers/base/dd.c) · [RPMh 전송 제어](https://github.com/torvalds/linux/blob/v6.18/drivers/soc/qcom/rpmh-rsc.c)

## 작업 스레드의 진행 기록

두 가지 기록기를 각각 호스트 전용 커널에 빌드했다. 첫 설계는 프로세스 문맥의 뮤텍스로 PID 1과 작업 스레드의 사건을 한 스냅샷에 담는다. 잠금을 보유한 채 드라이버나 flush를 호출하지 않는다. 두 CPU를 기동한 VM에서 작업 스레드가 기록을 무효화한 뒤, 본문을 쓴 뒤, 서명을 게시한 뒤에 각각 실행을 중단했다. 세 경우 모두 이전 완성본을 판독했고 마지막 경우에는 새 완성본도 읽었다.

두 번째 설계는 기존 240바이트 범위에 80바이트 앵커와 생산자별 40바이트 슬롯 두 개씩을 배치한다. PID 1과 단일 deferred work는 서로의 슬롯이나 I/O 잠금을 공유하지 않는다. 각 기록은 순번, 부팅 경과 밀리초, 단계, 공급자 상태를 담고 실험 식별값과 BLAKE2s로 검증한다. 두 CPU의 Command DB 부재 대조에서 PID 1의 159번째 호출 반환과 작업 스레드의 RSC 진입·복귀 및 `-517`을 각 생산자의 슬롯에서 읽었다. 실제 ARM64가 남긴 기록으로 두 슬롯 쌍의 게시 도중 96개 바이트 변경 단계를 재생해 직전 완성본의 보존을 확인했다. 서로 다른 부팅의 슬롯을 결합하지 않는다. 순번이나 시간만으로 부트루프 횟수를 추정하지 않는다.

완료 IRQ를 넣은 두 CPU 대조 중 한 번은 호스트 GDB가 중단됐다. 해당 시도는 성공 근거에서 제외했다. 두 CPU 작업 스레드·중단 실험과 한 CPU의 완료 IRQ 대조는 별도로 통과했다. 실물의 Download 복귀 과정에서 새 형식이 보존되는지는 여전히 확인할 사항이다.

## USB 위의 SSH까지 검증한 범위

- 실기에 넣었던 `/init`을 변경하지 않고, 가상 UDC를 실제로 분리한 뒤 4초 후 등록했다. PID 1의 진입과 재등록 뒤 이번 빌드의 83바이트 ACM 배너 수신을 확인했다.
- 별도 ARM64 서버용 실험에서는 복합 ACM+NCM을 생성했다. 가상 호스트와 서버를 서로 다른 네트워크 네임스페이스에 놓고 Linux의 실제 `cdc_ncm`으로 HTTP 요청과 응답을 주고받으면서 ACM에서도 데이터를 읽었다. **ACM을 먼저 연결하면 제어 인터페이스 번호가 `00`, NCM을 먼저 연결하면 `02`였다.** 기존 S20+ 관측기는 `00`을 요구하므로 서버 후보가 관측기를 재사용하려면 ACM을 먼저 연결해야 한다.
- 같은 복합 USB에서 Debian trixie arm64의 Dropbear 서버와 클라이언트로 공개키 인증 SSH 명령을 실행해 예상 응답을 받았다. 미등록 클라이언트 키와 잘못 고정한 서버 키는 각각 거절됐다. Debian 서명 색인과 패키지 체크섬을 확인했고 키는 각 VM의 RAM에서만 생성했다. 첫 SSH 기록 중 콘솔 종료 문장이 나뉘어 전달된 경우 수집기가 일찍 종료했다. 줄 끝까지 기다리도록 고친 뒤 성공·실패 대조를 재검증했다. 이 결과의 범위는 RAM에서 부팅한 가상 네트워크 서비스까지다. y2q 실물의 SSH, 설치형 Debian과 재부팅 후 서비스 복귀는 미검증이다. [Debian arm64 Dropbear 패키지](https://packages.debian.org/trixie/arm64/dropbear-bin)

## 독립 검토와 종료

| 회차 | Opus와 Carbon의 판단 및 후속 조치 |
| --- | --- |
| 1 | 두 모델이 작업 스레드 표식, 전원 요청의 완료, 예약 메모리, 하드웨어 대조와 서버 선행조건을 제안했다. 표식 부재에서 실물 정지를 단정한 의견은 이전 실기 기록과 대조해 정정했다. |
| 2 | 두 모델 모두 추가 조사가 필요하다고 답했다. Opus의 시간·늦은 클럭 정리·번역 상태 지적을 최종 ELF, 시간 필드, SMMU 소스로 확인했다. Carbon의 다중 TCS 부족·기록 잠금·MUIC 지적을 실제 드라이버 대조, 독립 슬롯, 순정 소스로 확인했다. |
| 3 | Opus는 현재 자료로 실물 실패 가설을 더 판별할 호스트 실험이 없다고 결론냈다. Carbon은 진행 중이던 ACM+NCM 대조를 마치면 같은 결론이라고 답했다. 해당 대조는 두 연결 순서에서 모두 완료했다. |

실물에서 다음 관측 가치가 있는 것은 새 커널의 부팅 인수, PSCI 공급자와 RPMh의 등록 결과, 첫 대기 안에서 재시도한 장치·복귀 여부, PID 1과 USB 열거다. 3차 검토는 여기서 마쳤다. 이후 판독 실험을 재개했으며 휴대전화의 서버 운용 목표도 열려 있다.

## 원복 판독과 부트루프 귀속 재검토

동일한 후보가 반복 부팅할 때 한 회차의 기록이 다음 회차에 남을 수 있는지를 시험했다. 처음에는 QEMU 메모리에서 새 슬롯을 직접 해석하고, 기존 Android 필터는 과거 80바이트 형식으로 별도 검증했다. 새 40바이트 형식으로 원복 판독까지 연결하니 두 가지가 드러났다.

1. 이전 실기에 사용한 판독기는 실험 식별값이 붙은 80바이트 `Y2QSURV1`을 찾는다. 새 기록기는 40바이트 `HLP2`와 `HLW2`를 쓴다. 새 형식의 진행 기록 4개가 있는 2,097,136바이트 복귀 스냅샷에서 기존 필터는 **앵커 1개, 진행 기록 0개**를 반환했다. 이때 기존 파서의 `complete`는 앵커만으로도 나올 수 있다. 이 결과로 커널이 그 지점에 도달했는지를 판정할 수 없다.
2. 첫 QEMU 부팅에서 RSC 재시도를 발생시킨 뒤 로그 RAM을 보존해 동일 커널을 다시 시작했다. 둘째 부팅은 Command DB 오류로 작업 스레드 재시도가 0회임을 명령 단위로 확인했다. 그런데 둘째 부팅 뒤에도 첫째의 유효한 작업 슬롯 두 개가 같은 위치에 바이트 단위로 남았다. 둘째 부팅을 빈 로그로 시작한 대조에서는 작업 슬롯이 0개였다.

각 경우에 원본 Magisk 커널의 `sec_log_buf_init` 기계어를 실행해 공개될 직전 로그를 생성했다. RAM·커널 서비스는 호스트에서 모사했고, 그 바이트를 IYC2 ARM64 Toybox `od`와 Magisk BusyBox `awk`에 전달했다. 휴대전화에서 새 로그를 채취하지 않았다.

호스트용 대조 커널은 난수 생성기가 준비됐을 때 128비트 부팅 식별값을 앵커에 기록하고 각 슬롯의 무결성 검증에 반영한다. 잘못된 실험 키, 찢어진 앵커·슬롯, 떨어져 나온 슬롯, 일부만 남은 창, 서로 다른 두 부팅의 창을 검사했다. 한 슬롯이 손상된 경우에는 나머지 유효 슬롯이 살아남았다. 판독기는 온전한 앵커와 240바이트 창을 요구하므로 잘린 창은 증거 공백으로 남긴다.

난수 입력의 효과도 분리했다. 기존 유니로더 정상 출력 DT 74개 모두 `/chosen/rng-seed`가 없었다. 외부 시드를 주지 않은 QEMU에서는 난수 준비를 요구하는 시제품이 초기 앵커를 발행하지 않았다. 가상 펌웨어에 시드를 명시적으로 준 양성 대조에서 서로 다른 부팅 식별값이 작동했다. 이것만으로 y2q 실물의 초기 난수 상태를 알 수 없다. 별도 호스트 시제품은 난수가 준비되지 않았을 때 **해당 실험 중 어느 회차에선가 발생한 사건**으로만 기록한다. 부팅별 기록과 이 형식을 따로 집계한다. [Linux 6.18의 초기 DT 처리](https://github.com/torvalds/linux/blob/v6.18/drivers/of/fdt.c)

Opus 5.5와 Carbon Medium 모두 반례를 검토하고 이전의 포괄적인 H0 종료 판단을 철회했다. 이번에 구분한 것은 보존된 기록의 작성 범위다. 실물에서 마지막으로 입증된 146번 initcall의 첫 대기 호출 지점과 부트루프 원인 미확인은 그대로다. 새 판독기는 호스트 실험용이며 실제 Android 복구 실행기에는 연결하지 않았다. 비공개 재현 자료는 `workspace/private/analysis/s20plus-y2q-return-reader-20261127/`에 있다. 해당 디렉터리의 `evidence-index.json` SHA-256은 `d227fe085ad8ce05ae7ca9baa497459c6eb50efb323237d896de8eebb2ecaec0`다.

## 원복 실행기를 통한 호스트 통합 검증

실기에서 회수한 원래 stdout을 보관된 영수증과 대조해 다시 해석했다. 원래 Image의 정규 initcall 153개 중 146번은 `deferred_probe_initcall`이다. 커널은 PID 1 문맥에서 첫 `flush_work()` 호출 직전 표식까지 썼다. 사용자 공간의 `/init` 실행, 대기 반환, 재시도 장치 이름과 리셋 사유는 이 캡처에서 확인할 수 없다. 새 호스트 Image의 159개 initcall에서는 같은 함수가 152번이다. 두 번호는 각각의 Image와 심볼 표에 연결했다.

### 원복 때 실제로 읽히는 값

네트워크와 실기 USB를 차단한 호스트에서 기존 복귀 실행기의 `publish`, `acquire`, `allowed`, `derive`, `first_return`과 B0의 최종 JSON 발행 함수를 호출했다. 명령은 ARM64 QEMU 안에서 IYC2의 셸·Toybox와 보관된 Magisk BusyBox로 실행했다. 기기 속성, su 진입, 첫 복귀 부팅 ID, 전송·루팅 영수증과 잠금 해제는 실험용 입력이다. 기존 최종 판정 함수는 유효한 새 표식이 있어도 `NO_PROOF`를 냈다. 새 형식용 해석 결과를 별도로 저장하고 가상 실행의 최종 결과에는 실기 성공을 부여하지 않았다.

| 원복 때 읽힌 기록 | 판독할 수 있는 내용 |
| --- | --- |

원본 Magisk 커널의 ARM64 `sec_log_buf_write`, `sec_log_buf_init`, `sec_last_log_buf_read` 기계어를 실행했다. 메모리와 커널 서비스는 모사했다. 보존 링의 시작점을 옮긴 여섯 입력 모두에서 최대 2,097,136바이트를 32 KiB씩 읽어 원래 스냅샷과 대조했다. 마지막 바이트, EOF, 짧은 읽기와 사용자 복사 실패에서의 파일 위치도 확인했다. 오래된 로그가 밀려 앵커의 첫 바이트만 사라져도 뒤의 완성 슬롯은 어느 부팅 것인지 판별할 수 없었다.

### 실패와 재시도

호스트 수집 프로세스를 명령 시작 직후 종료한 경우, 두 번 재개해도 명령은 재실행되지 않았고 `capture_cut`이 남았다. 원시 영수증이 완성된 후와 증거 파일을 디렉터리에 연결하기 직전·직후에도 프로세스를 종료했다. 이 세 경우는 보존된 원시 바이트로 같은 결과를 재현했다. 프로세스 종료 실험에서 호스트 전원 차단 중 파일시스템의 내구성까지 검증하지는 않았다. stdout·stderr·의도·증거·첫 복귀 티켓을 별도 복제 사례에서 바꾸자 검증이 중단됐다. 97바이트 stdout과 1,025바이트 stderr는 각각 상한 초과로, 실제 120초를 넘긴 생산자는 시간 초과로 분류됐다.

### 유니로더와 장치 이름 대조

새 기록기가 들어간 ARM64 Image를 유니로더와 결합했다. 여섯 보드 DT와 소스 주소·메모리·CPU 조건을 포함한 QEMU 97개 사례를 다시 실행했다. 정상 입력 74건에서 새 Image가 실제로 받은 DT를 검증하고 `unflatten_device_tree()`가 반환했다. 잘못된 입력 23건은 예상한 거부 지점에서 멈췄다. 이 결과의 범위는 에뮬레이터에서 커널이 기기 트리를 펼친 단계까지다.

작업 기록은 장치 이름 전체에서 계산한 32비트 값, 해당 호출의 진입·반환 구분, 직전 반환 장치 값을 담는다. 새 ELF의 `h0_worker`와 기록 인코더를 실제 ARM64 명령으로 실행해 여섯 보드 DT의 직접 SoC 장치 이름 69개와 구분 문자가 있는 두 이름을 검사했다. 시간과 최종 RAM 쓰기는 모사했다. QEMU의 RSC 이름은 `52000000.rsc`, y2q DT에서 산출한 이름은 `18200000.rsc`이며 기록 값도 서로 달랐다. 선정한 69개 이름 사이에는 충돌이 없었다. 이 사전은 동적으로 생성되는 모든 장치 이름을 포함하지 않는다. 작업 함수의 반환 표식은 해당 드라이버의 초기화 성공을 보증하지 않는다.

### 최대 크기 로그와 독립 검토

최대 크기 로그에 고정 시드 난수 데이터를 채워 한 예에는 버퍼 경계에 유효한 창을 넣고 다른 예에는 넣지 않았다. Opus와 Gemini Carbon Medium의 지적에 따라 유효한 고정 식별값 창으로 로그를 가득 채운 경우도 비교했다. 초기 판독기는 이 입력에서 가상 머신의 116초 제한에 걸렸다. 호스트용 수정본은 검증한 `od` 행을 최대 256개까지 캐시하고, 표식 후보를 가리키는 바이트 패턴이 256회보다 많이 검출되면 개별 슬롯 해석을 중단한다. 남은 입력 형식과 전체 길이 및 복귀 부팅 ID까지 확인한 뒤 표본 없는 `signature_limit`을 반환한다. 이때 개별 표식 수와 내용은 판정할 수 없다.

## 새 후보의 실기 준비

## 여러 창에 남은 호출 직전과 첫 대기 반환의 호스트 판독

[호스트 판독기](../../workspace/public/src/mainline/s20plus_y2q_h0/deferred_presence_h0.py)는 후보 nonce에 맞는 R4 앵커와 각 슬롯의 다이제스트, 생산자 위치, 순번 범위와 홀짝을 확인한다. 고정 식별값 또는 임의 epoch의 완전한 창마다 양쪽 슬롯을 개별 판독한다. 작업 스레드의 phase 1은 `bus_probe_device(dev)` 호출 직전, phase 2는 그 호출이 반환한 뒤의 장치 이름 해시를 각각 집합에 넣는다. ## TLMM 재시도 원인 후보와 첫 flush 구간의 다음 실험

11월 28일 호스트에서 실제 후보의 빌드 Image와 유니로더에 넘긴 Image의 SHA-256이 모두 `1219c5ab080ae32a1ec820777609b4eb53a1f5d822cc85ddfeda6fc2df61f73b`임을 확인했다. 보관된 `kernel-build/vmlinux`의 ARM64 호출 명령, `System.map`, 최종 설정과 보드 6종 호스트 인계의 합성 DTB를 대조했다. 여섯 출력 DTB는 동일했다(SHA-256 `0e2178c5b30baac8185c6be79d0175f3e9414a4fee132b5439f38c12cd76575e`). 이 DT는 모델링된 인계의 출력이며 후보 실행 당시 실물에서 읽어낸 FDT는 없다. 근거 파일은 `workspace/private/analysis/s20plus-y2q-deferred-worker-f1/`의 `candidate/linux-6.18/`, `candidate/kernel-build/`, `independent-h0/matrix-*/board-*/output.dtb`에 있다.

**의존성과 등록 순서.** TLMM 노드 `/soc@0/pinctrl@f100000`의 compatible은 `qcom,sm8250-pinctrl`이다. 일반 요약 인터럽트는 루트에서 상속한 GICv3(phandle 1)의 SPI 208, level-high다. 별도의 `wakeup-parent`(phandle 117)는 `interrupt-controller@b220000`의 Qualcomm PDC IRQ 컨트롤러를 가리킨다. PDC의 인터럽트 부모도 같은 GIC이며, PDC에는 드라이버가 요구하는 세 셀씩 네 구간의 `qcom,pdc-ranges`가 있다. TLMM의 `gpio-ranges`는 자기 자신을 가리킨다. TLMM에 직접 지정된 clocks·power-domains 속성은 없다. PINCTRL_SM8250, PINCTRL_MSM, QCOM_PDC, ARM_GIC_V3는 모두 내장이다. 합성 부트 인자는 `rdinit=/init cpuidle.off=1`로 fw_devlink 기본 RPM 모드를 바꾸지 않는다.

정규 initcall 표의 0부터 센 순번은 TLMM 드라이버 등록 **43**, 기본 OF 플랫폼 장치 생성 **47**, PDC 드라이버 등록 **113**, `deferred_probe_initcall` **152**다. 코어가 처음 TLMM을 매칭할 수 있는 시점에 PDC 장치는 아직 드라이버와 결합하지 않았을 가능성이 높다. 드라이버가 나중에 등록되더라도 `driver_deferred_probe_trigger()`는 활성화 전에는 즉시 반환하므로 첫 late flush에서 앞서 보류된 TLMM을 보는 것은 정상 진행과도 양립한다.

| --- | --- | --- |

`drivers/base/dd.c`에서 워커 표식은 `bus_probe_device(dev)`의 바로 앞과 뒤다. 코어는 드라이버 내부 오류의 부호를 뒤집을 수 있어 대기열 추가 경로는 ±EPROBE_DEFER를 모두 처리한다. `bus_probe_device`는 void이며, 그 반환만으로 드라이버 바인딩 성공을 알 수 없다. 기존 첫 flush 표식 308과 309 사이에는 첫 `flush_work`가 있고 두 번째 호출은 310과 311 사이에 있다. 트리거가 308보다 먼저 워커를 큐에 넣으므로 기존 TLMM 워커 표식은 PID 1의 배리어 대기 진입을 입증하지 않는다. 9개 창의 서로 다른 장치 표식을 이어 붙일 수도 없다.

**선택한 다음 실험.** 같은 DT·부트 인자·드라이버 순서를 유지한 관측 전용 후보 하나를 설계한다. (1) 정확한 TLMM 장치에서 최초 시도와 첫 트리거 후 재시도의 공급자 검사 결과를 구분하고, 보류 시 기존 오류 분기의 공급자(PDC/GIC/기타)를 기록한다. 공급자 결합에 의한 큐 추가 요청과 실제 신규 삽입을 구분한다. (2) TLMM 콜백 진입, 일반 IRQ 조회 결과, wakeup 도메인 검색의 성공/부재, 콜백 반환값과 PDC 도메인 게시 지점을 구분한다. (3) PID 1에서 첫 트리거 직전에 관측을 열고 첫 호출의 정확한 work 포인터에 한정하여 `start_flush_work`의 배리어 설치 여부, `wait_for_completion(&barr.done)` 직전·직후, 바깥 `flush_work` 반환과 bool 결과를 식별한다. 배리어 없이 빠르게 반환하는 경로도 별도로 기록한다. 해당 워커의 TLMM 호출 직후와 워커 루프 종료는 독립 사건으로 둔다.

H0 선행 대조는 공급자 차단/콜백 내부 보류/정상 반환, 배리어 없는 반환/배리어 대기 완료를 각각 알려진 입력에서 구분하고, 다음 부팅의 오래된 슬롯 및 표식 유실을 섞어도 인과관계를 합성하지 않는 것이다. 누적 비트와 제한된 상태 코드로 생산자별 진행을 보존하고 기존 쓰기 범위·횟수 안에서 가능한지 먼저 검증한다. 이 자료에서 PDC 미준비가 확인되더라도 첫 대기 반환이 관측되면 조사 위치는 대기 이후로 이동한다. 대기 진입만 있고 반환 증거가 없으면 확인 범위는 대기 직전까지이며, TLMM 정지나 리셋 원인을 단정하지 않는다. 이번 작업은 설계 선택까지이며 새 후보 제작·기기 명령은 없었다.

## 11월 28일 TLMM 및 첫 flush 관측 후보의 호스트 검증

전용 후보의 boot-only AP SHA-256은 `c5ebf1301144415a1b67b5607d891de27f82cac092adab37b01513570f2b7aa8`이며 ARM64 Image는 `af09cb6e7e10d0a0d5cca53c8da14264bac790e2e8f9fb12ff71fa758de0b7a0`이다. AP의 단일 `boot.img.lz4`를 독립적으로 풀어 64 MiB 부트 이미지에서 실제 유니로더·커널·램디스크와 이전 삼성 외부 DT를 대조했다. 빌드 구성, y2q 보드 DT, 전체 initcall 173개의 함수 순서와 레벨 경계(정규 initcall 159개)가 이전 후보와 일치한다. 새 빌드 식별값을 넣은 램디스크는 압축 패딩으로 원래 길이를 유지했다. 여섯 보드 입력을 실제 후보 유니로더에 넣고 QEMU에서 꺼낸 여섯 DT가 각각 이전 출력과 바이트 단위로 일치했다. 잘못된 FDT 대조는 커널 진입 전 거부됐다.

[계측 패치](../../workspace/public/src/mainline/s20plus_y2q_h0/tlmm-flush-hooks.patch)는 커널의 기존 반환·분기값을 관측한다. 코어의 잠금 구간에서는 비트만 기록한다. 정확한 TLMM 이름·compatible을 요구하고 첫 트리거 전 PID 1 관측과 해당 work 항목 실행 문맥의 관측을 분리한다. 각 문맥의 첫 콜백 반환 여부와 부호 있는 반환값은 한 원자적 값으로 보존한다. 기존 256바이트 창 안에서 앵커와 두 생산자의 슬롯이 240바이트를 쓰며 슬롯 게시 시도는 생산자당 최대 32회다. 구간별 누적 비트와 반환 영수증은 인과관계나 워커 호출 횟수를 복원하지 않는다.

## 11월 28일 TLMM wakeup 도메인 이후의 GPIO 등록 경로

실기에서 회수한 마지막 TLMM 드라이버 내부 표식은 `wake_found`다. 이 표식은 `irq_find_matching_host(..., DOMAIN_BUS_WAKEUP)`가 도메인을 찾았다는 뜻이다. 실기에 사용한 Linux 6.18 소스와 전달 DT에서 이후 경로를 추적했다.

1. `msm_gpio_init()`은 PDC 도메인의 직접 wake IRQ 처리 여부를 조회해 해당 GPIO를 표시하고, 부모 IRQ 배열을 할당한 뒤 `devm_gpiochip_add_data()`를 호출한다. 부모 배열 할당이 실패하면 `-ENOMEM`으로 돌아간다.
2. GPIO 코어의 `gpiochip_add_data_with_key()`는 칩과 라인 기술자, 유효 마스크를 마련한다. 라인 방향 초기화 루프는 유효 라인마다 `msm_gpio_get_direction()`을 통해 해당 타일의 제어 레지스터를 읽는다. SM8250의 GPIO 수는 181개이며 y2q DT에서 40–43번은 예약돼 있다. 후보는 기존 루프의 시작과 끝에서 한 번씩 관측한다.
3. `of_gpiochip_add()`는 이 DT의 자기 TLMM을 가리키는 `gpio-ranges`를 해석하고 GPIO hog를 스캔한다. 이어 GPIO 코어가 IRQ 칩을 등록한다. 부모 도메인으로 계층형 IRQ 도메인을 만들고 부모 IRQ에 연결 핸들러를 설치한다. 초기화 상태에 따라 GPIO 장치 등록도 수행한다. 관리형 래퍼는 코어 등록 성공 뒤 해제 동작을 등록한다.
4. 관리형 등록이 실패하면 반환 코드가 TLMM 호출자까지 전달된다. 성공하면 이 DT에서는 `gpio-ranges`가 있으므로 MSM의 수동 범위 추가 분기를 건너뛰고, `msm_pinctrl_probe()`가 드라이버 데이터를 저장한 후 0을 반환한다. 새 후보는 `platform_probe()`의 실제 `drv->probe(dev)` 호출 **직후**에 선택된 TLMM의 첫 콜백 반환값을 기록한다. 드라이버 코어의 후속 바인딩 성공은 별도 사건이다.

### 관측 후보와 호스트 결과

후보는 기존 240바이트 창 안에서 GPIO 등록 호출, 방향 루프 양끝, OF 처리 성공, IRQ 칩 등록 전후, 관리형 등록 성공·실패, 드라이버 데이터 저장을 구분한다. 선택된 워커의 콜백 반환값, 첫 `wait_for_completion(&barr.done)` 직후, 바깥 `flush_work()` 반환을 각각 판독한다. 대기 경로의 필수 비트는 인증된 한 슬롯에 함께 있어야 한다. 서로 다른 창에서 회수한 호출 순서나 같은 시도라는 관계는 복원하지 않는다.

| 같은 ARM64 Image의 QEMU 대조 | 선택된 TLMM 워커에서 회수한 결과 | 첫 flush 결과 |
| --- | --- | --- |
| 정상 GPIO 등록 | 방향 루프와 OF 처리, IRQ 칩·GPIO 등록, 드라이버 데이터 저장을 거쳐 호출자에서 0을 회수 | 콜백 반환 직후에는 대기 완료 표식이 없었다. 실제 대기 반환 후 `__flush_work()` 안에서 잡은 RAM에는 대기 완료만 추가됐다. 바깥 호출 뒤에는 true 반환도 확인했다. |

QEMU 모델 변경은 기능 대조용 virt DT에만 적용했다. 배포 후보는 직전 실기 후보와 커널 설정, 보드 DT, 펌웨어 입력 6가지에서 캡처한 전달 DT 전체, initcall 173개의 순서 및 레벨 경계가 일치했다. 완성된 AP의 유일한 엔트리 `boot.img.lz4`를 풀어 테스트한 Image가 포함된 것을 확인했다. 동일 슬롯 내 모순, 분할 슬롯, 오래된 epoch와 손상 슬롯을 검사했고, RAM 캡처 11개 모두 240바이트 창 밖은 초기값과 일치했다. 호스트 독립 검토에서 지적한 대기 직후 중단 위치 및 모순 비트 판독을 수정해 재검증했다. 최초 DT 검사에 사용한 이전 스크립트는 `/chosen`에 idle-off 인수가 없는 구성을 기대해 중단됐다. 실기 선행 후보의 검사기로 6개 입력을 모두 검증하고 DT 바이트도 직접 비교했다. TLMM이 비활성인 대조는 첫 flush 뒤의 309 지점에서 판정해 두 번째 flush의 대기를 제외했다.
