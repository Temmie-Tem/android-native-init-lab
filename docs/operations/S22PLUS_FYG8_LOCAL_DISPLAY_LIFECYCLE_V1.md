# S22+ local display lifecycle V1

Status: **H0 implementation independently reviewed PASS_GO; no live activation.**
Target: SM-S906N / g0q / S906NKSS7FYG8. This is refactor phase1B.
The consumed [console HUD V1](S22PLUS_FYG8_BOOT_HUD_V1.md) and its successor
records remain unchanged. Selecting this source profile grants no device effect.

## Start boundary and ownership

The explicit `local-display-v1` source profile starts local display ownership at
the existing native publication boundary, after the platform's fixed bootstrap
and USB preparation, before kernel boot-ID read and host OPEN/AUTH. The ordinary
`console-v1` profile retains exact 1A/P383 generated bytes. This unit separates
host authentication from local display; it does not move the earlier kernel,
module, gadget or Type-C bootstrap stages. No display proves those earlier stages.

PID1 owns one local lifecycle state and the existing renderer/collector children.
It creates the fixed `/s22-root-work` RAM directory/mount once, using the existing
numeric-root and tmpfs constraints. A failed creation is retained, not retried or
accepted as an existing foreign directory. HUD failure does not grant commands or
block an otherwise healthy console. Children close unrelated inherited FDs as
before. Only the same native PID1 may service or close its lifecycle state.

The display start is independent of receiving OPEN/AUTH. State updates and child
housekeeping are serviced during bounded protocol I/O waits and console ticks.
No daemon, proxy, second TTY owner or display restart is added. Blocking kernel
calls or a stalled PID1 remain outside this cooperative service guarantee; the
existing renderer stale-parent rejection remains in force.

## Authentication, preparation and timing

EXEC, STATUS, CANCEL and CONTROL retain their authenticated nonce/sequence rules.
No unsolicited USB transmission is added before a peer's first OPEN byte. Before
any OPEN byte, zero-byte reads and `EIO`, `ENODEV` or `EPIPE` may represent an
absent peer on the same nonblocking FD and are waited for within the same read
deadline. `EAGAIN`/`EINTR` keep their existing wait behavior. Other errors fail;
the FD is never reopened. After a byte is consumed,
transport/framing/authentication failure terminates the attempt without replay.

- Existing per-read handshake deadline: 30 seconds; total unauthenticated phase
  also has a fixed 120-second ceiling from local lifecycle start.
- Console command/session limits remain unchanged: the ten-minute session begins
  at console entry, and neither command nor state update renews it.
- Local display ownership has a fixed 15-minute ceiling from its first start.
  Display expiry alone does not renew or expand console authority.
- Authentication/runtime failure or ordinary console expiry publishes one local
  terminal state and services it for at most five seconds, capped by the local
  deadline. No new authentication or command is accepted during that hold.
- Accepted CONTROL is special: after its authenticated ACK is completely flushed,
  PID1 stops local updates, signals each still-owned child at most once and uses
  the existing single Download syscall. It never waits for DRM cleanup or repeats
  CONTROL. Kernel-stall/physical recovery requirements remain unchanged.

The root-work directory/mount now precedes authentication. Authenticated progress
stages61/62 therefore report the cached boot-local syscall results, not fresh
mkdir/mount calls at frame emission time. Stage60 still validates current numeric
credentials. A future activation must bind this profile and provenance explicitly;
old stage frames alone cannot establish contemporaneous inner-syscall timing.
The wire layout need not change, but its source/profile binding is essential.

## Local states and evidence

The existing 40-byte run/sequence/monotonic snapshot keeps READY0, BUSY1 and
BLOCKED2. The local-display profile additionally defines WAIT_AUTH3,
AUTH_FAILED4, EXPIRED5, PREPARING6, RUNTIME_FAILED7 and CLOSING8. Its renderer
accepts and labels exactly that set. The console-v1 renderer remains limited to
its original states. No local state or visible pixel is authentication proof.
Boot-ID/setup failures use RUNTIME_FAILED, independently of authentication. The
120-second admission check runs again after AUTH validation and immediately
before the authenticated state is entered.

The local renderer and its GEM-accounting reader allow 916 frames: 900 ordinary
one-second updates plus 16 reserved lifecycle transitions. Ordinary command state
changes retain the one-second rate limit. Collector/gauge producer and consumer
limits remain 601 samples; late metrics become STALE/N/A through the existing
freshness checks. The default renderer/GEM limit remains 601.

The local RAM HUD log is capped at 1,048,576 bytes inside the unchanged 64MiB
tmpfs; the default profile remains 262,144 bytes. A conservative fixed-output
bound is `916*1024 + 8*1152 + 32*128 + 32768 + 32768 = 1,016,832` bytes: frame
records, gauge diagnostics, GEM records, the existing one-shot kernel-log failure
output, and bounded startup/failure/exit records. The actual current maximum
HUD_FRAME format is 483 bytes. No collector count or kernel-log allowance is
expanded. One 512-byte nonblocking drain per tick and existing overflow/short-write
stops remain unchanged. Capacity does not establish lossless diagnostics.

Local startup, child creation, update publication, matched DRM flip and physical
visibility remain distinct evidence. The renderer keeps the existing run/sequence,
freshness, nonblocking IPC and immutable-buffer/retirement checks. Errors may
leave a stale physical frame; a stopped image is not current native health.
Fixed RAM logs are bounded; terminal cleanup closes owned IPC/log FDs and uses
nonblocking exact-child reaping only. A live or uninterruptible child is not
reported as successfully reaped merely because a signal was attempted.

## H0 completion and future use

Required checks exercise the actual generated production helper with absent,
delayed, malformed and incorrect authentication; terminal hold/deadline and
no-reentry; unchanged command/output/cancellation/CONTROL behavior; HUD/collector
failure or stall; and the actual renderer's new-state/freshness boundaries.
New numeric syscalls are checked against the exact target UAPI and representative
ARM64 behavior. Cross-compilation and host fixtures retain their stated limits.

The current bootstrap envelope must join the early local start to its real
publication entry; testing only a standalone helper is insufficient. Static
ARM64 helper/renderer builds and a generated source join are required. This H0
unit produces no READY manifest or flash authorization, allocates no live
candidate, and does not repair the separate host USB inventory race. Independent
review covers changed lifecycle/protocol/profile/bootstrap interactions before
this capability is called qualified. Live adoption requires its own fresh
artifact/source/target binding under the existing contracts.

The frozen P381 HUD observer accepts only console states0..2 and remains
unchanged. The separate [phase1C adapter](../reports/S22PLUS_FYG8_LOCAL_DISPLAY_OBSERVER_1C_H0_2026-09-10.md)
supplies compatible H0 observation on an owner's existing source-bound IO.
Fixed native health/idle STATUS precede optional HUD collection. A remaining
budget check can omit HUD and proceed to owned CONTROL; display failures never
provide health evidence. Raw replay checks the exact selected request sequence,
and the profile records cached stages61/62. This is not a live owner activation;
future adoption must bind the full platform/bootstrap/IO closure and artifacts.

Implementation, source-bound review and H0 evidence are recorded in the
[phase1B report](../reports/S22PLUS_FYG8_LOCAL_DISPLAY_REFACTOR_1B_H0_2026-09-10.md).
