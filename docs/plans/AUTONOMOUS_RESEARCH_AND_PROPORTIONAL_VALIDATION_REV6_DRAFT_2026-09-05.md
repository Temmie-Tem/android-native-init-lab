# 자율 연구와 비례 검증: Revision 6 개정안과 적용 기록

Date: 2026-09-05
Status: **APPLIED H0 POLICY / INDEPENDENT PASS_GO / TARGET AUTONOMOUS F1 NOT ACTIVE**

이 문서는 사용자와 합의한 설계·이력 검토와 적용 결과를 보존한다. 현재 공통
계약은 [AGENTS.md](../../AGENTS.md) Revision 6이며, 정확한 적용 범위는 9절에
기록한다. 1–8절의 제안과 검토 시점 기록은 독립된 실행 권한이 아니다.
이번 변경은 기기 실행 승인, 자율 F1 활성화, 기존 실행의 재개 또는 소비된
후보의 재실행을 허용하지 않는다. 실행 코드, 승인, 저널과 가드는 변경하지 않았다.

## 1. 개정 목표

- 에이전트가 통제와 복구를 수행할 수 있는 승인된 연구 범위에서는
  Download 진입, boot-only 플래시, 테스트, 롤백, 최종 상태 확인까지 자율화한다.
- 매 후보의 기계적 검증은 유지하되, 같은 연구 범위의 후보마다 사람의 승인,
  새 정책, 실행기 복제, 독립 아키텍처 검토를 반복하지 않는다.
- 호스트 개발과 검증은 변경 범위에 비례시키고, 완료 기준을 충족하면 끝낸다.
  개정은 기존 요구의 교체와 통합을 우선하며 새 관리 프레임워크를 요구하지 않는다.

## 2. AGENTS 공통 F1 참석 규칙의 제안 문구

> 기본 F1은 참석 방식으로 수행한다. 정확한 대상 계약이 검토된 자동 제어·복구
> 범위를 활성화한 경우, 사용자는 하나의 유한한 연구 세션에 대해 그 범위 안의
> 후보 생성, 검증, Download 진입, boot-only 플래시, 관측, 롤백과 최종 건강
> 확인을 승인할 수 있다. 이 범위의 후속 후보에는 새로운 사람의 승인을 요구하지
> 않는다. 실행기는 각 후보의 정확한 산출물과 현재 기기 상태를 실행 전에 바인딩한다.
> 물리 개입이 필요하거나, 영구 손상 위험 또는 복구 경로의 손실·변경이 예상되면
> 해당 전환 전에 중단한다. 예상하지 못한 제어 상실 이후에는 사전 승인된 복구만
> 수행하며, 자동 복구가 불가능하면 상태를 보존하고 물리 개입을 요청한다.

이 문구는 기존 `F1 is never unattended`와 참석·후보별 승인 규정을 명시적으로
개정하는 제안이다. 현재 규칙의 예외를 암묵적으로 추론하는 문구가 아니다.

## 3. 자율 F1의 승인 범위와 자동 복구 조건

1. 세션은 정확한 대상, 허용된 후보 변경 범위, 실행기·전송 도구·관측 방식,
   정확한 rollback, 시간·후보 횟수 한도를 지정한다. 한도는 기존 세션 기록과
   저널로 관리하며, 에이전트가 스스로 갱신하거나 초기화하지 않는다.
2. 후보를 미리 전부 열거할 필요는 없다. 세션에서 승인한 변경 범위 안의 새 후보를
   에이전트가 만들고 검증할 수 있다. 새 권한, 파티션, 실행·복구 방식 또는
   자동 복구를 무효화할 수 있는 변경은 그 범위를 벗어난다.
3. 현재 연결 가능 여부만으로 자동 복구 가능성을 판단하지 않는다. 대상에 맞는
   복구 근거는 정상 경로뿐 아니라 허용된 실험의 실패 경로를 포함해야 한다.
   후보 userspace의 응답에만 의존하는 복구는 그 userspace가 멈출 수 있는
   실험의 자동 복구 근거가 아니다. 부팅 실패·제어 채널 상실이 가능한 후보는
   그 실패에서도 도달 가능한 복구 수단이 검증된 범위에서만 자율 실행한다.
4. Download 진입과 복귀는 그 대상의 검토된 명령·전송 경로만 사용한다.
   버튼 조작이나 케이블 재연결이 필요한 알려진 경로는 참석 경로로 분류한다.
   호스트 테스트, 문서 또는 정상 재부팅만으로 실제 실패 복구를 증명하지 않는다.
5. 각 실행 전에는 정확한 기기·건강 상태·복구 수단과 candidate/rollback의
   실제 바이트·크기·boot-only 구성을 확인한다. 승인 후 산출물이 바뀌면 그 후보의
   바인딩을 새로 만든다. 관계없는 문서나 다른 대상의 변경으로 준비 전체를
   무효화하지 않도록 실제 실행 의존성만 바인딩한다.
6. 이미 시작한 실행의 롤백·관측·최종 건강 확인에 필요한 한도는 미리 확보한다.
   세션 만료는 새 실험을 막지만 승인된 복구를 막지 않는다. 최종 건강과 실행
   종료가 확인된 뒤에만 다음 후보를 시작한다.

boot-only, 대상 격리, 금지 파티션·명령, 비공개 증거, 효과 전 저널 기록과
후보 재실행 금지는 유지한다. F2 및 R1의 권한은 이 F1 개정에서 확장하지 않는다.
과거 소비된 후보, 불확실한 전송, 가드와 승인 기록은 재사용·초기화하지 않는다.

## 4. 실행과 실패 처리

정상 경로는 기존 실행기에서 다음 순서로 이어진다.

`현재 상태 확인 -> 후보 검증 -> Download 진입 -> 플래시 -> 테스트 -> 롤백 -> 건강 확인 -> 다음 후보`

| 상황 | 기본 처리 |
| --- | --- |
| 호스트 빌드·파서·테스트 오류 | 같은 작업 범위에서 수정하고 관련 검증을 반복한다. 실패 횟수만으로 연구 전체를 중단하지 않는다. |
| 같은 시도에 새 근거가 없거나 자원 한도 소진 | 해당 접근을 중단하고 근거와 남은 선택지를 보고한다. |
| 정상적으로 종료된 실험의 음성·미증명 결과 | 결과를 그대로 보존한다. 롤백·건강 확인이 끝났고 새 위험이 없다면 승인 범위의 다음 후보로 진행한다. |
| 전송·기기 효과 발생 여부 불명확 | 해당 효과를 반복하지 않는다. 기존 저널의 관측·승인된 복구만 이어간다. |
| 보고서 저장·호스트 출력 실패 | 원시 증거와 저널에서 재처리한다. 기기 동작을 다시 요구하지 않는다. |
| 예상하지 못한 제어 상실 또는 복구 불확실성 | 새 후보를 중단한다. 사전 승인된 자동 복구가 불가능하면 물리 개입을 요청하고 호스트 분석은 계속한다. |

설명되지 않은 전송·복구 사고를 단순한 실험 음성 결과로 분류하지 않는다.
연구 증명의 불확실성과 기기 안전 상태의 불확실성을 별도로 기록한다.

## 5. 개발 속도와 비례 검증

- 시작할 때 작업 범위와 완료 기준을 짧게 정한다. 필요하지 않은 전체 재조사,
  주변 리팩터링, 미래 요구만을 위한 일반화는 하지 않는다.
- 과거 보고서의 결함을 현재 작업 목록으로 옮기기 전에 현재 소스와 실제 실행된
  진입 경로를 확인한다. 실행되지 않은 함수나 아직 재현하지 않은 가설만으로
  원인을 확정하거나 새 필수 검증을 만들지 않는다.
- 기존 도구로 끝낼 수 있으면 재사용한다. 일회성 작업은 일회성으로 처리하고,
  반복 사용이 확인된 부분만 공통화한다. 후보별 실행기·검증기 복제를 기본으로 삼지 않는다.
  동일한 등록·인코딩·결과 처리 규칙을 여러 곳에 수작업으로 복사하지 않는다.
  실제 반복 결함은 기존 공통 경로에서 고치며, 정확한 허용 목록은 유지한다.
- 변경된 기능과 실제 실패 경로를 검증한다. 통과한 동일 소스·입력 검증은 새 근거
  없이 반복하지 않는다. 빌드 입력이 같으면 산출물을 재사용하되 실제 전송 바이트와
  변하는 기기 상태의 실행 직전 확인은 생략하지 않는다.
  준비 산출물이 실제 실행 분기·관측기·결과 재열기로 연결되는 대표 경로를
  호스트에서 확인한다. 실제 경로와 다른 helper의 테스트 수로 이를 대신하지 않는다.
- 코드와 무관한 문서 변경은 코드 재빌드나 후보 재준비 사유가 아니다.
  관측기만 바뀌면 해당 관측 경로를 재검증한다. 후보 바이트 변경에는 후보 검증,
  실행·복구 경계 변경에는 관련 안전 회귀와 독립 검토를 적용한다.
  전체 파일 수, 누적 이력 건수, 다른 대상의 비관련 변경은 실행 정체성이 아니다.
  현재 이를 바인딩하는 코드가 있다면 의존성을 검토해 분리하며, 기존 검사를
  임의로 건너뛰지 않는다. 운영 계약의 의미 변경은 계속 검토 대상이다.
- 테스트는 고정 fixture와 동작 불변식을 기준으로 한다. 계속 증가하는 실제
  원장의 전체 건수나 현재 활성 상태를 정답 상수로 고정하지 않는다.
  특정 역사 시점을 재현하는 테스트는 입력 시점까지 고정하고 그 범위를 명시한다.
  활성화 기능은 동일한 검토 대상 안에서 비활성·활성 상태를 모두 시험할 수 있게 한다.
- 준비, 활성화, 후보 소비, 복구, 종료 상태를 구분한다. 정상 전환이 만든 파일을
  이유로 앞 단계의 부재 조건을 다시 요구하지 않는다. 각 단계에는 그 단계의
  증거와 의존성만 요구한다. 현재 안전 상태 확인과 소비된 효과의 재실행 금지는 유지한다.
- 검토된 실행 코드와 위험 가정이 그대로면 기존 검토를 재사용한다.
  새로운 후보 데이터나 실험 번호만으로 아키텍처 검토를 반복하지 않는다.
  검토는 현재 실행 경로와 명시된 위협 모델을 기준으로 한다. 범위 밖의 가정은
  자동 필수 작업으로 만들지 않는다. 실제 새 위험이 확인되면 해당 범위를 중단하고
  검토 범위를 갱신한다. 검토 완료 항목은 새 근거 없이 다시 열지 않는다.
- 새 검증·절차에는 막는 실제 실패와 적용 범위를 설명할 수 있어야 한다.
  근거는 기존 변경 설명에 남기고, 이를 위한 별도 승인 계층은 만들지 않는다.
  별도 daemon·proxy·권한 계층을 도입할 때는 기존 전송 도구의 장치 점유와
  정상 준비·복구를 방해하는지도 확인한다. 기존 도구로 해결되는 경우 재사용한다.
- 정상 반복은 기존 저널·구조화된 결과·간결한 상태 갱신으로 끝낸다.
  별도 보고서는 새 성과, 사고, 복구 이탈, 설명이 필요한 모호한 결과에 한정한다.
  실패 경로의 원시 증거는 기존 대상별 capture/privacy 허용 범위 안에서만
  결과 해석·직렬화 실패에도 보존한다. digest-only 경계나 허용 수집량은 확대하지 않는다. 완료된 실행의
  재검토에 필요한 소스 버전과 증거 위치는 기존 종료 기록에 남긴다.
- 임시 제한은 기존 계약의 해제 조건을 충족하면 제거한다. 완료 조건을 충족한
  작업을 검증 수나 문서 수를 늘리기 위해 계속 확장하지 않는다.
  과거 검토 항목은 현재 경로의 미해결 위험, 명시적으로 해결된 항목,
  폐기된 경로의 항목을 구분한다. 다른 제목의 PASS를 자동으로 해결 근거로
  삼거나, 반대로 관계없는 과거 미해결 건수를 모든 후속 작업의 장벽으로 삼지 않는다.

## 8. AGENTS 반영 우선순위

1. **즉시 개정 후보:** 호스트 첫 실패 중단 규칙을 교체하고, 위 5절의 범위 기반
   검증·실제 경로 확인·안정된 테스트 입력 원칙을 Development/Review에 통합한다.
   별도의 체크리스트·매니페스트·daemon을 추가하지 않는다.
2. **다음 작은 코드 개선:** 누적 원장 숫자 테스트의 입력을 고정하고,
   후보 등록의 중복 선언을 기존 구조 안에서 줄인다. 후자는 실행 경로 변경이므로
   관련 안전 검토를 거쳐야 하며, 정책 조사와 함께 즉석에서 수정하지 않는다.
3. **수리 완료 사항은 보존:** P319 census·runtime binding, P0 전용 ADB 제거,
   A90 역할별 준비, 공유 결과 publisher는 재작업할 버그 목록이 아니다.
   필요한 원칙만 공통 계약에 일반화하고 기존 실험의 결과는 유지한다.
4. **정책 이력 정리:** `bf6486edd1`의 검토 재사용 원칙은 현재 AGENTS에도 남아 있다.
   `7738655683`의 간결한 routine 기록은 퇴역 trial 안의 역사적 선례이므로
   승인 면제 등 당시 권한과 함께 복원하지 않는다. 현재 계약에 남은 trial 참조를
   정리하고, 과거 미해결 review는 실제 적용 범위에 따라 처리한다.

[P319 미해결 검토 감사](../reports/S22PLUS_FYG8_P319_OPEN_REVIEW_OBLIGATION_AUDIT_2026-09-02.md)는
검토 제목과 범위가 달라 이미 살펴본 코드도 미해결로 남을 수 있음을 보여 준다.
이것은 미해결 항목을 자동 면제할 근거가 아니다. 현재 실행 의존성과 위험을
확인하고, 범위가 실제로 겹치면 검토자의 명시적 coverage 확인을 재사용한다.
퇴역 경로는 그 사유를 남기되 과거 미증명 결과를 PASS로 바꾸지 않는다.
