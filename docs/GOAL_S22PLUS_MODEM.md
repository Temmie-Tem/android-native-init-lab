# GOAL: S22+ 모뎀 기동과 서비스 연구

**현재 상태 (2026-11-22).** 순정 S22+의 같은 부팅에서 MPSS·원격 저장소 서비스 실행과 모뎀 IPCRTR 채널의 바인딩을 확인했다. 같은 부팅에서 `qcom-scm` IRQ 카운터의 합계는 2였다. 각 IRQ의 원인은 미확인이다. ML053 기반의 PAS 활성 커널과 2,988,260바이트 원격 저장소·TFTP 통합 RAM 아카이브를 ARM64 VM에서 검증했다. SysV init이 펌웨어 게시 뒤 두 서비스를 시작했고, 같은 GLINK 상대가 순정 순서의 저장소 읽기 네 건과 FYG1 파일 전체 수신을 마쳤다. 저장소 백엔드 연결이 지연돼도 TFTP 파일 수신은 성공했다. 후속 아카이브에는 RAM의 빈 `/tmp`를 추가했다. 같은 상대가 `server_check.txt` 쓰기를 마치기 전과 후 모두 순정에서 관측한 펌웨어 구간을 읽었다. 별도 H0 사본에서는 Debian 시작 프로그램이 입력 검사 후 저장소 메모리 모듈을 적재해 VM의 사전 적재 없이 11개 QMI 거래를 완료했다. 이 2,988,428바이트 아카이브를 넣은 로더가 커널 진입점에 넘긴 Image·DT·initrd도 호스트에서 대조했다. 파일 서비스에 성공한 VM의 공유 메모리에는 VMID 속성이 없었다. VMID 15를 지정하고 SCM이 없는 경우에는 메모리 probe가 지연되어 저장소 서비스가 시작되지 않았다. TFTP의 펌웨어 읽기에는 오프라인 시험 프로세서를 사용했다. 별도로 시험한 실제 PAS probe도 SCM이 없는 VM에서 지연됐다. 과거 Android 운용 중에는 FS1·FS2 쓰기 완료도 기록됐다. 현재 Debian 구성에서 합성 FS1 쓰기는 핸들을 닫으면 사라졌다. 실기 모뎀용 저장소 입력과 메인라인 SCM의 권한 수락은 미확인이다. [두 서비스의 통합 시험](reports/S22PLUS_FYG1_COMBINED_FILE_SERVICES_H0_2026-11-22.md) · [펌웨어 수신기](reports/S22PLUS_FYG1_FIRMWARE_STAGE_H0_2026-11-22.md)

## 완료한 실기 목표 · S22+ 메인라인 SCM 연결 관측

**2026-11-22 실기 결과.** MPSS를 끈 채로 S22+를 메인라인에 한 번 부팅했다. 동일 부팅의 인증된 USB 응답에서 지정된 SCM 장치의 드라이버 연결(`bound`)을 확인했다. 후보와 원래 Android는 각각 한 번 전송했고 최종 건강 상태는 `ANDROID_CLOSED_HEALTHY`다. 이 후보와 승인은 소모됐다. 다음 실기 설계의 질문은 고정 RMTFS 메모리에 대한 VMID 15 권한 요청의 실제 반환값이다. IRQ 등록 여부는 별도 미확인 항목이다. [실기 관측과 복구 근거](reports/S22PLUS_MAINLINE_SCM_USB_RUN_2026-11-22.md)

**VMID 15 후속 실험은 복구 근거 대기 중이다.** 2.5 MiB 메인라인 예약 영역은 순정에서 실측한 모뎀 UIO 범위와 겹치지 않는다. 선택한 RMTFS 드라이버는 HLOS 단독 권한으로 되돌리는 호출의 결과를 버린다. 원래 Android AP와 이전 복구 기록은 재검증했다. 실기 진행에는 권한 반환 실패나 강제 리셋 뒤에도 같은 영역의 VMID 15 권한을 회수할 수 있다는 근거가 필요하다. P441의 warm reset 전후 커널에서 같은 범위를 포함하는 System RAM 등록을 확인했다. 순정 DMA-BUF 조회는 객체에 저장된 상태를 검사하고, Gunyah 회수는 등록된 메모리 묶음의 핸들을 요구한다. 이 영역에 대한 리셋 후 권한 해제와 회수는 미확인이고, 실기 권한 요청은 미실행이다. [FYG8 펌웨어·리셋 원본과 조회·회수 경로 대조](reports/S22PLUS_RMTFS_VMID15_RECOVERY_H0_2026-11-22.md#fyg8-펌웨어와-리셋-기록의-후속-확인)

MODEMST1·MODEMST2·FSG의 별도 순정 1회 관측도 끝났다. 그 실측 결과는 `workspace/private/runs/s22plus-nv-summary-DT4HWb8w/summary.md`에 있다.

### 첫 H0 입력과 판독 결과

검토할 커널은 저장소 서비스 VM에 사용한 ARM64 Image `5a0b12b0e690…`다. 조합할 DT는 **MPSS를 켜기 전의 ML053 원본**이다. 원본은 MPSS·UFS·SD 컨트롤러를 비활성으로 두고 USB를 활성화한다. 고정 RMTFS 영역의 `no-map` 예약은 유지한다. Image에서 추출한 설정에서는 SCM이 내장이고 PAS와 RMTFS 메모리 드라이버는 모듈이며, UFS 호스트와 `/dev/mem`은 꺼져 있다. 모듈을 담지 않은 ML022의 Debian RAM 아카이브를 기준으로 삼고, 폐기된 USB 키와 기존 후보 승인은 재사용하지 않는다.

예비 판독 함수는 고정된 SCM 장치의 OF 경로와 호환 문자열을 확인하고, 플랫폼 장치와 드라이버의 양방향 링크 및 `waiting_for_supplier` 속성을 두 번 읽는다. 드라이버 코어는 probe 호출 전에 링크를 만들 수 있다. 따라서 이번 커널의 첫 연결에서는 probe 성공 후 공급자 속성이 제거되는 순서까지 대조한다. ARM64 파일시스템 시험 10건에서 연결·미연결·판정 불가가 예상대로 나왔다. 별도로 같은 Image를 부팅한 VM에서 인터커넥트 공급자를 기다리는 실제 플랫폼 장치는 미연결, 다른 OF 호환 문자열은 판정 불가로 읽혔다. 일반 VM에 SCM 노드만 추가한 시험은 40초 동안 판독 출력을 남기지 못했다. 실제 SCM 드라이버 연결 성공은 이 VM 시험에서 관측하지 못했다.

판독 함수는 SCM 호출을 보내지 않는다. 커널의 SCM probe에는 대기열 조회와 Download 모드 설정 시도, 조건부 SDI 비활성화 등 자체 초기화가 있으므로 후보 검토에는 이 경로도 포함한다. ML022가 한 번 실험 부팅을 전송하고 물리 Download에서 원래 Android를 한 번 복원해 건강하게 닫힌 기록을 확인했다. 보관된 복구 AP는 지금도 읽을 수 있고 단일 부트 멤버의 해시가 맞으며, ML053 작업의 복구 참조와도 일치한다. 이력만으로 현재 기기의 복구 상태를 판정하지 않는다. [ML022 실기 종료 기록](reports/S22PLUS_MAINLINE_ML022_RUN_2026-11-04.md)

예비 소스, VM 원시 기록, 입력과 복구 파일의 해시는 `workspace/private/analysis/s22plus-mainline-scm-attended.37TSBan1/`에 있다.

### 인증된 USB 판독과 실기 후보 선택

같은 Image를 부팅한 VM의 CDC-NCM에서 실제 SCM 호환 장치의 미연결 응답을 회수했다. 별도 시험 드라이버에서는 첫 probe가 USB 응답 전후로 진행 중이면 판정 불가, 연결 완료 통지 뒤에는 연결, 실패 통지 뒤에는 미연결로 판독했다. 변경한 요청 태그에는 응답이 없었다. 독립 검토에서 정상 응답 4건의 HMAC과 진행 중 대조의 커널 관측 순서를 확인했다. [USB 판독 실험](reports/S22PLUS_MAINLINE_SCM_USB_H0_2026-11-22.md)

입회 부팅 1회의 우선 구성은 기존 Image와 MPSS 비활성 DT를 유지하고, Debian 관측기의 USB 응답에서 요청 시점의 SCM 상태를 읽는 것이다. 별도 보존 RAM 표식은 변경된 Image의 더 이른 시점을 관측한다. 이 둘을 같은 부팅 시도로 묶는 증거는 없다. USB가 응답하지 않으면 SCM 상태는 미확인으로 닫는다.

선정한 Image에서 SCM probe는 공급자 조건이 충족되면 SHM Bridge 지원 조회와 조건부 활성화를 시도한다. 뒤쪽에는 NODUMP 레지스터 갱신, SDI 비활성화 및 QTEE 지원 조회 경로도 남아 있다. RAM 아카이브에서 모뎀·QTEE 모듈을 빼도 SCM 코어의 이 초기화는 남으므로 실기 후보 검토에 포함한다. [링크된 커널과 DT 대조](reports/S22PLUS_MAINLINE_SCM_USB_H0_2026-11-22.md#선정한-image에서-scm-probe-자체가-요청하는-효과)

기기용 AP `c7dd8fa726fe…`를 H0에서 완성했다. 두 AP 사본을 해제해 기존 Image, MPSS 비활성 DT, 모듈 없는 Debian RAM과 새 관측기를 확인했다. 기기용 판독기는 이 로더가 인계한 DT 전체 해시와 봉인된 USB 응답을 검사한다. 별도 시험 키로 세 상태값과 거부 대조 10건을 검증했다. [기기용 패키지와 최종 판독기](reports/S22PLUS_MAINLINE_SCM_BOARD_ARTIFACT_H0_2026-11-22.md)

격리 브랜치 `codex/s22-scm-attended-h0`의 `3b6ee4fb5b`에서 준비한 세션을 재사용했다. 정상 연결·미연결·판정 불가, 무응답 뒤 원래 Android 복원과 최종 건강 확인을 호스트에서 검증했다. 공용 터미널과 uniLoader→Android에는 새 소스에 대한 독립 검토 기록을 발급했다. 재사용 UFS V13의 같은 모듈·고정 입력과 보존 증거를 묶은 후속 검토 기록은 `workspace/private/outputs/s22plus-scm-usb-attended-adoption-20261122-1/v13-compat/`에 있다. 이후의 V13 후보에는 새 키와 후보 자격 확인을 적용한다. 과거의 후보·작업·승인은 원래 검토 기록에 묶인다.

**방향 점검.** 이번 `bound` 관측으로 선정한 커널의 SCM 연결을 확인했다. 펌웨어가 개별 요청을 수락하는지, 실기 모뎀에 필요한 저장소 입력을 어떻게 공급할지는 남아 있다.

## 메인라인 모뎀 연구에서 남은 판정

운영자 소유 S22+의 순정 D0와 필요한 고정 Magisk `su` 읽기를 연구 범위에 포함한다. 이번 단위에서 순정 드라이버의 연결과 원격 OPEN 등록 경로, 메인라인의 정상 GLINK 서비스 경로, 예상 백엔드가 없을 때의 서비스 시작 조건까지 조사했다. 메인라인 SCM 연결 이후의 실기 판정은 대기열 IRQ 등록과 고정 RMTFS 메모리의 VMID 15 권한 요청 결과다. SCM의 가용 플래그 하나로 이 셋을 판정할 수 없다. 순정 D0와 가상 SCM 부재 대조로는 이 반환값을 얻을 수 없다. 메인라인 부팅은 별도 효과이며, 해당 대상 계약·복구·실행 권한에 따른다.

## 목적과 범위

대상은 Galaxy S22+ SM-S906N의 FYG8 배포본에 포함된 순정 FYG1 모뎀이다. 메인라인 Linux에서 순정 모뎀의 **기동 가능성, 준비 상태의 증거, 호스트와 모뎀 사이 통신의 증거**를 구분해 조사한다. 이 문서는 별도 연구 목표다. 루트 `GOAL.md`의 USB/UFS 서버화 트랙, 정책, 권한, 기존 작업은 바꾸지 않는다.

2026-11-21 운영자 요청에 따라 H0 빌드·분석과 운영자 소유 S22+의 D0 실기 관측을 함께 진행한다. 이번 기동 의존성 검증은 한 번의 순정 상태 스냅샷을 수집한다. 그 항목은 순정 Android에서 MPSS와 RMTFS 메모리 드라이버의 바인딩, remoteproc 상태, 원격 저장소 서비스 상태다. 후속 D0는 현재 연구 요청과 대상 계약이 허용하는 범위에서 진행한다. 같은 단말·포트·부팅을 확인한 뒤 고정된 읽기만 실행하며, 필요한 sysfs 관측에는 기존 Magisk `su`를 사용한다. 범위와 실행은 [대상 계약의 D0](operations/targets/S22PLUS_FYG8_TARGET_CONTRACT.md#s22-d0) 및 적용되는 실제 권한을 따른다. 관측 도중의 불명확한 결과는 그대로 보존한다. 새 기동·리셋·플래시·펌웨어 쓰기·전파 송신은 이 D0의 범위 밖이다. 서명이나 접근 제어 우회, 취약점 재현·개발, 임의 신호 송신 및 실망 상호작용은 연구 범위에서 제외한다.

## 출발점

- 기존 순정 Android 실기 로그는 순정 FYG1 모뎀 기동의 기준점이다. 메인라인 기동 기록은 아니다.
- 11월 19일 H0 보고서는 서명 검증이 순정 기동의 전제라는 정적 근거를 담는다. 실제 수정 펌웨어 실행·거부와 모뎀 펌웨어 복구는 미검증이다.
- ML050 이미지에는 모뎀 기동에 필요한 구성이 빠져 있었다. 메인라인 기동 완료, 모뎀과의 통신, 송수신은 별개이며 모두 미확인 상태에서 시작한다.
- 먼저 `docs/reports/S22PLUS_FYG1_CP_SIGNING_AND_RECOVERY_H0_2026-11-19.md`와 최신 로컬 결과를 읽어 이 출발점을 갱신한다.

## 반복 작업

1. **상태 갱신:** 최신 기록을 읽고 주장마다 출처·실험 ID·환경을 붙인다. 순정/메인라인, 실기 관측/정적 추론/시뮬레이션을 분리한다.
2. **다음 목표 하나 선택:** 최종 목표에 가장 가까우면서 호스트에서 반증 가능한 질문을 고른다. 먼저 기존 순정 로그에서 ‘기동 요청’, ‘기동 완료’, ‘호스트 통신 가능’을 각각 구별할 수 있는 증거가 있는지 확인한다. 한 번에 질문 하나, 성공 기준 하나, 관측 불가 기준 하나를 정한다.
3. **검증 실행:** 이미 확보한 증거를 먼저 사용한다. 부족하면 공개 소스 비교 또는 합성 로그·오프라인 테스트 중 가장 작은 검증을 실행한다. 결과가 없는 경우를 실패와 동일시하지 않는다.
4. **결과 기록:** 날짜, 질문, 환경, 관측값, 근거, 한계, 다음 후보를 한 단락으로 기록한다. 판정은 ‘확인’, ‘반증’, ‘미확인’으로 남긴다. 장치 로그나 펌웨어 원본은 내보내지 않는다.
5. **결과에 따라 다음 목표 선택:** 새 증거가 있으면 다음 H0 질문으로 넘어간다. 지속 연구 중 검증이 끝난 단위마다 결과를 커밋하고 다음 질문을 선정한다. 같은 질문이 새 증거 없이 반복되거나 현재 범위 밖의 효과가 필요하면 해당 경로를 멈추고, 독립적으로 가능한 H0와 승인 범위의 D0를 이어간다. 남은 H0 작업이 없으면 필요한 관측과 이유만 사용자에게 보고한다.

## 2026-11-20 · FYG1 메모리 적재 범위와 ML053 예약 영역

**확인.** FYG1을 Linux 7.2.11 MDT 로더 규칙으로 적재할 때 필요한 주소 범위와 최종 ML053 부팅 이미지의 MPSS 주 예약 영역은 모두 **306 MiB(320,864,256바이트)**다. 세그먼트 30개가 전부 들어가고 마지막 세그먼트의 끝이 예약 영역의 끝과 일치한다. [앞선 순정·ML050 대조](reports/S22PLUS_FYG1_CP_SIGNING_AND_RECOVERY_H0_2026-11-19.md#ml050에-서명된-순정-fyg1을-그대로-공급할-수-있는가)에서도 같은 크기를 관측했다.

- **펌웨어.** 앞서 순정 CP와 대조한 MDT를 해시로 식별하고, ELF32 헤더를 직접 읽은 결과를 `readelf`와 대조했다. 적재 대상 30개 모두 재배치 플래그가 있어 각 시작 오프셋은 해당 물리 주소에서 최저 적재 주소를 뺀 값이다. ML053의 예약 시작 주소가 이 최저 주소와 같아 실제 계산상의 이동량은 0이다. 개별 메모리 길이에 더해 세그먼트 사이의 빈 공간 592 KiB를 포함하고, 마지막 주소 바로 다음 경계를 4 KiB로 올림한 전체 범위를 확인했다.
- **상한.** 파일 길이가 0인 인덱스 14, 21, 30이 메모리에서 총 171 MiB를 차지한다. 마지막인 30번까지 포함했을 때 예약 영역 끝의 여유는 0바이트다. 비교식에서만 예약 크기를 1바이트 줄인 대조에서는 30번 하나가 범위를 벗어났다.
- **기기 트리.** 패키지의 `boot.img`에서 uniLoader와 DTB의 바이트를 확인하고 MPSS의 첫 `memory-region` 참조가 가리키는 `no-map` 고정 영역을 읽었다. 영역 전체가 DTB의 RAM 범위에 있고 다른 고정 예약 영역 및 FDT 예약 표와 겹치지 않는다. 같은 로더의 보관된 ARM64 호스트 시험에서 나온 DTB도 같은 결과다. 패키지본과 시험본의 속성 차이는 `/chosen`의 초기 램디스크 시작·끝 두 개뿐이었다.

이 판정은 Linux 로더의 주소 범위 조건까지다. 실기에서의 TrustZone 인증과 모뎀 기동은 미확인이다. 세그먼트별 오프셋·길이, 경계 대조, 입력 해시와 재현 스크립트는 `workspace/private/analysis/s22plus-ml053-fyg1-memory.fHQ6iUPg/`에 있다. 다음 H0 질문은 ML053의 모뎀 준비(`ready`) 인터럽트가 순정 FYG8과 같은 모뎀 측 SMP2P 신호 비트에 연결되는지다.

| 모뎀의 도메인 이름 | DT 도메인 ID | 링크된 SM8450 테이블의 대상 | command DB 자원 이름 |
| --- | --- | --- | --- |
| `cx` | 0 | `cx` | `cx.lvl` |
| `mss` | 12 | `mss` | `mss.lvl` |

Image에서 추출한 설정에 `CONFIG_QCOM_RPMHPD=y`, `CONFIG_QCOM_RPMH=y`, `CONFIG_QCOM_COMMAND_DB=y`가 모두 있었다. 빌드 기록의 objcopy 명령으로 보관된 `vmlinux`에서 Image를 재생성하자 최종 `boot.img` 안의 Image와 바이트 단위로 일치했다. 이 ELF에서 공급자의 compatible 항목이 `sm8450_desc`를 가리키고, 그 13개 슬롯 중 0번과 12번이 각각 위 두 객체를 가리키는 것까지 확인했다. 초기 램디스크에 별도로 동봉된 커널 모듈은 `g0q_ml030.ko` 하나다. 전원 도메인 공급자·RSC·command DB 드라이버는 모두 커널 본체에 있다.

공급자 코드와 도메인 테이블은 고정 Linux 7.2.11 아카이브와 일치한다. 이 후보의 RSC 소스에는 프로젝트의 기존 전송 코드가 추가돼 있어 원본과 추가분을 각각 당시 빌드 기록의 해시로 대조했다. 실제 공급자 등록은 드라이버가 SM8450 테이블의 각 자원을 command DB에서 조회하고 ARC 유형과 레벨 매핑을 검사한 뒤에 이뤄진다. 이번 호스트 검증으로는 ML053에서의 공급자 등록이나 모뎀 전원 요청 수락을 확인할 수 없다. 입력 해시와 재현 스크립트, ELF 슬롯 대조 결과는 `workspace/private/analysis/s22plus-ml053-mpss-power.xEC1BkZ1/`에 있다.

다음 H0 질문은 보관된 SM-S906N 자료에 `cx.lvl`·`mss.lvl`의 실제 command DB 항목과 ARC 레벨을 대조할 수 있는 기록이 있는지다.

## 2026-11-20 · FYG8 AOP 배포본의 ARC 자원과 레벨

**배포본에서 정적 복원 확인.** SM-S906N FYG8 정식 ZIP에서 BL 멤버의 크기와 SHA-256을 [배포본 기준값](operations/S22PLUS_FYG8_STOCK_FIRMWARE_EVIDENCE_POLICY_2026-07-08.md)과 대조했다. 그 안의 `aop.mbn.lz4`를 풀어 보관된 AOP 사본과 바이트 해시가 일치함을 확인했다. AOP ELF의 테이블 참조에서 길이 24바이트인 자원 레코드 24개와 보조 데이터 384바이트를 찾았다. 두 포인터를 각각 ELF 파일 위치로 변환한 뒤 ML053의 command DB 레이아웃으로 키, 자원 주소, 보조 데이터 길이와 상대 오프셋을 읽었다.

| 자원 | RPMh 자원 주소 | ARC 유형 | 패딩을 제외한 가상 성능 레벨(하드웨어 인덱스 0부터) |
| --- | --- | --- | --- |
| `cx.lvl` | `0x30000` | 3 | 0, 16, 64, 128, 192, 256, 288, 320, 384, 400, 416, 432, 480 |
| `mss.lvl` | `0x30060` | 3 | 0, 56, 64, 128, 192, 256, 320, 384 |

두 레코드의 보조 데이터는 각 32바이트이고 표 안의 시작 오프셋은 각각 0과 192다. ML053 드라이버의 규칙을 적용해 첫 레벨 0은 유지하고 마지막의 0 패딩을 제외했다. 이 값은 성능 상태를 선택하는 코드다. 인접한 `.tmr` 레코드는 주소가 4씩 다르고 레벨 데이터 길이는 0이다. 같은 표에서 ML053의 SM8450 공급자 13개 슬롯이 참조하는 고유 자원 9개 모두에 레벨 데이터가 있음을 확인했다.

**FYG8 Android 부팅 기록.** 7월 13일 보관한 FYG8/FYG1 bugreport 두 건을 각각 캡처 영수증과 대조했다. 두 기록 모두 128 KiB의 AOP command DB 예약 영역과 순정 드라이버의 매핑을 보여 준다. ZIP 멤버에서 두 자원 이름이나 command DB 덤프 표제는 발견되지 않았다. 배포본에서 복원한 레벨 표가 해당 부팅에서 같은 바이트로 공급됐는지, 실제로 어느 레벨을 요청·수락했는지는 미확인이다. 입력 해시, 레코드별 원본 레벨, 부팅 기록의 대응 행과 재현 스크립트는 `workspace/private/analysis/s22plus-fyg8-arc-levels.lCA2CKG4/`에 있다.

다음 H0 질문은 ML053의 PAS 드라이버가 모뎀 기동을 위해 요청하는 성능 상태를 이 두 표에 적용하면 각각 어떤 하드웨어 인덱스가 선택되는지다.

## 2026-11-20 · 모뎀 기동 요청에 대응하는 ARC 하드웨어 인덱스

**순정 FYG8 표를 적용한 결과는 `cx = 12`, `mss = 7`이다.** ML053에 대응하는 Linux 7.2.11의 SM8450 PAS 기동 코드는 두 도메인에 차례로 `INT_MAX`(2,147,483,647)를 요청한다. RPMh 공급자는 패딩을 제외한 표에서 요청값 이상인 첫 레벨을 찾는다. 어느 레벨도 요청값에 도달하지 않으면 마지막 유효 인덱스인 `level_count - 1`을 선택한다.

| 자원 | 유효 레벨 수 | 선택한 인덱스(0부터) | 해당 가상 성능 레벨 | 최고 인덱스로 넘어가는 경계 대조 |
| --- | ---: | ---: | ---: | --- |
| `cx.lvl` | 13 | 12 | 480 | 요청 432 → 인덱스 11, 요청 433 → 인덱스 12 |
| `mss.lvl` | 8 | 7 | 384 | 요청 320 → 인덱스 6, 요청 321 → 인덱스 7 |

**호스트 검증.** 해시를 대조한 FYG8 AOP에서 두 자원의 패딩 포함 원본 데이터를 다시 읽었다. PAS 요청 함수와 RPMh 레벨 해석·선택·집계 함수의 원문을 ARM64 시험 프로그램으로 컴파일해 QEMU에서 실행했다. genpd·runtime PM은 시험용 연결 함수를 썼고 RPMh 전송 함수는 호출 인자만 기록했다. 공급자 동기화 전후와 초기 도메인 on/off 조합, 경계값을 포함한 14개 경우를 별도 표 계산과 대조했다. 정상 기동 요청에서 기록된 RPMh 데이터는 `cx`의 active·wake·sleep 모두 12, `mss`의 active는 7이었다. 동기화 전에는 공급자 자체가 최고 인덱스로 제한하므로, 최대값보다 낮은 요청과 구분하는 경계 대조는 동기화 후 조건에서 판정했다.

현재 ML053은 MPSS가 비활성화돼 있고 PAS 드라이버도 빠져 있다. 이 값은 기동 요청을 적용한 계산 및 호스트 재현 결과다. 실기 전송·수락 여부는 미확인이다. 입력 해시와 호출별 결과, 재현 코드는 `workspace/private/analysis/s22plus-ml053-mpss-corners.6RGnco6U/`에 있다. 다음 H0 질문은 PAS 기동 경로에서 전원 도메인 다음에 활성화하는 `xo` 클럭이 ML053 DTB의 어느 공급자에 연결되며 해당 드라이버가 패키지에 포함돼 있는지다.

## 2026-11-20 · ML053 모뎀의 xo 클럭 공급자

**모뎀의 `xo`는 SM8450 RPMh 클럭 공급자의 0번 출력이며 공급자 드라이버는 최종 커널에 내장돼 있다.** PAS 코드는 이름 `xo`로 클럭을 얻고 기동 시 전원 도메인을 활성화한 다음 `clk_prepare_enable(pas->xo)`를 호출한다. 패키지의 모뎀 노드에서 이 이름의 `clocks` 참조를 따라가면 `/soc@0/rsc@17a00000/clock-controller`의 `RPMH_CXO_CLK`(ID 0)에 도달한다. 공급자의 compatible은 `qcom,sm8450-rpmh-clk`다.

| 경로 | ML053에서 확인한 값 |
| --- | --- |
| 모뎀이 요청하는 출력 | ID 0 → `clk_rpmh_bi_tcxo_div4`. 클럭 프레임워크 이름은 `bi_tcxo`, RPMh 자원은 `xo.lvl`이다. ID 1은 별도의 active-only 출력이다. |
| 공급자의 기준 입력 | `/clocks/xo-board`의 `fixed-clock`은 76.8 MHz다. 0번 출력의 분주비는 4이며 드라이버의 계산 주파수는 19.2 MHz다. |
| 드라이버 포함 근거 | 패키지 Image의 내장 설정에 `CONFIG_QCOM_CLK_RPMH=y`가 있다. 같은 빌드의 `vmlinux`에서 재생성한 Image가 최종 `boot.img` 속 Image와 바이트 단위로 일치했다. |

ELF에서 compatible 매치 항목 → SM8450 클럭 배열 → 0번 객체를 직접 따라가 이름, 자원 문자열과 분주비를 읽었다. 기준 입력의 `fixed-clock` 등록 항목도 ELF에 있었다. ML053의 `clk-rpmh.c`에는 기존 전송 경로가 추가한 RPMh 호출 제한이 있어 당시 빌드 영수증의 수정 전후 해시로 확인했다. 패키지 DTB와 로더의 보관된 호스트 시험 DTB에서 `xo` 연결은 동일했다.

실기에서의 클럭 공급자 등록, 모뎀의 활성화 요청 및 출력 주파수는 미관측이다. 입력 해시와 재현 스크립트, ELF 대조 결과는 `workspace/private/analysis/s22plus-ml053-mpss-xo.VraDoml5/`에 있다. 다음 H0 질문은 이 클럭 공급자가 등록될 때 필수로 조회하는 command DB 자원을 순정 FYG8 배포 자료에서 확인할 수 있는지다.

## 2026-11-21 · 순정 부팅 중 PAS 매핑과 ML053의 대조

**FYG8 Android 부팅에서 PAS가 매핑한 모뎀 메모리의 시작 주소와 예약 크기가 ML053의 주 예약 영역에 일치한다.** 오퍼스와 논의해 XO 공급자의 추가 조사보다 이 대조를 먼저 진행했다. 7월 13일의 FYG8/FYG1 bugreport 두 건을 각각 캡처 영수증과 검증했다. 두 보고서 모두 `mpss_region` 행에서 주소를 가렸지만 크기는 306 MiB로 기록했다. 같은 보고서의 `/proc/vmallocinfo`에는 순정 PAS 드라이버의 매핑 물리 시작 주소가 남았다. 배포 모듈에서 기록된 호출 위치는 첫 번째 `memory-region`의 시작과 길이를 `devm_ioremap_wc`에 넘긴 직후다. 가상 할당 표시 길이는 320,868,352바이트로, 예약 길이 320,864,256바이트에 가드 한 페이지(4 KiB)를 더한 값이다.

별도 시점에 보관한 순정 실기 FDT, ML053 패키지 DTB 및 FYG1의 적재 세그먼트 30개와도 양 끝이 맞는다. 순정의 두 번째 `memory-region`은 CMA 풀이다. 순정 `cx-supply`와 `mx-supply`를 실제 조절기까지 따라가면 각각 `cx.lvl`과 `mss.lvl`이며 ML053의 두 전원 도메인이 조회하는 자원과 일치한다. 두 DT의 출력 `stop`은 `master-kernel` 비트 0이고, 이름으로 대조한 입력 인터럽트 6개의 컨트롤러 종류와 신호 번호도 일치한다. SMP2P 에지 플래그는 순정 DT에서는 미지정, ML053에서는 상승이다. 이 대조는 두 커널이 같은 시점에 같은 전원 요청을 했거나 메인라인에서 IRQ를 수신했다는 증거를 제공하지 않는다. [기존 준비 인터럽트 대조](#2026-11-20--순정-fyg8과-ml053의-모뎀-준비-완료-인터럽트)

구성 차이도 확인했다. 순정 MPSS는 `rproc_ddr`, `crypto_ddr` 두 인터커넥트를 선언한다. ML053의 MPSS 노드에는 `interconnects`가 없다. 메모리 대조는 주 예약 영역을 수정할 근거를 발견하지 못했다. 새 검증의 파일별 해시, 보고서 대응 행, DT 참조와 재현 코드는 `workspace/private/analysis/s22plus-fyg8-mpss-runtime-map.oHL1ggCN/`에 있다.

## 2026-11-21 · 순정 원격 저장소와 DMS 응답, H0 탐색 종료

**순정 모뎀용 저장소 요청은 기동 중에 이미 처리되고 있었다.** 7월 13일 보관한 두 FYG8/FYG1 bugreport에서 `vendor.rmt_storage`가 모뎀 파일을 열고 읽기 요청을 받았으며, 같은 요청 핸들과 파일에 대해 512바이트를 읽은 완료 기록까지 확인했다. 두 경우 모두 모뎀 GLINK의 IPCRTR 바인딩 이후, 커널이 MPSS 기동 완료를 기록하기 전이었다.

| FYG8 Android 캡처 | 첫 512바이트 읽기 완료 (부팅 후) | MPSS 기동 완료 (부팅 후) | DMS 동기 조회와의 순서 |
| --- | ---: | ---: | --- |
| 09:57 UTC 캡처의 `last_kmsg` (이전 부팅) | 8.982846초 | 8.983805초 | 이 부팅에 연결한 DMS 결과 없음 |
| 14:20 UTC 캡처의 `ap_klog` (R4W1-A 부팅) | 9.087235초 | 9.092829초 | 같은 저장소 요청의 성공 응답 송신 로그로부터 1.261초 뒤에 RILD가 DMS `GET_OPERATING_MODE` 성공을 기록 |

두 번째 캡처의 시간 차는 같은 Android 로그 시계에서 계산했고, 커널과 Android 양쪽에 남은 같은 SystemServer 부팅 표식으로 순서를 교차 확인했다. 저장소 서비스 수준의 요청 처리와 응답 송신을 입증하는 기록이다. 패킷의 상대 주소는 확인되지 않았으며, 이 서비스를 제외했을 때 모뎀 기동이나 DMS 호출이 실패하는지는 미확인이다.

**ML053에서 순정 저장소 동작을 재현하려면 AP 측 서비스 경로도 구현 범위에 들어간다.** 순정 실기 FDT에는 `qcom,sharedmem-uio` 클라이언트가 있고 ML053에는 `qcom,rmtfs-mem` 예약 노드가 있다. 크기 2.5 MiB와 클라이언트 ID 1은 일치한다. ## 2026-11-21 · 모뎀 ready와 GLINK 등록 순서

**ML053에 대응하는 Linux 7.2.11 소스에서는 MPSS 기동을 활성화하면 PAS가 ready 완료를 기다린 뒤 GLINK를 등록한다.** remoteproc 코어가 하위 장치 준비, 프로세서 기동, 하위 장치 시작을 차례로 호출한다. GLINK는 시작 콜백에서 SMEM 전송을 등록한다. GLINK 시작 시점을 옮기거나 대기 시간을 바꿀 근거도 확보되지 않았다. 소스·모듈 해시, 부팅별 근거 행과 시험 결과는 `workspace/private/analysis/s22plus-mpss-glink-order.8OWXLdAr/results.json`에 있다.

## 2026-11-21 · 첫 파일 읽기의 버퍼 주소 해석

**FYG8 순정 서비스는 구형 클라이언트의 단일 섹터 읽기에서 IOVEC의 두 번째 32비트 값을 버퍼의 절대주소로 해석한다.** 정상 할당 콜백은 양수 요청과 0바이트 더미 요청을 구분해 공유 상태에 모드를 기록한다. 배포된 읽기 작업자는 구형 모드에서 전달값에서 앞서 저장한 UIO 기준 주소를 빼고, 그 차이를 사용자 공간 매핑 시작점에 더한다. 더미 요청 모드에서는 전달값 자체를 바이트 변위로 사용한다. 두 모드 모두 로그에 찍는 파일 `offset`은 첫 번째 필드인 파일 섹터 번호에 512를 곱한 값이다.

순정 요청 디코더에 정상적인 단일 섹터 요청 여섯 건을 넣어 두 모드의 좌표와 파일 섹터가 서로 다른 필드로 보존됨을 확인했다. Debian ARM64 데몬에는 구형 모드의 정상 요청 세 건을 보내 서로 다른 파일 섹터가 공유 영역의 오프셋 4,096, 8,192 및 마지막 512바이트에 도착하는지 버퍼 전체로 검산했다. 세 건 모두 일치했다. 순정 작업자의 주소 산술은 정적으로 확인했으며, 실제 바이트 이동은 Debian 데몬과 합성 메모리에서 관측했다.

## 2026-11-21 · 고정 배치를 유지하는 2단계 펌웨어 공급

전체 아카이브에서 펌웨어 28개만 분리한 초기 램디스크는 2,005,257바이트(79개 항목)다. 새 Image·DT·초기 램디스크를 같은 고정 주소로 링크했을 때 로더는 46,166,352바이트이고, 기존 부트 외피의 잔여 용량은 53,049,216바이트다. 로더·커널·DT·initramfs 네 구간은 보관된 RAM 뱅크 안에 있고, 어느 구간도 서로 또는 고정 예약 영역과 겹치지 않았다. 실제 부트 v4 패키징과 S22+ 기동은 아직 수행하지 않았다.

ARM64 VM에서 이 초기 램디스크와 시험용 init을 부팅했다. 공급 전 실제 커널의 `request_firmware("modem.mdt")`는 ENOENT였다. VM 전용 virtio 포트로 109,340,422바이트를 전달해 RAM 파일로 게시한 뒤, 같은 커널 API로 MDT를 읽고 `request_firmware_into_buf`로 27개 분할 파일을 각각 읽었다. 시험 모듈에서 읽힌 크기와 SHA-256 전부가 맞았고, 실제 MDT 함수가 계산한 적재 범위는 306 MiB였다. 별도 부팅에서는 마지막 파일 한 바이트를 바꾸자 시험 모듈의 해시 검사가 EBADMSG를 반환했다. 이 검사는 Qualcomm의 서명 검증을 수행하지 않는다. 두 부팅 모두 Debian 데몬의 별도 합성 파일 읽기까지 확인했다.

첫 스트림 시험은 게스트가 포트를 열기 전에 호스트가 송신해 읽기가 끝났다. 게스트 준비와 수신 완료를 양 끝에서 확인한 뒤 정상·변형 대조가 모두 통과했다. 이 결과가 검증한 공급 경로는 VM의 virtio다. 실제 S22+에서 필요한 부팅 후 전송 경로, 저장소 백엔드와 기동 주체는 별도로 정해야 한다. 결과는 같은 비공개 빌드 디렉터리의 `split-layout.json`, `split-valid-pass.json`, `split-altered-pass.json`에 있다.

**Debian이 받은 FYG1에서 PAS 초기화용 메타데이터 구성 확인 (2026-11-22).** ML053 기반 ARM64 VM에서 기존 Debian 통합 RAM 아카이브를 사용했다. 파일 게시 전 커널의 `modem.mdt` 요청은 `ENOENT`였다. 가상 CDC-NCM으로 28개 파일(109,340,422바이트)을 보내고 완료 인증값을 확인한 뒤, 아카이브에 들어 있던 `mdt_loader.ko`의 `qcom_mdt_read_metadata()`를 호출했다. 반환된 5,584바이트 전체가 순정 CP에서 별도로 추출한 ELF 헤더(`modem.b00`, 1,076바이트)와 해시·서명 데이터(`modem.b31`, 4,508바이트)를 순서대로 이은 값과 일치했다. 두 대조 파일은 전송 목록에 없었다.

같은 ML053 기반 모듈의 PAS 초기화 코드에서 이 함수의 반환 포인터와 길이가 정상 경로의 `qcom_scm_pas_init_image()` 인자로 전달됨을 확인했다. VM에서 측정한 범위는 그 입력 버퍼의 구성까지다. 실제 S22+ 보안 영역의 수락 여부와 모뎀 기동 결과는 미확인이다. 원본 CP·모듈·시험 코드 해시, Debian 아카이브와 VM 원시 기록은 `workspace/private/analysis/s22plus-mdt-metadata.LO2j7OA8/result.json`에 연결했다. ## 2026-11-21 · 합성 원격 QRTR 노드에서 첫 저장소 요청

같은 노드의 소켓 시험에서 한 단계 더 나아가, 동일한 새 커널·전체 아카이브를 사용한 ARM64 VM에서 별도의 합성 QRTR 노드를 연결했다. 원격 상대는 커널의 `qrtr-tun`을 통해 정상 HELLO를 교환하고 서비스 14의 공지를 받았다. 공지에 담긴 실제 서비스 포트로 열기·할당·읽기·닫기를 요청했다. 네 응답의 송수신 노드와 포트, 트랜잭션, 결과 코드가 맞았고, Debian 데몬도 네 요청을 모두 합성 상대 노드에서 받은 것으로 기록했다. 공유 메모리 전체와 원본 파일을 바이트 단위로 확인했다. 여기에서 대체한 계층은 실제 S22+의 GLINK/SMEM과 FYG1 상대다. 로그와 재현 입력은 비공개 빌드 디렉터리의 `remote-vm-pass.json`, `remote-vm/`에 있다.

## 2026-11-21 · Debian PID 1에서 USB CDC-NCM 수신과 첫 원격 읽기

부트스트랩의 원래 Debian SysV init을 PID 1로 실행했다. VM 전용 inittab이 시험 프로그램을 직계 자식으로 시작했고, 자식은 `/proc/1/exe`가 아카이브의 원래 init과 같은 파일인지 확인했다. 기존 연구 코드의 configfs NCM 구성과 별도 네트워크 네임스페이스에 둔 호스트 측 `cdc_ncm` 인터페이스를 사용했다. VM 전용 dummy USB 컨트롤러로 양 끝을 연결했다. 외부에서 공급한 원본은 호스트 측 프로세스까지만 virtio를 사용하며, 게스트의 수신기는 실제 Linux USB NCM과 TCP를 통해 파일을 받는다.

정상 시험은 109,340,422바이트를 받아 28개 파일 각각의 고정 해시와 전송 끝을 확인한 뒤 임시 디렉터리를 게시했다. 커널이 게시된 파일 전체를 읽은 후 Debian 데몬을 시작했다. 별도의 합성 QRTR 노드가 서비스 공지를 받고 요청한 512바이트가 정확한 위치에 전달됐다. 한 바이트만 바꾼 별도 부팅은 게시 전에 거부됐고, 커널에서 여전히 MDT가 보이지 않았으며 서비스 시작 횟수는 0이었다. 대상 USB 컨트롤러, 실물 케이블, 기기측 송신자 인증과 실제 EFS 백엔드는 이 VM 시험에서 검증하지 않았다. `sysv-valid-pass.json`·`sysv-altered-pass.json`이 각 원시 로그와 사용한 바이너리를 식별한다.

## 2026-11-21 · PAS 식별자와 RMTFS 메모리 권한 요청

보관된 순정 S22+ 실기 DT와 이번 메인라인 DT에서 각각 선택되는 모듈의 OF 매치 항목을 ELF 재배치까지 따라갔다. 순정 waipio 모뎀 항목과 메인라인 SM8450 항목은 서로 다른 디스크립터로 연결되며, 둘 다 주 PAS ID 4와 기본 파일명 `modem.mdt`를 지정한다. 순정 바이너리에서 해당 ID가 PAS 인증·리셋 함수 인자로 전달되는 경로를 확인했다.

## 2026-11-21 · 순정 실기 GLINK 채널 바인딩과 OPEN 경로

운영자 소유 순정 S22+에서 기존 Magisk 권한으로 보관된 부팅 로그의 정확한 IPCRTR 장치 한 개를 확인했다. 앞의 서비스 D0와 같은 부팅이었다. 채널은 MPSS 플랫폼 장치의 자손이자 rpmsg 버스 소속이고, OF 링크는 순정 모뎀의 명시적 QRTR 자식 노드를 가리켰다. 실제 드라이버는 `qcom_smd_qrtr`, 연결 모듈은 `qrtr_smd`였다. 조회 전후의 채널 소속과 단말·부팅을 확인했다. 독립 검토와 합성 시험 24건, 해시 대조한 원시 캡처 7건은 각각 `workspace/private/analysis/s22plus-fyg1-glink-d0.qQ8tD7tM/`, `workspace/private/runs/s22plus-fyg1-glink-d0-qQ8tD7tM/`에 있다.

두 과거 부팅의 같은 커널 워커에서 해당 장치의 드라이버 probe와 성공 로그를 찾았다. 확보된 dumpstate에는 IPCRTR의 OPEN 송수신 시각 쌍이 없었다. 배포 `qcom_glink.ko`에서 일반 rpmsg 장치를 등록하는 유일한 호출은 `qcom_glink_rx_open`에 있다. 같은 이름의 로컬 채널이 이미 있으면 새 장치 등록을 건너뛰고, 없으면 원격 OPEN을 처리하면서 DT 자식을 조회해 장치를 등록한다. 따라서 해당 등록 경로에서 DT 자식은 채널 정보를 제공한다. 실제 선로에서 어느 OPEN이 몇 시에 먼저 나갔는지는 직접 관측하지 않았다. 명령을 보내지 않은 이번 D0에서 새 CP 응답을 측정한 것은 아니다.

**모뎀 채널에서 QRTR 끝점 등록이 끝난 시각.** FYG8 배포 모듈 세 개를 해시로 대조했다. `qrtr-smd.ko`에서 `Entered`는 probe 진입 시 출력된다. 같은 함수가 `SMD QRTR driver probed`를 출력하는 경로에서는 `qrtr_endpoint_register`가 이미 0을 반환했다. `qrtr.ko`의 등록 함수는 `HELLO` 송신 작업을 커널 워커에 맡기고 반환한다. 워커는 제어 포트를 찾지 못하면 송신 전에 종료할 수 있다. [공개 Qualcomm QRTR 등록·워커 구현](https://android.googlesource.com/kernel/msm.git/%2B/732511d94b9722374c18a391e9523b2a5f50e27c/net/qrtr/qrtr.c)

라우터는 모뎀의 기능 마스크 수신을 노드 0 광고 목적지를 출력한 것과 같은 밀리초에 기록했고, 1 ms 뒤에는 모뎀의 진단 ID 요청 수신을 기록했다. 해당 목적지 행은 NAS의 첫 명시적 성공보다 1.134초 앞섰다. 앞뒤의 SystemServer 표식으로 환산하면 모뎀 IPCRTR 끝점 등록 로그보다 약 128 ms 뒤다. 이는 이 부팅에서 라우터가 모뎀으로 분류한 진단 서비스의 광고 주소와 초기 활동을 보여준다. 이 통신이 거친 GLINK 에지와 다른 부팅의 DMS 주소와의 관계는 미확인이다. 원본 행과 시각 대조, 배포 실행 파일·라이브러리 해시 및 시험 결과는 `workspace/private/analysis/s22plus-stock-qrtr-advert.7ME8pdEi/result.json` 및 `fixtures.json`에 있다.

## 2026-11-21 · 채널 DT 자식 없이 메인라인 GLINK로 전달한 첫 읽기

같은 ARM64 VM 안에서 메인라인 커널 자체의 GLINK native 두 끝점을 연결했다. ### FYG8 Android 전화 상태와 NAS 조회 응답

**전화 상태 조회가 읽는 값.** FYG8 배포본의 `TeleService.apk`, `telephony-common.jar`, `services.jar`를 압축 해제해 바이트코드를 확인했다. 전화 서비스의 `getRadioPowerState`는 권한과 대상 슬롯을 확인한 정상 경로에서 `Phone.getRadioPowerState`를 호출한다. 기본 셀룰러 RIL의 `BaseCommands.getRadioState`는 메모리 필드 `mState`를 반환한다. HIDL의 `RadioIndication.radioStateChanged`는 HAL 상태를 Android 값으로 변환해 이 필드를 갱신한다. 레지스트리의 `notifyRadioPowerStateChanged`는 통지받은 값을 별도 필드에 저장하고 덤프는 그 필드를 출력한다. 따라서 두 값을 읽어도 그 시점의 새 DMS 거래를 확인할 수 없다. [Android 전화 전원 상태 상수](https://android.googlesource.com/platform/frameworks/base/%2B/3fdbf46ac172de22670d7faa824c2fcda19168ec/telephony/java/android/telephony/TelephonyManager.java)

DMS 모드 5 조회 성공을 기준으로 +3,164 ms에 Android의 RILJ가 상태 0(꺼짐)을 기록했다. +4,208 ms에는 RILD가 유효한 DMS 모드 0(ONLINE) 통지를, +4,218 ms에는 RILJ가 상태 1(켜짐)을 기록했다. +4,484 ms에는 VoLTE 서비스가 슬롯 인덱스 0의 전원 상태를 1로 읽었다고 기록했다. 같은 보고서의 레지스트리 덤프에도 1이 있었다. 이 시각들은 각 계층이 로그를 남긴 때다.

**더 이른 서비스 응답.** 같은 부팅의 무선 로그에서 NAS의 동기 `GET_SYS_INFO` 송신, 해당 메시지의 일반 수신, `Result(0), Error(0)`가 동일 RILD 스레드의 연속 세 행으로 나온 경우가 24건이었다. 첫 성공은 DMS 모드 조회 성공보다 5 ms 앞섰다. 한편 다른 NAS 조회(`GET_LTE_CPHY_CA_INFO`)는 수신 행에 `err(0)`을 기록했지만, 바로 다음 같은 스레드의 디코딩 결과에는 `Result(1), Error(74)`가 있었다. 수신 행만 남아 있을 때 확인할 수 있는 범위는 RILD가 해당 메시지의 수신을 기록했다는 사실까지다. 각 거래의 QRTR 주소와 선로 거래 번호는 미확인이다. 배포 파일 해시, 바이트코드 경로와 원본 행 위치는 `workspace/private/analysis/s22plus-android-radio-cache.MXCUJBFO/h0.json`에 있다.

**보관 구간의 첫 수신과 첫 명시적 성공.** 같은 radio 로그에서 RILD의 첫 `ReceiveMessage`는 DMS 모드 조회 성공보다 199 ms 앞선 VOICE의 `END_CALL` 응답이었다. 수신 행은 `err(0)`이었고, 같은 스레드의 다음 행은 `Result(1), Error(41)`이었다. 통화 성립을 보여주는 기록은 아니다. 이 구간에서 처음으로 `Result(0), Error(0)`이 명시된 행은 DMS보다 6 ms 앞선 NAS 통지 등록 응답에 속했다. 바로 뒤에서 RILD는 LTE 반송파 집성 통지 항목을 지원한다고 기록했다. 이어 같은 스레드가 같은 메시지 번호로 다시 요청했을 때에는 `Result(1), Error(17)`과 함께 E911 SMS 상태 통지 항목을 지원하지 않는다고 기록했다. 첫 `GET_SYS_INFO` 성공은 그 뒤 1 ms였다. 이는 보관 로그와 배포 RILD의 판정 범위이며, 실제 선로의 첫 패킷이나 LTE 반송파 집성 동작을 특정하지 않는다. 원본 행과 시각 대조는 `workspace/private/analysis/s22plus-nas-registration.m0KowmgL/early.json`에 있다.

**순정 실기 NAS 수신 기록 (2026-11-22 09:17 KST).** 운영자가 선택한 rev81 관측기로 FYG8 Android·FYG1 모뎀의 무선 로그 버퍼를 일반 ADB 셸에서 한 번 읽었다. 고정 필터에 맞는 RILD의 NAS `GET_SYS_INFO` 수신 헤더는 **0건**이었다. 명령은 시간 초과 없이 정상 종료했고 24건 상한에 도달하지 않았다. 이 결과는 읽은 시점에 표시된 행 수다. 이 부팅에서 NAS 조회가 실행됐는지, 어떤 응답이나 결과가 있었는지는 판정할 수 없다.

### Debian 조회기로 확인한 메인라인 DMS 응답

ML053 기반 모뎀 서비스용 Image와 RAM 아카이브를 ARM64 VM에서 부팅했다. VM에만 Debian arm64 `qmicli` 1.36.0과 실행에 필요한 라이브러리, 시험용 inittab과 합성 DMS 상대를 추가했다. Debian 서명 인덱스와 패키지 해시를 확인했고 조회기 바이너리는 수정하지 않았다. 합성 상대가 RAM FIFO로 연결된 실제 GLINK의 `IPCRTR` 채널을 열자 앱 쪽에 `qcom_smd_qrtr`가 연결됐다. 상대는 QRTR 서비스 2를 광고했다. 모뎀 펌웨어를 공급하지 않았다.

같은 부팅에서 조회기를 세 번 실행했다. 각 실행에서 합성 상대가 받은 서비스 데이터는 본문 없는 `GET_OPERATING_MODE`(0x2d) 한 건이었다. 수신 요청과 송신 응답의 노드·포트, 메시지 번호, 거래 번호 및 응답 필드를 원시 바이트에서 대조했다.

| 거래 번호 일치, 성공, 모드 0 | `online`, 종료 코드 0 |

[qmicli 1.36.0의 모드 출력 처리](https://github.com/linux-mobile-broadband/libqmi/blob/1.36.0/src/qmicli/qmicli-dms.c)

### 같은 DMS 응답이 어느 전송 경로로 들어왔는지 확인한 ARM64 VM 시험

ML053 기반의 기존 커널 Image와 Debian `qmicli`를 사용했다. VM에만 넣은 `qrtr-smd` 드라이버 사본은 모델의 `vm-glink-app` 부모 아래에서만 연결된다. 이 드라이버는 고정된 시험용 QRTR v1 DMS 요청·응답 형식에 대해 RPMsg 장치·부모·채널, 발신·수신 주소, QMI 메시지·거래 번호와 방향을 기록한다. 송신은 `rpmsg_send` 성공 뒤, 수신은 재조립된 패킷을 `qrtr_endpoint_post`가 받아들인 뒤에 기록한다. 클라이언트 쪽에서는 배포판 `strace`로 `recvmsg`가 반환한 발신 주소와 응답 18바이트 전체를 확인했다.

| GLINK, 모드 5 | 발신 주소와 응답 전체 일치 | 송신·수신 각 1건 | 모드 5 |

### MPSS 기동 직후 CoreSight가 기록한 서비스 발견

두 FYG8 커널 로그에서 `modem_etm0`와 `modem2_etm0`가 각각 숫자 2와 11을 붙여 `Connection established`를 기록했다. MPSS 기동 완료 표식 이후 경과 시간은 09:57 보고서의 이전 부팅에서 각각 106.831 ms·107.218 ms, 14:20 보고서의 R4W1-A 부팅에서 100.883 ms·101.148 ms였다. 모두 같은 부팅의 커널 시계로 계산했다.

배포 `coresight-remote-etm.ko`는 두 클라이언트 모두 **CoreSight 서비스 51(0x33), 버전 1**을 조회한다. 인스턴스는 각 장치의 `qcom,inst-id`에서 가져오며 FYG8 vendor_boot의 기본 DT 네 개 모두 두 장치에 2와 11을 지정했다. 서버 발견 콜백은 통지받은 노드·포트를 저장하고 연결 플래그를 켠 뒤, 자신에게 설정된 인스턴스 번호를 로그에 출력한다. 이 콜백이 호출하는 외부 함수는 로그 출력뿐이다. 따라서 위 두 행이 직접 보여주는 것은 두 CoreSight 클라이언트의 서비스 발견이다. 해당 행에는 DMS·NAS 거래나 모뎀 응답 본문이 없다. [공개 Qualcomm 드라이버의 서버 발견 콜백](https://android.googlesource.com/kernel/msm/%2B/04749e7fec2a8a5784a984d09f03fd0f2715fd1b/drivers/hwtracing/coresight/coresight-remote-etm.c)

ML053 기반 ARM64 VM에서는 FYG8 소스의 서버 발견·삭제 콜백 본문을 그대로 컴파일해 두 시험용 클라이언트에 연결했다. 기존 메인라인 QRTR·QMI 모듈을 사용했고 모뎀·펌웨어 없이 게스트 안에서만 광고했다. 서비스 51·버전 1에서 인스턴스 2와 11은 각각 해당 발견 로그 한 건을 남겼다. 서비스 2·버전 1·인스턴스 0, 서비스 51·버전 1·인스턴스 12, 서비스 51·버전 2·인스턴스 11을 광고한 세 대조에서는 새 발견 로그가 없었다. 각 광고 소켓을 650 ms 관측한 동안 읽을 수 있는 데이터는 0건이었다.

FYG8 순정 커널과 배포 모듈을 그대로 넣은 별도 VM은 55초 안에 시험용 init에 도달하지 못했다. 첫 ML053 VM은 사용자 공간 시험을 마쳤지만 직렬 출력에서 콜백을 확인할 수 없어, 다음 부팅에서 게스트 커널 로그의 해당 행을 직접 셌다. 부팅별 원본 로그와 입력 해시, 배포 모듈·DT 대조 및 시험 결과는 `workspace/private/analysis/s22plus-boot-service-lookup.mlvW9elx/result.json`에서 추적할 수 있다.

### 순정 QRTR 이름 서비스에서 DMS 광고 조회

앞선 두 FYG8 Android 보고서의 `dumpstate.txt`와 `dumpstate_board.txt`에서는 서비스 2의 QRTR 광고 행을 찾지 못했다. ### DMS 광고 노드와 AP 로컬 노드 구별

최근 실기 D0와 같은 부팅의 건강 기록에서 `boot`와 `vendor_boot` 파티션 해시를 확인했다. 첫 해시는 보관된 Magisk 부트 이미지와, 둘째 해시는 FYG8 배포 vendor_boot 이미지와 일치했다. Magisk 부트의 커널은 배포 커널과 내장 설정이 같고 전체 바이트 해시는 다르다. 배포 vendor_boot의 램디스크에서 직접 꺼낸 `qrtr.ko`와 `qrtr-smd.ko`는 분석한 두 모듈과 바이트 단위로 일치했다.

**이 FYG8 모듈에서 AP의 새 QRTR 소켓은 로컬 노드 1, 초기 포트 0으로 시작한다.** `getsockname`은 이 로컬 주소를 반환한다. 모듈이 이름 서비스를 초기화할 때도 이 값을 읽어 로컬 노드로 저장한다. 로컬에서 서비스를 등록하면 이름 서비스는 송신 소켓의 노드·포트를 사용한다. 따라서 같은 부팅의 DMS 조회에 표시된 노드 0은 이 구현에서 AP 로컬 서비스에 부여하는 노드와 다르다. 수신한 서비스 광고는 전송 끝점을 거쳐 다른 노드를 알릴 수도 있다. 어느 GLINK 에지가 그 광고나 DMS 응답을 실어 왔는지는 여전히 미확인이다.

## 2026-11-22 · SCM 드라이버가 RMTFS 권한 요청 전에 대기하는 조건

S22+의 메인라인 DT에서 SCM은 인터커넥트 경로를 먼저 요청한다. 최종 ARM64 vmlinux에서 다시 생성한 Image가 백엔드 검증에 사용한 Image와 동일했다. 실제 OF 매치 테이블과 링크된 포인터를 따라가면 `qxm_crypto → qns_a2noc_snoc → qnm_aggre2_noc → qns_gemnoc_sf → qnm_snoc_sf → qns_llcc → llcc_mc → ebi`가 이어진다. 네 SM8450 공급자(aggre2-noc, system-noc, gem-noc, mc-virt)는 모두 DT에서 활성 상태이고 같은 BCM voter를 참조한다. 실제 대역폭 요청의 인가는 별도다. 링크된 `qcom_icc_set`은 voter의 반환값을 버리고 0을 반환하므로 이 값만으로 하드웨어 적용을 판정할 수 없다.

같은 커널을 사용한 두 ARM64 VM에서 실제 SCM 플랫폼 장치의 지연 사유를 읽었다. 합성 DT 공급자가 바인딩되기 전에는 장치 코어가 공급자 대기를 기록했다. 바인딩 후에는 두 경우 모두 SCM probe가 인터커넥트 획득 실패를 기록했고 SCM 가용 플래그는 0이었다. 별도 시험 장치가 같은 경로를 조회하자, 목적지 공급자를 게시하지 않은 경우에는 출발·도착·경로가 각각 `0, -517, -517`이었고, 양 끝을 게시하되 연결하지 않은 경우에는 `0, 0, -517`이었다. 두 경우의 최종 SCM 진단은 같았다. 따라서 SCM이 나타나지 않을 때는 개별 공급자 등록, 경로 완성, SCM probe 완료, RMTFS 권한 반환을 구분해야 한다. 실제 기기에서 이 경로가 실패했다는 관측은 없다.

재현 입력과 ELF 검증, 두 VM의 원시 로그는 `workspace/private/analysis/s22plus-ml053-scm-icc.LKMCuZz1/`에 있다. 결합 기록 `joined.json`의 SHA-256은 `9faa354428333544ed2aa57f5d8c2afa95878d988117fc546cb4fe86eda79138`이다. 초기 시험 코드에서 음수 errno를 잘못된 printf 폭으로 출력한 문제를 수정하고 두 VM을 다시 검증했다.

## 2026-11-22 · 순정 SCM IRQ 실측과 메인라인 대기열 분기

순정 S22+의 기존 Magisk 권한으로 펌웨어 SCM 노드의 고정 IRQ 속성과 해당 카운터 한 행을 읽었다. 앞서 MPSS·IPCRTR를 확인한 것과 같은 부팅이었다. 실기 DT는 `GIC_SPI 930`, 상승 에지이고, 커널의 GICv3 하드웨어 번호 962에 등록된 단독 액션은 `qcom-scm`이었다. 표시된 CPU 8개의 카운터 합계는 2였다. 이 스냅샷으로는 개별 인터럽트를 일으킨 호출, 발생 시각, 모뎀 귀속 또는 PAS 성공을 알 수 없다. IRQ를 유발하는 요청은 보내지 않았다. 관측기는 단말 쪽에서 고유 행과 읽기 완료를 확인한 후 정규화한 필드만 반환했다. 독립 검토·합성 시험 30건은 `workspace/private/analysis/s22plus-fyg1-scm-irq-d0.4UDcX8tV/`, 해시와 부팅 경계를 대조한 원시 캡처 7건은 `workspace/private/runs/s22plus-fyg1-scm-irq-d0-4UDcX8tV/`에 있다.

순정 배포 모듈은 플랫폼 IRQ를 요청하고 이 이름의 핸들러를 등록한다. 새 메인라인 DT의 SCM 노드는 같은 GICv3 인터럽트 부모를 사용하지만 자체 `interrupts` 속성이 없다. 드라이버는 먼저 펌웨어의 대기열 정보를 조회한다. 소스 그대로 추출한 변환·선택 분기를 ARM64로 컴파일해 확인했다. 펌웨어가 962를 반환한다는 조건에서는 메인라인도 순정과 같은 세 셀 `0, 930, 1`을 만든다. 동적 IRQ 획득이 성공하면 DT 대체 경로를 호출하지 않는다. 반대로 동적 조회가 실패하고 플랫폼에도 IRQ가 없어 `-ENXIO`이면, IRQ를 요청하지 않고 이 분기를 통과한다. 플랫폼 조회의 `-EPROBE_DEFER`와 IRQ 등록 오류는 각각 상위로 반환됐다. 따라서 메인라인에서 SCM이 가용하다고 표시돼도 대기열 IRQ 등록 성공이나 고정 영역 권한 승인까지 추론할 수 없다. 실제 S22+에서의 메인라인 펌웨어 응답은 아직 미측정이다. ARM64 실행 로그와 입력 해시는 앞의 SCM 디렉터리의 `irq-branches-result.json`에 있다.

메인라인 커널의 `scm_smc_done` 이벤트에서 전송 반환값은 `ret`, 펌웨어 상태는 `res`에 기록된다. 두 값이 모두 성공해도 동일한 GET_INFO 명령을 어느 함수가 호출했는지 알아야 드라이버가 소비한 값을 식별할 수 있다. ARM64 VM에서 추적을 끈 채 이벤트 형식을 읽고, 그 형식대로 만든 성공 응답 하나를 두 호출부와 대조했다. 대기열 개수 조회는 `res0`에서 2를, IRQ 조회는 `res1`에서 962를 취한다. 전송 실패와 펌웨어 실패도 각각 구별했다. 이 숫자는 시험 입력이다. S22+ 실기에서 메인라인이 받은 응답은 미측정이다. 이벤트 형식·소스 해시·세 대조 결과는 같은 SCM 디렉터리의 `trace-format.json`과 `trace-proof.json`에 있다.

## 2026-11-22 · 모뎀 없이 AP가 응답한 도메인 조회

ML053 기반 커널에서 PAS 드라이버는 보호 도메인 매퍼(PD mapper)를 remoteproc 하위 장치로 등록한다. 이 장치의 준비 콜백이 보조 장치를 만들며, remoteproc 코어는 준비 콜백을 프로세서 시작 함수보다 먼저 호출한다. S22+ DT의 루트 호환 문자열 `qcom,sm8450`은 패키지에 든 매퍼의 내장 서비스 표에 대응한다. 따라서 모뎀 도메인 이름이 들어간 응답을 어느 쪽에서 보냈는지가 중요하다.

### TFTP 요청의 발신 노드와 MPSS 기동 순서

R4W1-A 부팅에서 AP의 TFTP 서버가 `847_f_0.mbn` 읽기 일곱 건에 기록한 발신 주소는 **모두 노드 0**이었다. 발신 포트는 순서대로 51·52·53·54·55·56·59였다. FYG8 배포 서버에서 `recvfrom`이 돌려준 주소의 노드·포트가 `rcvd request`의 네 번째·다섯 번째 수로 들어간다. 작업 스레드도 같은 포트를 옵션 응답(`OACK`)에 출력한다. 포트별 수신 행을 해당 작업자의 MPSS 파일 경로·완료 행과 대조했다. 같은 서버의 CDSP 파일 요청 세 건은 노드 10으로 구별됐다. 이 자료로 AP가 받은 원격 요청의 주소와 파일을 연결할 수 있다. 실제 GLINK 에지를 직접 기록한 패킷 추적은 없다.

배포 서버는 소켓 계열 42(QRTR), 27(MSM IPC) 순으로 검사한다. R4W1-A 커널은 부팅 0.892초에 계열 42 등록을 기록했다. 해당 서버 소켓의 계열을 직접 보관한 행은 확인되지 않았다. 두 코드 경로 모두 수신 주소에서 노드 다음에 포트를 읽으므로 위 발신 주소 해석은 같다. ### FYG8 RILD가 DMS 모드 응답에 표시하는 크기와 오류

7월 14:20 R4W1-A의 `ReceiveMessage` 행은 모드 조회에 `size(20)`을 표시했다. FYG8 배포 `libsec-ril.so`의 조회 함수는 메시지 `0x2D`의 거래를 준비할 때 응답 버퍼 크기 20을 지정한다. 수신 함수는 거래 객체의 해당 크기 필드를 로그에 출력한다. 이 값으로 그때 전송된 QMI 본문의 길이나 선택 필드 유무를 판정할 수 없다.

FYG8 라이브러리의 DMS 응답 테이블에서 이 메시지에 해당하는 기술자와 공통 결과 형식 참조를 추출했다. 앞서 ARM64 VM에서 수신한 합성 모드 5·0 응답을 FYG8 배포 QMI 디코더로 각각 해석했다. 두 응답 모두 본문은 11바이트, C 구조체는 20바이트였고 선택 필드 두 개의 유효 표시는 모두 0이었다. 모드 5 본문에 정상 선택 필드 두 개를 넣은 대조에서는 본문·구조체가 각각 20바이트였고 유효 표시는 모두 1이었다. 세 경우 모두 다시 인코딩한 필드의 번호와 값이 입력과 일치했다. 11바이트와 20바이트는 QMI 헤더를 제외한 본문 길이다.

배포 RILD의 수신 행은 `err`를 부호 있는 10진수로, 해석 결과 행은 `result`와 `err`를 16진수로 출력한다. 예를 들어 해석 결과 행의 `err(10)`은 십진수 16이다. 보관된 무선 로그에서 UID·태그·메시지 조건에 맞춰 RILD 5,828행에 필터를 적용하자 GET 송신·수신·해석 세 줄만 남았다. 동일 PID·TID의 표시 순서는 확인할 수 있다. 이 세 줄에는 전송 거래 번호와 물리 에지 정보가 없다.

### FYG8 공장 배포본에서 원격 저장소 초기 파일명 확인

FYG8 파티션 표는 MODEMST1·MODEMST2·FSG의 플래시 파일 이름을 각각 `nvrebuild1.bin`, `nvrebuild2.bin`, `nvrebuild3.bin`으로 지정한다. CP 내부와 Odin 직접 멤버에 이어, 같은 배포본의 파일시스템 14개와 FOTA ZIP 두 개를 확인했다. 디렉터리 항목의 마지막 이름을 대소문자 구별 없이 비교했고 압축 확장자 `.lz4`도 허용했다.

| 검사한 배포 자료 | 확인한 이름 수 | 세 파일명과 일치 |
| --- | ---: | ---: |
| AP `super` 안의 system·odm·product·system_ext·vendor·vendor_dlkm | 13,581 | 0 |
| CSC·HOME_CSC의 cache·omr·prism·optics, 중복 이미지를 제외한 다섯 개 | 287 | 0 |
| AP가 배포한 persist·vm-bootsys·userdata | 54 | 0 |
| AP·CSC의 FOTA ZIP 직접 항목 | 1,459 | 0 |

공장 AP와 `super`의 SHA-256을 보관된 배포 검증 기록과 대조했다. 각 논리 파티션의 길이를 확인했고, system·vendor를 다시 추출한 해시는 이전 독립 추출과 일치했다. F2FS는 읽기 전용으로 마운트한 호스트 경로에서 검사기를 dry-run으로 실행했다. 공장 userdata에서는 이름이 있는 항목 27개, 루트 1개, 슈퍼블록이 지정한 쿼터 관리용 inode 3개를 합쳐 체크포인트의 31개와 대조했다. ext4는 루트 inode부터 하위 디렉터리 항목을 따라갔다. 모두 배포 파일을 대상으로 한 호스트 검사다.

vendor의 `init.qcom.efs.sync.sh`도 확인했다. inode 안에 직접 들어 있는 원문은 기존 추출과 바이트 단위로 일치했다. 스크립트 본문은 경로 환경을 설정하고 sysfs의 `force_sync` 속성 두 개를 읽는다. 초기 파일을 복사하거나 생성하는 명령은 없었다.

이 범위에서 파티션 표에 지정된 이름의 초기 파일은 발견되지 않았다. 파일 본문 안에 다른 이름·형식으로 들어 있는 데이터와 단말별 저장소 내용은 미확인이다. 기존 합성 FS1·FS2·FSG 입력은 계속 VM 시험용이다. 파티션별 원시 목록과 해시, ZIP 멤버 대조는 `workspace/private/analysis/s22plus-factory-seed-census.lNjZjfDv/coverage.json`에서 추적할 수 있다.
